# C. Issues Found

### Issue 1: `fill` command fails with CSS selectors in direct mode but works in batch

**Severity:** Critical
**Category:** Product / Reliability

**Reproduction:**
```
browser4-cli fill "#first-name" "Alice"
```
**Expected:** Text "Alice" filled into the `#first-name` input field.
**Actual:** Error 鈥?`ERROR: browser_type failed: No node with given id found`
**Workaround:** Same command works inside batch mode: `browser4-cli batch "fill #first-name 'Alice'"`

**Suggested Improvement:** Unify CSS selector resolution between direct and batch command paths. The `browser_type` backend tool should accept CSS selectors consistently, or the CLI should resolve CSS selectors to accessibility refs before dispatching.

---

### Issue 2: Batch including `goto` causes 120s HTTP timeout

**Severity:** High
**Category:** Reliability

**Reproduction:**
```
browser4-cli batch "goto http://localhost:18080/generated/form-filling.html" "fill #first-name 'Alice'"
```
**Expected:** Navigate and fill the form in one batch invocation.
**Actual:** `Error: HTTP request timed out [tool=command_batch, timeout=120s]`
**Workaround:** Run `goto` separately before `batch`.

**Suggested Improvement:** Investigate why `goto` inside batch hangs on the backend. The documentation and README both show `goto` in batch examples 鈥?this should work reliably.

---

### Issue 3: `batch` command hidden from main help output

**Severity:** High
**Category:** Discoverability

**Reproduction:**
1. Run `browser4-cli help` and scan the output.
2. Look for "batch" command.

**Expected:** `batch` appears in the command listing (or at least a note saying "see `help batch` for batch mode").
**Actual:** `batch` is only discoverable if the user already knows to run `browser4-cli help batch`. The global help lists 40+ commands but omits `batch`, `extract`, `summarize`, `agent`, `swarm`, `domsnapshot`, `console`, and `pdf`.

**Suggested Improvement:** Add a one-line entry for `batch` (and other advanced commands) in the global help output with a pointer to `help <command>` for details.

---

### Issue 4: Inconsistent CSS selector support documentation

**Severity:** Medium
**Category:** Documentation / UX

**Reproduction:**
1. Read `browser4-cli help` 鈥?`fill` says "ref: Exact target element reference from the page snapshot".
2. Read `browser4-cli help` 鈥?`type` says "ref: Optional CSS selector or element reference to type into".
3. CSS selectors actually work for `fill`, `click`, `check`, and `select` (at least in batch mode), but only `type` documents it.

**Expected:** Consistent description across commands 鈥?either all mention CSS selectors or all mention snapshot refs, with clear documentation of which is accepted where.
**Actual:** Mixed and misleading descriptions. `fill` says "Exact target element reference" yet CSS selectors work in batch.

**Suggested Improvement:** Standardize the arg descriptions. Either use "CSS selector or element reference" for all ref-accepting commands, or clearly document the expected format for each.

---

### Issue 5: Batch output is confusingly minimal

**Severity:** Medium
**Category:** UX

**Reproduction:**
```
browser4-cli batch "fill #first-name 'Alice'" "select #country us" "click #submit-btn"
```
**Expected:** Clear indication of which commands ran and their results.
**Actual:** Output is just `[us]` 鈥?the return value of the last `select` command. The fill and click results are invisible. The `[us]` prefix format is unexplained.

**Suggested Improvement:** Batch should print per-command status (at minimum: command name + success/failure), or add a `--verbose` flag. The `[]` bracket format needs documentation.

---

### Issue 6: `eval` command produces no output on success

**Severity:** Medium
**Category:** Product / UX

**Reproduction:**
```
browser4-cli eval "JSON.stringify(window.__browser4State)"
browser4-cli eval "document.title"
```
**Expected:** Printed return value of the expression.
**Actual:** First command produced no output at all (silent success). Second command produced no visible output either.

**Suggested Improvement:** `eval` should always print its return value when the expression evaluates successfully. Silent success is confusing.

**Reproduction:**
