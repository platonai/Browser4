### Issue 1: Task instructions assume Cargo, but project uses npm

- **Severity:** Medium
- **Category:** Documentation
- **Reproduction:** Run `cargo run -- help` in `cli/` directory
- **Expected:** Command succeeds with help output
- **Actual:** Fails with "could not find Cargo.toml". The actual binary is installed via npm and invoked as `browser4-cli`.
- **Suggested:** The evaluation task instructions should detect the project type, or the project root README should be clearer that `cli/` is a packaging directory, not the Rust source root. The Cargo.toml is in `cli/browser4-cli/`, not `cli/`.

---

### Issue 2: `snapshot` command does not display inline content

- **Severity:** Medium
- **Category:** UX / Discoverability
- **Reproduction:** Run `browser4-cli snapshot`. Output shows only a file path.
- **Expected:** Snapshot content displayed inline in terminal, or at minimum a clear indication of how to view it.
- **Actual:** Only a file path like `[Snapshot](snapshot-2026-...yml)` is shown. The user must separately open the YAML file.
- **Suggested:** Add an `--inline` flag to print the snapshot tree to stdout, or make inline display the default for interactive use. The current UX creates a context-switching burden 鈥?the user must open another file to find element refs, then return to the CLI.

---

### Issue 3: `type` command times out but may partially execute

- **Severity:** High
- **Category:** Reliability
- **Reproduction:** Run `browser4-cli type "pens to draw on whiteboards" e37` on an Amazon search box.
- **Expected:** Either succeed with text typed, or fail cleanly with no side effects.
- **Actual:** Command times out after 30s with error `HTTP request timed out`. However, the search later showed the query was typed (possibly twice), suggesting the action executed despite the timeout error. This creates an unreliable state where the user doesn't know if the command worked.
- **Suggested:** Increase the default timeout for `type`/`fill` commands. Distinguish between "operation timed out but may have succeeded" and "operation definitely failed". Add a mechanism to check whether text was actually typed.

---

### Issue 4: `fill` command times out identically to `type`

- **Severity:** High
- **Category:** Reliability
- **Reproduction:** Run `browser4-cli fill e37 "pens to draw on whiteboards"` on an Amazon search box.
- **Expected:** Either succeeds or fails cleanly.
- **Actual:** Same 30s timeout as `type`. Both text-input commands share the same timeout path.
- **Suggested:** Same as Issue 3 鈥?increase default timeout and improve error reporting. Consider that `fill` and `type` use different underlying MCP tools (`browser_type` vs `browser_press_sequentially`) but both hit the same timeout ceiling.

---

### Issue 5: Search query was duplicated due to timeout/silent-execution

- **Severity:** Medium
- **Category:** Reliability
- **Reproduction:** Have a `type` command timeout, then type again. The search URL contained: `k=pens+to+draw+on+whiteboardspens+to+draw+on+whiteboards`
- **Expected:** Query appears exactly once in the search URL.
- **Actual:** Query appears twice, concatenated. This directly resulted from Issue 3 鈥?the timed-out command actually typed the text, then the second command added it again.
- **Suggested:** This is a consequence of Issue 3. Fixing the timeout/misreporting will fix this. Additionally, `type` could clear the field before typing, or `fill` could replace content rather than append.

### Issue 6: `press Enter` output shows stale page URL

- **Severity:** Medium
- **Category:** Reliability / UX
- **Reproduction:** Type a search query, press Enter. The command output shows the same page URL as before.
- **Expected:** Output should reflect the post-submission page (or wait for navigation).
- **Actual:** `### Page - Page URL: https://www.amazon.com/` 鈥?same as before typing. The search did navigate (confirmed by later snapshot), but the output captured the pre-navigation state.
- **Suggested:** After `press Enter` (and similar navigation-triggering commands), wait for the page URL to change before capturing output. Use the `wait --url` mechanism internally.

---

### Issue 7: `extract` command consistently times out at 30s

- **Severity:** High
- **Category:** Reliability
- **Reproduction:** Run `browser4-cli extract "extract the name, price, rating..."` on a search results page.
- **Expected:** AI agent extracts structured data from the page.
- **Actual:** `HTTP request timed out [tool=agent_extract, timeout=30s]`. The 30-second hard timeout is too short for AI-based extraction which requires LLM inference time.
- **Suggested:** Increase the agent tool timeout significantly (at least 120s). Document the expected latency. Provide a `--timeout` flag for long-running operations. Make the timeout configurable.

- **Suggested:** Add a spinner or elapsed-time indicator for commands that take more than 1-2 seconds. This gives the user confidence the tool is working, not stuck.
