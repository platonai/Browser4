# Deliverable C: Issues Found

---

### Issue 1: `cargo run -- help` fails 鈥?misleading first impression

**Severity**: Medium
**Category**: Documentation / Discoverability

**Reproduction**:
1. Enter the `cli/` directory
2. Run `cargo run -- help`

**Expected**: The SKILL.md instructions say "Before performing any browser interaction: 1. Run `cargo run -- help`." This implies it should work from the `cli/` directory.

**Actual**: Fails with `error: could not find Cargo.toml`. The project uses npm/pnpm for distribution, not Cargo from this directory. The Cargo.toml exists at a higher level or only for native build steps.

**Suggested Improvement**: Update the evaluation instructions or add a note in SKILL.md that `browser4-cli help` (global CLI) is the correct first command, not `cargo run -- help`. Alternatively, document that `cargo build` is only for native binary compilation via `npm run build:native`.

---

### Issue 2: `scroll down <px>` returns help output instead of scrolling

**Severity**: High
**Category**: Reliability / Product

**Reproduction**:
1. Open any page with `browser4-cli open <url>`
2. Run `browser4-cli scroll down 500`

**Expected**: Page scrolls down 500px with a success message or updated snapshot.

**Actual**: The command outputs the full help text (Usage listing all commands), as if the command was not recognized. This happened consistently across multiple attempts.

**Suggested Improvement**: Investigate the scroll command parser. The syntax `scroll down <px>` is documented in SKILL.md and matches the help output format, but it's silently falling through to the help handler. The `mousewheel` and `eval "window.scrollBy(...)"` workarounds exist but are not intuitive for new users.

---

### Issue 3: Backend HTTP timeouts (`click`, `summarize`, etc.)

**Severity**: High
**Category**: Reliability

**Reproduction**:
1. Open a page and wait briefly
2. Run `browser4-cli click <ref>` or `browser4-cli summarize "..."`

**Expected**: Command executes within a reasonable time.

**Actual**: `HTTP request timed out [tool=browser_click, endpoint=http://localhost:8182/mcp/call-tool, timeout=30s]`. Occurred on 3 separate commands (click e311, summarize, click e22527).

**Suggested Improvement**: The default 30-second timeout may be too short for some operations on complex pages (like Baidu with its dynamic content). Consider increasing the default timeout for click/agent operations, or implement automatic retry with backoff. The error message could also suggest checking backend health (`browser4-cli status`).

### Issue 4: `get text <ref>` returns help output on stale refs

**Severity**: Medium
**Category**: UX / Reliability

**Reproduction**:
1. Navigate to a page (refs are assigned)
2. Perform an action that changes page state (click, navigate)
3. Try `browser4-cli get text <old-ref>`

**Expected**: An error message like "Ref e12509 not found on current page" or "Stale ref 鈥?take a fresh snapshot."

**Actual**: The command outputs the full help text, which is confusing and makes it look like the command syntax was wrong rather than the ref being stale.

**Suggested Improvement**: Detect stale/invalid refs and produce a specific, actionable error message. Falling through to help output for invalid refs is misleading.

---

### Issue 5: Snapshot refs become stale after any page interaction

**Severity**: Medium
**Category**: UX

**Reproduction**:
1. Take a snapshot, note a ref (e.g., e311 for search button)
2. Use `fill` on a textbox
3. Try to `click` the previously noted ref

**Expected**: The ref should remain valid if the element still exists on the page.

**Actual**: Refs are regenerated on every interaction (the accessibility tree is re-enumerated), making previously captured refs invalid. The user must take a new snapshot after every action to get current refs.

**Suggested Improvement**: This is a fundamental design choice, but the documentation should emphasize this more strongly. The workflow description "snapshot 鈫?click e15" implies refs persist, but they don't survive intermediate commands. A note like "鈿狅笍 Refs are only valid for the next immediate command 鈥?you must snapshot again before any subsequent interaction" would help.

### Issue 6: No `--json` output for snapshots returned to stdout

**Severity**: Low
**Category**: UX / Discoverability

**Reproduction**:
1. Run `browser4-cli snapshot --json`

**Expected**: Snapshot data returned as JSON to stdout.

**Actual**: The `--json` flag exists as a global option, but snapshots are always written to YAML files on disk. The command output references a file path. There's no way to get snapshot data directly in stdout without reading the file.

**Suggested Improvement**: Allow `browser4-cli snapshot --json` to output the accessibility tree as JSON directly to stdout, or document clearly that snapshots are file-only and must be read from disk.

---

### Issue 7: `summarize` and `extract` commands are unreliable on complex pages

**Severity**: High
**Category**: Reliability

**Reproduction**:
1. Navigate to a content-heavy page like Baidu search results
2. Run `browser4-cli summarize "..."`

**Expected**: AI-powered summary returned within reasonable time.

**Actual**: Timed out (30s). The `summarize` command seems to send the page content to an AI backend that times out on rich pages.

**Suggested Improvement**: These agent commands are among the most valuable for task completion but also the least reliable. Consider streaming partial results, implementing a longer timeout with progress indication, or chunking large pages.

---

### Issue 8: Baidu-specific interaction challenges not documented

**Severity**: Low
**Category**: Documentation

**Reproduction**: Attempt to use browser4-cli on Baidu.com.

**Actual**: Baidu uses dynamic placeholder text in the search box (trending topics), complex redirect URLs, and JavaScript-heavy rendering. The search button ref becomes stale after typing. These are common challenges but not addressed in documentation.

**Suggested Improvement**: Add platform-specific notes for popular Chinese sites (Baidu, Taobao, JD.com) that are likely targets for browser4-cli users. Document known quirks and recommended workflows.

---

### Issue 9: Installation verification is unclear for first-time users

**Severity**: Medium
**Category**: Discoverability / Documentation

**Reproduction**: A first-time user reading SKILL.md.

**Expected**: Clear indication of how to verify installation succeeded.

**Actual**: SKILL.md documents installation methods (`npm install -g browser4-cli`, PowerShell script, bash script) but doesn't provide a verification step. The "Quick start" assumes `browser4-cli install` was already run separately. A user who runs `browser4-cli open` without first running `browser4-cli install` might encounter unclear errors if the Java backend isn't available.

**Suggested Improvement**: Add a "Verify installation" section: `browser4-cli --version` should return a version number, and `browser4-cli status` should show backend health. Document that `browser4-cli install` is needed before `open`.

---

### Issue 10: SKILL.md references `cargo run` but the project is npm-distributed

**Severity**: Medium
**Category**: Documentation

**Reproduction**: The evaluation instructions say to run `cargo run -- help`. SKILL.md mentions "Installs the native Rust binary" but the primary installation method is npm.

**Actual**: The project mixes Rust (native binary) and npm (distribution wrapper) in a way that's confusing. The Cargo.toml exists in a parent directory and is only used for build steps. A new user would be confused about whether this is a Rust project or a Node.js project.

**Suggested Improvement**: Clarify the architecture: browser4-cli is a Rust binary distributed via npm. For development, use `npm run build:native` not `cargo run`. For usage, `browser4-cli` is the only command needed.
