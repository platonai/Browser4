Swarm 后端插件化迁移评估

评估对象：将 swarm 命令的后端实现（browser4-rest）迁入运行时插件  |  2026-08-17  |  基于 Browser4-4.14 代码实查

结论：可行，但不建议"大爆炸式"整体搬迁。
"swarm 后端"实际是两层：① 会话机制层（SessionKind.SWARM、PulsarSessionManager.ensureSwarmSession、AgenticContexts）——被 ScrapeService（crawl）和会话路由共享，必须留在核心；② 任务门面层（SwarmController + SwarmService + SwarmToolExecutor，约 600 行 + 4 个测试类）——理论上可搬，但插件注册 @RestController 在本仓库无先例、未验证，且存在对 browser4-rest 内部类的编译依赖，违背现有 PDK 插件只依赖 skeleton/protocol/agentic 的惯例。推荐"接缝提取 → 控制器插件验证 → 门面搬迁"三阶段路径，或采用风险更低的核心保留薄 REST 门面 + 插件承载实现变体。
实施状态（2026-08-19）：方案 B 已落地。
核心保留薄 SwarmController（7 个端点路径与裸 UUID 契约不变），通过 agent-tools 中的 SwarmFacade SPI + SwarmFacadeRegistry（ToolMount 式）委托；实现迁入新插件 browser4-plugins/browser4-swarm（SwarmService/SwarmToolExecutor/SwarmAutoConfiguration，@ConditionalOnBean(SwarmSessionProvider) 保证无宿主 bean 时优雅退避）。共享的 ScrapeStatusRequest/ScrapeHyperlinkFactory 下移到 browser4-agent-tools；会话仍由 rest 的 SwarmSessionProviderConfiguration 以 SwarmSessionProvider 接口提供给插件。插件缺失时返回 503 {"error":"Swarm not installed"}。验证：插件持久化测试 5/5、SwarmControllerTest 13/13、SwarmControllerE2ETest 5/5（含真实浏览器抓取）全部通过。

1. 现状盘点：swarm 后端由什么构成

组件位置行数/规模可搬性
SwarmController（7 个端点：open / submit / query / count / status / {id}/status / {id}/result）browser4-rest~144 行条件可搬
SwarmService（Caffeine 任务缓存 + JSONL 持久化 + 2 个清理协程）browser4-rest~273 行条件可搬
SwarmToolExecutor + SwarmToolMountConfiguration（MCP/LLM 工具，domain="swarm"）browser4-rest~135 行可搬（ToolMount 是官方插件挂载点，weather 等插件已在用）
ScrapeHyperlinkFactorybrowser4-rest~53 行共享——ScrapeService（crawl）同样依赖，不能随 swarm 走；其 import 全部来自 agentic，可下移
SessionKind.SWARM 路由 + PulsarSessionManager.ensureSwarmSessionbrowser4-rest散布必须留核心——ScrapeService 直接用 swarm 会话做分布式抓取；getOrCreateSession 按 SWARM_SESSION_ID 特判路由
AgenticContexts.ensureSwarmSessionbrowser4-agentic—必须留核心（agentic 本就是插件 provided 依赖，无需搬）

CLI 侧（Rust）http.rs 中 4 个函数硬编码 /api/swarm/submit|query|{id}/status|{id}/result 路径，且 submit 依赖裸 UUID 字符串（非 JSON 包裹）响应格式——这是搬迁时必须原样保留的线上契约。

2. 插件体系能承载什么（实查结论）

  • 加载机制支持：PluginClasspathEnhancer 在 main()、Spring 启动之前把 plugins/*.jar 挂进 URLClassLoader 并设为 TCCL，Spring Boot 可发现其中的 AutoConfiguration.imports。因此插件 auto-config 里用 @Bean 注册的 @RestController，理论上会被 RequestMappingHandlerMapping 在 context refresh 时正常映射。机制成立。
  • 但没有先例：现有 7 个插件（weather/captcha/images/markdown/media/pptx/seo）全部只走 ToolMount（工具执行器）+ 事件挂载，零个注册 REST controller。这条路径未经测试，属新能力开拓，需要 PDK 补文档 + 验证测试。
  • 依赖惯例：插件 pom 对 skeleton/protocol/agentic 全部 provided。而 SwarmService 直接注入 PulsarSessionManager（browser4-rest 类）、用 ScrapeStatusRequest（rest entities）——插件要么新增对 browser4-rest 的 provided 依赖（破坏惯例，且与宿主形成二进制版本耦合），要么先把接缝下移。
  • manifest dependsOn 不被强制：PluginService 实际只读 name/version/description/autoConfigurationClasses，依赖声明目前纯文档性质。
  • AOT 影响（Leyden）：插件类不入 AOT cache 是既定形态。搬出后 swarm 相关类启动时按传统路径加载——量级很小（几个类），代价可忽略；同时 browser4-rest 主链路反而略瘦。

3. 收益 vs 风险

维度评估
核心瘦身browser4-rest 减约 550–800 行 + 2 个单测类。收益真实但有限——会话机制层本来就得留下。
战略价值高 "插件可注册 REST 端点"一旦打通，插件生态就能交付服务端能力（不只是工具），与"插件是核心产品决策"的定位一致。swarm 是个不错的试点候选。
独立演进swarm 任务队列（TTL、compact、stale 超时逻辑）迭代频繁，独立发版可减少核心发版节奏压力。
可选性不需要 swarm 的部署可移除插件；但 CLI 的 7 个 swarm-* 命令会得到 404——需要 CLI 侧优雅降级提示（目前直接报错，可接受但需文档化）。
未验证路径主要风险 controller-in-plugin 无先例：类加载器可见性（parent-first，宿主类对插件可见 ✅）、Jackson 对 ScrapeResponse（agentic 类）序列化、Spring MVC 扫描时机，都需 spike 验证。
测试迁移SwarmControllerTest、SwarmServicePersistenceTest、SwarmControllerE2ETest、SwarmCrawlFixtureTest 需随迁或改造；CLI/Rust e2e 用 mock server 按 HTTP 黑盒测，路径不变即不受影响；tests-production 的 PS1 压测脚本同理不受影响。
打包browser4-standalone 打包必须把插件 jar 放入 plugins/，否则开箱即坏的 swarm——发布矩阵多一个组合。
耦合残留抽象渗漏插件实现仍需拿到 swarm 会话（PulsarSessionManager 或等价接口）。若不做接缝提取，插件将编译依赖宿主内部类，宿主每次重构都可能破坏插件二进制兼容。

4. 推荐路径

方案 A（推荐）：三阶段渐进

  • 阶段 1 — 接缝提取（1–2 天，纯重构零行为变化）：
    • ScrapeHyperlinkFactory、ScrapeStatusRequest 从 browser4-rest 下移到 browser4-agentic（前者 import 已全是 agentic 类，零阻力；ScrapeService 改 import 即可）；
    • 在 agentic 定义 SwarmSessionProvider 接口（fun session(): GenericAgenticSession），由 rest 的 PulsarSessionManager 提供实现 bean——插件从此不碰任何 rest 类；
    • 验证：现有 4 组 swarm 测试全绿。
  • 阶段 2 — 能力验证（1 天）：写一个 spike 插件注册最简 @RestController（如 /api/hello），跑通 Spring MVC 映射 + REST e2e + AOT cache 启动回归。通过后把"controller 挂载"写入 PDK 文档与 browser4-plugin-archetype。
  • 阶段 3 — 门面搬迁（3–5 天）：新建 browser4-plugins/browser4-swarm，迁 SwarmService/SwarmController/SwarmToolExecutor + 测试；browser4-rest 删除原实现与 SwarmToolMountConfiguration；standalone 打包含插件；CLI 保持路径与响应格式逐字节不变。

方案 B（低风险替代）：核心薄门面 + 插件实现

REST controller 留在核心作为 ~40 行薄壳，仅做参数校验后委托给 agentic 中定义的 SwarmFacade 接口；插件通过 ToolMount 式注册表提供实现。线上契约、CLI、打包全部不动，插件缺失时返回明确的"swarm 未安装"错误。如果战略目标只是"实现放插件里"而非"端点也放插件里"，这是成本最低、风险最小的形态。

方案 C（不推荐）：整体大爆炸搬迁

一次性把 controller+service+tool 塞进插件。技术上有机会成功，但同时引入未验证的 controller 挂载、rest 编译依赖、测试搬迁、打包变更四类风险，出问题时定位面太大。

5. 必须保留在核心的清单（搬迁红线）

  • SessionKind.SWARM 与 PulsarSessionManager 的 SWARM 路由特判（ConcurrentHashMap 嵌套 computeIfAbsent 的规避逻辑依赖它）；
  • AgenticContexts.ensureSwarmSession（ScrapeService 的分布式抓取建立在它之上）；
  • ScrapeHyperlinkFactory 的共享语义（下移到 agentic，而非进插件）；
  • REST 路径 /api/swarm/** 与 submit 返回裸 UUID 的契约（若走方案 A 阶段 3，由插件逐字节复刻）。
