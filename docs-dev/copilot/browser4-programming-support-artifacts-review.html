3. P1 契约错位（模板/校验器 vs 真实运行时）

P1 plugin.json 字段与真实 PluginManifest 不符

真实契约（browser4-skeleton/.../plugin/PluginManifest.kt）：必填 name、version；可选 description、dependsOn、autoConfigurationClasses。真实插件（browser4-captcha/markdown/seo）均用此结构。

脚手架生成的是：{"id", "name", "version", "domain", "description"} —— 多出 id/domain（Jackson 因 FAIL_ON_UNKNOWN_PROPERTIES=false 宽容，但语义不对），缺失 dependsOn 与 autoConfigurationClasses。后者是 PluginService.isPluginLoaded() 判断插件是否已激活的第一检查项（按自动配置类查 Bean）；缺失会导致「已加载插件显示为未加载」。且 name 用了 toClassName()（如 "Browser4Seo"），而真实插件 name 是 artifact 名（"browser4-seo"），isPluginLoaded 的 removePrefix("browser4-") 域推导随之失效。

校验器同病：ArtifactValidator.validatePluginJson 把 id 当必填——真实 manifest 根本没有 id，用它校验真实插件会误报。

browser4-skeleton/.../plugin/PluginManifest.kt · browser4-boot/.../plugin/PluginService.kt:205-234 · ArtifactScaffolds.kt:118-126 · ArtifactValidator.kt:162-186

P1 脚手架生成的 AutoConfiguration 未实现 ToolMount → 工具永远不会注册

工具暴露链是 PluginManager 扫描 PluginMount Bean → ToolMount.getToolExecutors() → CustomToolRegistry → 渲染进 LLM prompt（ToolCallSpecificationRenderer）。参考插件 browser4-seo 的 SeoAutoConfiguration : ToolMount 并重写 getToolExecutors()。而脚手架生成的 AutoConfiguration 只有两个 @Bean（config + toolExecutor），没有实现 ToolMount——照模板写出的插件即使编译安装成功，工具也永远不会进入 CustomToolRegistry，Agent 完全看不到。

browser4-agentic/.../tools/ToolMount.kt · browser4-boot/.../plugin/PluginManager.kt:148-162 · ArtifactScaffolds.kt:145-171（对照 browser4-plugins/browser4-seo/config/SeoAutoConfiguration.kt:45-56）

P1 skill frontmatter 字段与 SkillDefinitionLoader 不符

真实加载器（SkillDefinitionLoader.parseFromYamlAndMarkdown）要求：name（须与目录同名、kebab-case、≤64 字符）与 description（1..1024 字符）必填；另有 allowed-tools 等可选。脚手架与校验器却围绕 summary + read_when 展开——按脚手架生成的 SKILL.md 在真实加载器下会被 require(rawDescription.isNotBlank()) 直接拒绝。校验器会放行加载器拒绝的技能，等于「校验通过 ≠ 可加载」。

注意：仓库自带技能（browser4-cli / browser4-seo / browser4-experience）均使用 name + title + description + tier 结构，与加载器一致；脚手架/校验器反而偏离了仓库既有惯例。

browser4-agentic/.../skills/SkillDefinitionLoader.kt:423-438, 529-535 · ArtifactScaffolds.kt:273-307 · ArtifactValidator.kt:274-327

P1 脚手架 pom 依赖未定义的 ${revision}，且依赖声明不足

脚手架 pom 的 parent version 写死 ${revision}，但本仓库 36 个 pom.xml 均无 <revision> 属性（pulsar-parent 4.5.0 亦无），真实版本是字面量 4.13.4-SNAPSHOT——照模板生成的插件直接 mvn compile 会因 parent 无法解析而失败。另：脚手架只声明了 browser4-agentic（provided），生成的代码还用到 MutableConfig/ImmutableConfig（browser4-common）与 spring-boot-autoconfigure（@AutoConfiguration 注解），参考 seo pom 明确声明了 browser4-skeleton/browser4-protocol/spring-boot-autoconfigure 等，脚手架需补齐。

ArtifactScaffolds.kt:91-116（对照 browser4-plugins/browser4-seo/pom.xml 全量依赖）

P1 validate 的 plugin 模式绕过沙箱文件系统

coding.validate(type=plugin) 直接用 java.io.File 读任意路径（ArtifactValidator.validatePlugin 内部 File(baseDir).walkTopDown() + readText()），而 coding 域其他文件操作都经 CodingAgentFileSystem.resolvePath() 做 workspace 沙箱约束。该入口绕过了路径穿越防护，且对超深/超大目录有性能与 IO 风险，应改为经 fs 解析路径或显式限制在 workspaceRoot 内。

CodingToolExecutor.kt「validate」分支 · ArtifactValidator.kt:76-157 · CodingAgentFileSystem.kt resolvePath

7. 结论

架构判断不变：以 coding.scaffold → coding.write → coding.validate → coding.shell/tab.eval 组织四类工件生产，方向正确且贴合编程内核定位；JS 场景已是差异化亮点。当前状态是「骨架已在工作区、但不可编译、契约未对齐」——上一轮把「缺什么」收敛到模板+校验是对的，但交付前提是能编译且模板与真实加载链路一致。按 P0+P1 六条修复后，四场景可全部端到端打通；届时编程支持评级可从上轮 B+ 提升至 A-。
