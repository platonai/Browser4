Browser4 服务器端 AOT 优化方案深度分析

2026-08-15 · 基于 Browser4-4.14 工作区 · Spring Boot 4.0.6 / Kotlin 2.3.21 · 本文为《启动速度优化评估》的 AOT 专项补充
结论（TL;DR）

社区口语里的「AOT」其实是三件原理、产物、约束都不同的事，混为一谈会得出错误结论：

  • JVM AOT Cache（Project Leyden，JEP 483/514/515）——纯 JVM 旗标，缓存「已加载+已链接」的类与 JIT 热点 profile。它不改变 bean 装配来源，因此与 Browser4 的运行时插件加载（PluginClasspathEnhancer 的 URLClassLoader）无冲突，是唯一可默认启用的 AOT。硬前提是 JDK 24/25：官方 bundle 已是 25（可用），但 Dockerfile/本地开发默认 21（需升或回退 AppCDS）。
  • Spring AOT（spring.aot.enabled=true）——构建期生成 bean 定义，消除运行时反射与条件评估。与插件动态加载结构性冲突，只能作为「无第三方插件」的独立发布形态。
  • GraalVM Native Image——整机 AOT 编译，启动最快但封闭世界假设，与插件模型彻底冲突；已铺路但仅适合 Serverless/冷启动场景。

三者可叠加：官方基准里 Spring AOT + AOT Cache 组合把 Spring PetClinic 压到 0.58s。对 Browser4 的务实路线是：先上 JVM AOT Cache（需 JDK 25 + 修 classpath 通配符 + 训练跑设计），再把 Spring AOT 作为无插件形态的可选项。

1. 先厘清：三种「AOT」不是一回事

一句话记忆：Spring AOT 消灭「框架自己的反射工作」；JVM AOT Cache 消灭「JVM 加载/链接类的工作」；GraalVM 把整个 JVM 都消灭了。前两者正交可叠加，后者是另一条路线。

2. JVM AOT Cache（Leyden）—— 首选，唯一无冲突的 AOT

2.1 原理：训练跑 + 冷凝器

Project Leyden 的核心思想是「把每次冷启动都重复做的 JVM 工作，在训练跑里做一次、固化下来复用」。普通 Spring Boot 应用冷启动要读入、解析、校验、加载、链接 15,000–25,000 个类——这些工作在每次启动都重来一遍。AOT cache 在训练跑中记录这些状态，冷凝成二进制缓存，之后每次启动直接从缓存取「已加载+已链接」的类。

2.2 版本演进

JEPJDK能力关键旗标
JEP 48324AOT 类加载与链接（AppCDS 的后继，缓存完整链接态而非仅解析元数据）-XX:AOTMode=record/create、-XX:AOTConfiguration、-XX:AOTCache
JEP 51425命令行人机工程：训练+组装合并为一步-XX:AOTCacheOutput=app.aot（训练+产出）、-XX:AOTCache=app.aot（生产）
JEP 51525AOT 方法 profiling：缓存 JIT 热点方法 profile，冷启动即热编译复用上述旗标，自动生效
JEP 51626AOT 对象缓存（任意 GC，含 ZGC），尚未发布—
# JDK 25 两步工作流
# ① 训练跑（记录 + 组装，进程退出时产出缓存）
java -XX:AOTCacheOutput=app.aot -cp lib/* MainClass --server.port=8182
# ② 生产跑
java -XX:AOTCache=app.aot -cp lib/* MainClass --server.port=8182
注意：单步 -XX:AOTCacheOutput 在组装阶段会另起一个同堆大小的子 JVM，内存峰值是命令里堆大小的 2 倍。若 -Xms2G -Xmx2G，则需 4GB。资源受限时改用三步（record → create → run），可在小实例训练、大实例组装。

2.3 硬约束（必须逐条满足，失配静默降级为普通启动）

  • 同一 JDK 版本：训练跑与生产跑必须用同一 JVM（版本号精确匹配）。
  • 同一 classpath（JAR 列表，非目录/通配）：缓存按 classpath 校验。这正是当前 daemon.rs 里 -cp {lib_dir}/* 目录通配符的致命障碍——目录通配符不产生稳定、有序的 jar 列表。
  • 同一 JVM 参数集：影响类加载/编译的参数（如 -XX:TieredStopAtLevel、GC 选择）需纳入缓存失效 hash。
  • 缓存失效策略：升级版本 / 换 JDK / 换参数后必须重新训练，否则静默回退。

2.4 对 Browser4 的适用性与缺口

为什么它是首选：PluginClasspathEnhancer 在 main() 里用 URLClassLoader 挂载 plugins/*.jar。JVM AOT cache 只缓存训练跑里实际加载过的类；插件类不在缓存里，就按普通路径加载——不报错、不降级功能，只是插件类享受不到缓存加速。这与 Spring AOT / native 的「封闭世界直接 break」本质不同。

当前缺口（要落地必须先补）：

  • JDK 版本三轨并存：官方 runtime bundle 经 release.yml 的 BUNDLE_JAVA_VERSION='25' 用 jlink 打包 Temurin JDK 25——AOT cache（JEP 483/514/515）对官方 bundle 用户直接可用。但 Dockerfile 运行时仍是 eclipse-temurin:21-jre-alpine，本地 install-depends.ps1 默认装 Temurin 21——这两条路径要么升 25、要么回退 AppCDS。
  • classpath 通配符：daemon.rs 的 -cp {lib_dir}/* 需改为显式枚举 lib/*.jar（runtime bundle 已产出 lib/ 目录，只需在启动器里展开为有序列表）。
  • 懒加载下的训练跑设计：spring.main.lazy-initialization=true 下，用 -Dspring.context.exit=onRefresh 训练会漏掉大部分 bean（都是懒代理）。训练跑应走「启动 → StartupWarmer 完成 → 一轮轻量 MCP 调用 → 退出」的仿真负载序列。
  • 缓存失效 hash：把「JDK 版本 + lib 目录 jar 内容 hash + 关键 JVM 参数集」作为缓存文件名或清单的 key。

3. Spring AOT —— 无第三方插件形态的可选项

3.1 原理与收益

process-aot 在构建期把 Spring 的注解扫描、条件装配、反射实例化提前算好，生成静态 bean 定义代码；运行时加 -Dspring.aot.enabled=true 跳过这些反射工作。它通常与 CDS / AOT cache 组合。独立测试（deepaksorthiya/spring-boot-docker，Spring Boot 4.0.3）：

形态启动耗时
exploded jar（基线）2.309s
+ AppCDS1.338s
+ Spring AOT + CDS0.92s
+ Spring AOT + AOT cache（JDK 24+）0.817s

3.2 结构性冲突：插件加载

Spring AOT 的约束原文是「classpath 在构建期固定且完全定义；bean 定义运行时不可变」。而 Browser4StandaloneApplication.kt 里：

if (System.getProperty("org.graalvm.nativeimage.imagecode") == null) {
    PluginClasspathEnhancer.enhance(Path.of("plugins"))  // 运行时动态挂 jar
}

第三方插件是「编译完成后丢进 ./plugins/」的分发方式，构建期根本不知道有哪些插件类，AOT 自然也无法为其生成 bean 定义。结论：Spring AOT 只适用于「插件全部打进 fat jar、无运行时扩展」的官方 bundle 形态。

3.3 与懒加载 / StartupWarmer 的交互

AOT 生成的代码预计算了条件装配结果；懒加载语义保留，但 AOT 会在需要处注入 bean 实例化逻辑。StartupWarmer 用 applicationContext.getBean(name) 触发创建，AOT 下仍成立——但必须重跑 SwarmCrawlFixtureTest 那类回归（懒加载+预热竞态曾导致 "Protocol not found (1600)"）。

3.4 其他约束

  • @Profile：AOT 下 profile 构建期固定。Browser4 在 main() 硬编码 standalone/private/advanced，反而 AOT 友好。
  • @ConditionalOnProperty(.enabled 类)：AOT 不支持「因属性改变而增减 bean」，需审计现有配置里是否有此类用法。
  • 现状：browser4-standalone/pom.xml 的 native profile 已含 process-aot，但那是为 native 服务的。缺一个「只 process-aot、不 native-image」的 JVM AOT 构建 profile。

4. GraalVM Native Image —— 场景化，已铺路未启用

已有铺路资产（全部存在，无需从零做）：

6. 关键发现（与既有《启动优化评估》的差异）

  • JDK 版本三轨并存，AOT cache 只在官方 bundle 直接可用：官方 runtime bundle 经 release.yml 的 BUNDLE_JAVA_VERSION='25' 用 jlink 打包 Temurin JDK 25（已解包验证），JEP 483/514/515 对官方 bundle 用户无需升级即可用。但 Dockerfile 运行时仍是 temurin:21-jre-alpine、本地依赖安装默认 Temurin 21——这两条路径上 AOT cache 不可用，只能回退 AppCDS（或升 25）。daemon.rs 需按「运行 JDK 版本」分叉：25+ 走 -XX:AOTCache，17–24 走 -XX:SharedArchiveFile。
  • pom 里 javaVersion=17 是遗留值，隐藏了「21+ 才能跑」的事实：Spring Boot 4（Spring Framework 7）运行时基线是 Java 21+（其依赖 jar 是 21 字节码）。release.yml 用 JAVA_VERSION='17' 编译（产出 17 字节码）、BUNDLE_JAVA_VERSION='25' 打运行时，所以整体能跑。但 javaVersion=17 会把 Browser4 自己的源码锁在 17 语法，并误导「可在 JDK 17 运行」（实际不能）。建议把 javaVersion 提到 21，顺带同步 dokka 的 jdkVersion。
  • classpath 通配符是 AOT cache/CDS 的隐性障碍：daemon.rs 的 -cp {lib_dir}/* 必须先改成显式 jar 枚举，CDS 与 AOT cache 都要求稳定有序的 classpath。
  • 懒加载削弱了「简单训练跑」的覆盖：-Dspring.context.exit=onRefresh 在懒加载下几乎不加载 bean，训练收益会打折，必须用仿真负载序列补。

7. 推荐路线（聚焦 AOT）

Tier 0 —— 先决条件（半天）

  • 官方 bundle 已是 JDK 25（JEP 515 可用），无需动；把 Dockerfile 运行时从 temurin:21-jre 升到 temurin:25-jre，本地开发态保留 21 并走 AppCDS 回退。
  • 把 daemon.rs 的 classpath 从目录通配符改为显式 lib/*.jar 有序枚举。
  • 修 pom javaVersion 17 → 21（消除与 Boot 4 的隐性不一致）。

Tier 1 —— JVM AOT cache（首选，约 1 周）

  • daemon.rs 增加：仿真负载训练跑（启动 → StartupWarmer 完成 → 一轮轻量 MCP → 退出）+ -XX:AOTCacheOutput 产出 + 按「JDK 版本 + jar 内容 hash + JVM 参数集」失效 + -XX:AOTCache 生产加载，失配静默回退。
  • JDK 21 上回退 AppCDS（-XX:ArchiveClassesAtExit / -XX:SharedArchiveFile），保证开发态也有收益。
  • 目标：端口就绪 ~2.0s → 1.0–1.4s，JEP 515 同时压低首条 CLI 命令的 warmup 延迟。

Tier 2 —— Spring AOT 无插件形态（按需，约 1–2 周）

  • 新增「JVM AOT」构建 profile（只 process-aot、不 native-image），产出 AOT-processed fat jar。
  • 审计 @ConditionalOnProperty / @Profile 用法；重跑懒加载预热竞态回归。
  • 与 Tier 1 叠加，向 0.6–0.9s 逼近。

Tier 3 —— GraalVM native（场景化）

  • 已有铺路资产，仅在 Serverless/密度敏感场景作为独立发布物，持续维护 hints。

8. 风险清单（AOT 专项）

  • AOT cache 失配静默降级：JDK/classpath/JVM 参数任一漂移都必须能回退普通启动，绝不能启动失败。缓存失效 hash 必须覆盖这三者。
  • 单步训练跑 2× 堆内存：-XX:AOTCacheOutput 组装阶段子 JVM 复用训练堆大小，小内存容器要用三步法。
  • C1 限档与 JEP 515 的张力：-XX:TieredStopAtLevel=1 禁止 C2，而 JEP 515 缓存的是热点方法 profile 供 JIT 用——C1 限档下方法 profile 的价值打折。若启用 AOT cache，应重新评估是否放宽 C1 限档（JEP 515 本身已能缩短 warmup）。
  • Spring AOT 条件装配审计：漏审一个 @ConditionalOnProperty 可能让某个 bean 在 AOT 形态下不出现，需靠现有测试兜底。
  • 懒加载 + 预热竞态回归：任何改 bean 初始化时序的方案（尤其 AOT）都必须重跑 SwarmCrawlFixtureTest。
