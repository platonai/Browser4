# Agent sandbox: no OS-level execution sandbox backend on Linux/macOS (default off, POSIX ids fail hard)

## Summary

On Linux and macOS the coding-agent execution sandbox has no working backend. `browser4.agent.sandbox` defaults to `off` on both platforms, and selecting one of the documented POSIX backends (`bwrap`, `nsjail`, `sandbox-exec`, `container`) aborts the task with `SandboxUnavailableException`, because those ids are recognized but not implemented yet. As a result `coding.shell` and `coding.runCode` run as the backend's own user with no OS-enforced boundary; only the in-process advisory layers remain.

## Current behavior

- `ExecutionSandbox.KNOWN_IDS` contains `off`, `windows-acl`, `bwrap`, `container`, `nsjail`, `sandbox-exec` (`browser4-coding/src/main/kotlin/ai/platon/pulsar/coding/sandbox/ExecutionSandbox.kt`). Only `off` and `windows-acl` are implemented; the POSIX ids hit the `in KNOWN_IDS ->` branch that throws "known but not implemented in this build". Unknown ids fail the same way, and `validateConfigured()` is called from `CodingComponents` init, so the failure happens when the coding domain is built, not on the first command.
- `SandboxDefaults.defaultForPlatform()` returns `windows-acl` only for Windows and `off` otherwise; the decision is persisted to `<dataDir>/sandbox-default` and reused on later starts.
- On POSIX, `ProcessLauncher` never gets a sandbox account, so commands are launched through a plain `ProcessBuilder` under the current user.

## What still applies (in-process only)

- Access presets (`full` / `write` / `read-build` / `read`, plus unattended derivation).
- `Authorizer` boundaries: canonical (`realpath`) for file tools, lexical for the shell.
- Shell command whitelist, protected and sensitive paths, inline-script validation.
- `SandboxEnvironment` variable whitelist for child processes.
- `coding.requestAccess` approvals (REST / CLI / workspace policy file) and permission audit events.

These are advisory at the OS level: a command that computes paths at runtime can still write anywhere the backend user can write, and an OS "permission denied" is indistinguishable from a boundary denial (`SANDBOX_DENIED` is never produced while the sandbox is `off`).

## Expected

POSIX backends (the P2 scope already described in `docs-dev/copilot/agent-permission-capability-model-design.md`):

- Linux: `bwrap` (`--ro-bind / /`, `--bind <workspace>`, `--tmpfs /tmp`, `--unshare-net`, `--clearenv`) or an `nsjail` / container equivalent.
- macOS: `sandbox-exec` profile or a container.
- Selecting an unimplemented backend should keep failing hard (fail-closed), but implemented ones must produce real OS-level denials.
- The platform default should switch to the working backend only after the evidence gate is satisfied.

## Acceptance criteria

1. Sandbox probe: writing inside the workspace succeeds, writing outside is rejected by the OS, and the rejection is reported as `SANDBOX_DENIED` rather than a generic tool failure.
2. Network access is actually cut when network is not granted (Linux: `--unshare-net`), and the child environment contains only whitelisted variables.
3. Linux CI runs the sandboxed E2E suite; macOS is either covered or explicitly documented as unsupported.
4. Docs updated: the `docs/config.md` default table and the two-layer boundary section of `skills/browser4-cli/references/agent.md` reflect the real per-platform default.

## Additional context

The implementation is mostly a `ProcessSpec` / launcher transformation; the design and parameter-level plan already exist (`docs-dev/copilot/agent-permission-capability-model-design.md`, `docs-dev/copilot/agent-permission-capability-model-dev-plan-v2.md`, P2-1..P2-4 and gate G2). The current blocker is verification evidence on Linux CI (and a macOS decision), not design work: the write-outside-workspace denial has not yet been demonstrated on a POSIX runner, which is exactly what the G2 gate requires before a backend can be enabled by default.
