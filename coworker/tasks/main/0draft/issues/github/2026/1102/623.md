## 背景

一次真实任务：在 amazon.com 上找当天最畅销的 20 台微波炉，逐个进详情页采集产品信息，按用户给的 75 列字段模板（`asin_field_description.xlsx`）写成电子表格。

环境：Windows + PowerShell，`browser4-cli` 4.15.2-SNAPSHOT，headless 会话。

任务最终做完了，但过程中踩到的坑比较集中。按用户要求，**把遇到的所有问题汇总到这一个 issue 里**整理成清单；下面每一条都可以单独拆成后续 issue。每条给的都是本机真实输出（不是推测），带 ✅ 的是已单独提过的，这里只做关联。

## 问题清单

### A. 本地文件：路径拿不到、表格读不动

- [ ] **A1 `coding_*` 系列工具拒绝工作区外的绝对路径，而任务给的正是这种路径**
  - 复现：`coding_stat {"path": "D:\\Backup\\Data\\20260719\\asin_field_description.xlsx"}`
  - 实际：`Error: Path not resolved: D:\Backup\Data\20260719\asin_field_description.xlsx`；`C:\`、`C:\Users\<user>\.browser4\workspaces` 同样报 `Path not resolved`，连 `..` 也不行。
  - 期望：支持一份显式 allow-list（或 `--allow-outside-workspace`），至少错误里回显"允许的根目录是哪里、怎么授权"，而不是只有一句 not resolved。
  - 关联：#573（user-facing local file support）。

- [ ] **A2 没有"读本地文件/表格"的原语，只能自己造页面去解析**
  - 现象：为了读一个 xlsx，只能先写一个 `sheetread.html`，再用 `-s sheet open file:///.../sheetread.html` 打开，然后在页面里用 JS 解析。`htmlsnapshot` 只能读"已经加载的页面"，`readability <url>` 也不适用于本地二进制。
  - 期望：`browser4-cli read <file>`（文本/CSV/xlsx 转表格）或让 `open file://x.xlsx` 直接给出可读结构。

- [ ] **A3 `upload` 的失败信息无法区分三种原因**
  - 复现：`upload "#f" "D:/Backup/Data/20260719/[asin]_[field]_[description].[xlsx]"`
  - 实际：`[INVALID_ARGUMENT] browser_file_upload failed: upload: file(s) not found or not readable on this machine: D:/Backup/Data/20260719/[asin]_[field]_[description].[xlsx]`
  - 问题：路径里带方括号时无法判断是"被当成 glob 展开成 0 个匹配"、"文件确实不存在"，还是"路径在本机不可达"；报错也没回显解析后的绝对路径。
  - 期望：默认按字面路径处理（glob 需显式开启），错误里回显 `resolved: <abs path>` + 具体原因。

- [ ] **A4 用 `file://` 兜底读文件时，整个文件内容都会进上下文**
  - 现象：打开 181 KB 的 jsonl / 247 KB 的页面快照后，`snapshot` / `innerText` 动辄 2K+ 行，需要靠 `--page`、`get` 一点点切。
  - 期望：给本地文本文件一个 `grep` / 分页读取的入口，而不是"全量塞进来再自己切"。

### B. Windows / PowerShell 下的命令组装

- [ ] **B1 内联 JS 会被 PowerShell 撕碎，报错完全是另一回事**
  - 复现：`browser4-cli eval "() => ({url: location.href})"`
  - 实际：`ParserError: Line | 1 | ... eval () => ({u ... | ~ | 表达式或语句中包含意外的标记`（并且中文输出变成乱码 `��`）。
  - 期望：解析到表达式被 shell 破坏（括号不配对、出现乱码）时，直接提示 `try eval --file script.js / --stdin / --base64`。现在 `eval --help` 里写了"Windows 建议用 --file"，但报错本身完全不指路，只能靠猜。

- [ ] **B2 全局 `-s/--session` 位置敏感，写在后面就被当成子命令自己的非法选项**
  - 复现：`browser4-cli open --headless "file:///C:/.../sheetread.html" -s sheet`
  - 实际：`error: unknown option -s for 'open' (the command takes 1 positional argument)`
  - 对照：`browser4-cli -s sheet open ...` 正常。
  - 期望：接受后置全局参数，或在报错里明写 "global options must precede the subcommand"。

- [ ] **B3 通用选项在子命令上不存在时，报错没有"你是不是想要…"**
  - 复现：`browser4-cli eval --stdout "() => 1"`
  - 实际：`error: unknown option --stdout for 'eval'`（`eval` 默认就打印结果，所以 `--stdout` 在很多命令上是对的、在 `eval` 上是错的）
  - 期望：quick reference 是按"能力"列 `--stdout` 的（snapshot/htmlsnapshot），实际是子命令级开关；建议在未知选项报错里附一句 `eval prints its result by default`，或统一支持。

- [ ] **B4 ✅ `snapshot grep` 的正则含 `|` 被 PowerShell 当管道拆开**
  - 已提：#622。这里只做关联：所有需要"多分支正则"的定位场景都会踩，建议随本清单一并推进（`--pattern-file`）。

- [ ] **B5 文件类参数的路径规范化与报错文案不统一**
  - 现象：`--file`、`--sql @f.sql` 能接受相对路径，但 `upload` 对 `D:/Backup/...`（正斜杠）和 `D:\Backup\...`（反斜杠）没有统一规范化，报错文案也不一样。
  - 期望：所有文件类参数统一走同一套路径规范化 + 同一套错误文案。

### C. 会话管理：命令发现性差

- [ ] **C1 `session` 不是命令，但最容易被猜到**
  - 复现：`browser4-cli session list`
  - 实际：`Unknown command: 'session'`
  - 真相：命令叫 `list`（还有 `session-default <name>`、`close-all`、`kill-all`）。
  - 期望：未知命令时给出最相近候选（像 git 那样 `Did you mean: list, session-default, status?`）。

- [ ] **C2 `list` 把 URL 截断，多会话调试时看不出谁在哪**
  - 现象：`list` 输出里 URL 只到 `file:///C:/Users/pereg/.browser4/workspaces/Bro…`，会话名与 UUID 两列并排（`doc` / `ext` / `gh` / `sheet` 混着 UUID），只能靠再切过去确认。
  - 期望：`list --json` 输出完整 URL + 标题 + 是否 headless，方便脚本判断该复用哪个会话。

- [ ] **C3 `-s <name>` 命中不到会话时的提示过于平淡**
  - 实际：`No active session — creating a new one.`（随后才打印 `Session opened: sheet (c9bea14f-…)`）
  - 期望：明确说"名字 `sheet` 下没有活跃会话，已新建"，并提示残留的同名会话（如果有）。

### D. 错误信息语义

- [ ] **D1 `No active session` 与 `Nothing to read` 分不清是"没开页面"还是"选择器没匹配"**
  - 现象：`wait` 类命令在无活动页时抛 `No active session`；元素始终不出现时抛 `Nothing to read`，两者语义重叠且都不带被等待的条件。
  - 期望：错误里带上"等待的选择器 / 已等待时长 / 当前 URL"。

- [ ] **D2 `Invalid CSS selector` 不回显是哪个选择器**
  - 现象：一个脚本里拼多个选择器时，只能靠删减猜是哪一条。
  - 期望：回显原始字符串。

### E. 采集任务本身（模板 / 字段语义）

- [ ] **E1 75 列模板没有 schema 校验，只能靠人眼对齐内部名与中文标签**
  - 现象：`asin_field_description.xlsx` 的 `Sheet2` 是 row0=内部名、row1=中文标签、row2+ 示例数据的"导出式"布局，没有类型、没有必填标记、没有分组；解析出来是 75 个裸列名，采集端要自己维护 40+ 字段映射。
  - 期望：`browser4-cli sheet schema <file>` 之类的命令，输出"列名 / 标签 / 类型 / 是否必填 / 示例值"，最好能直接生成 X-SQL 的 SELECT 骨架。

- [ ] **E2 可选字段的空值语义未定义**
  - 现象：`rank`、`coupon`、`boughttogethermetadata`、`jsVariables` 这类字段在多数详情页上并不存在；写回 xlsx 后"没采到"和"页面上确实没有"长得一样。
  - 期望：约定三态（缺失 / 空 / 有值），或在采集结果里带 `missing_fields` 汇总。

## 影响

- A 组让"读用户给的模板文件"这一步从 0 行代码变成"写 HTML + 起会话 + 页面内解析"，是本任务最长的单点耗时；
- B 组是 Windows 上每个新用户第一次跑就会撞的墙，且报错都指向错误的方向（shell 错误看起来像 CLI 错误）；
- C/D 组只影响调试效率，但多会话并行采集时每次都要重来一遍。

## 建议优先级

1. B1、B2（一行文档 + 一行报错提示就能省掉大量试错）
2. A1、A2（本地文件支持，直接决定"能不能按用户给的路径干活"）
3. A3、E1（错误回显 / 模板 schema）
4. C1、C2、D1、D2（发现性与可观测性）
5. B4（#622）、B3、E2
