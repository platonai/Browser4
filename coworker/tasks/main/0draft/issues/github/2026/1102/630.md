# Windows: detached backend/AOT JVM inherits the caller's stdout pipe (stray handle leak)

URL: https://github.com/platonai/Browser4/issues/630
State: OPEN
Author: galaxyeye
Created: 10/31/2026 16:31:56
Updated: 10/31/2026 16:31:56

## Summary

On Windows, the detached JVMs that `browser4-cli` starts (`launch_server` and `spawn_aot_training`) can inherit **stray handles** from the CLI's parent process, notably the parent's stdout pipe. Because the leaked handle outlives both the CLI process and `cmd.exe`, a parent that captures this CLI's output can block forever waiting for EOF.

This was observed during a live agent run on 2026-10-31; the immediate deadlock was already mitigated (see *Current mitigation*), but the underlying handle leak remains.

## Impact

- Any wrapper that captures `browser4-cli` output through a pipe can hang after the command itself has completed.
- The leaked write end stays open for the lifetime of the backend server, so the pipe never reaches EOF.
- One leaked handle per detached launch; low resource cost, but nonzero and surprising for embedding/capturing callers.

## Root cause

1. `std::process::Command::spawn` uses `CreateProcessW(..., bInheritHandles = TRUE)`, which hands **every inheritable handle** in the parent's handle table to the child.
2. `StdHandleInheritanceGuard` (used around `launch_server`) only clears the inherit bit on std handles (`GetStdHandle(0/1/2)`).
3. When the command's own stdout is redirected (`browser4-cli eval ... > out.json 2>&1`), the CLI's std handles point at the redirect file, **not** at the parent pipe. The pipe is then a *stray* inherited handle, is not cleared by the guard, and is passed on to the server/AOT JVM.
4. `spawn_aot_training` currently has no guard at all.

## Evidence (live run)

Command issued by the agent through `coding.shell`:

```
browser4-cli eval --file .b4scratch/fb_0.js --await --json > .b4scratch\fb_0.json 2>&1 & echo exit=%ERRORLEVEL%
```

- `.b4scratch/fb_0.json` was written completely (ending with the CLI's `"Session required"` error), i.e. the CLI and `cmd.exe` had exited.
- `java.exe` started by that same invocation (runtime `v4.15.2`, `Server ready in 31.5s`) kept listening on port `18182`.
- The capturing reader in `CodingAgentShell` never saw EOF and blocked indefinitely.

## Current mitigation

- `browser4-coding` `CodingAgentShell.runCommand` no longer waits unboundedly for stream EOF after the process exits: capture times out after a short grace period and reports that the stream stayed open.
- `spawn_aot_training` now drops the std-handle inherit bit like `launch_server` does.

These stop the deadlock, but do not eliminate the stale inherited handle.

## Proposed fix

Launch detached children with **`STARTUPINFOEX` + `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`** so only explicitly listed handles (stdin `NUL`, stdout/stderr log files) are inherited. This means calling `CreateProcessW` directly (or via a small helper) instead of `std::process::Command` for the detached server/AOT launches.

Alternative lower-cost option: clear the inherit bit on all handles the CLI owns before spawning. Not practical without enumerating inherited handles (`NtQuerySystemInformation` style APIs), hence the handle-list approach is preferred.

## Acceptance criteria

- A test wrapper that runs `browser4-cli ... > file 2>&1` through a pipe sees EOF immediately after `cmd.exe` exits, even when the command auto-starts a backend and AOT training.
- No long-lived child of `browser4-cli` holds the caller's stdout/stderr pipe.
- `launch_server` and `spawn_aot_training` consistently use the same handle-list mechanism.
