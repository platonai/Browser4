# Security: Chrome is launched with certificate verification disabled, with no supported way to re-enable it

URL: https://github.com/platonai/Browser4/issues/602
State: OPEN
Author: insodimension
Created: 09/22/2026 16:12:59
Updated: 09/22/2026 16:12:59

## Summary

Browser4 launches Chrome with certificate verification disabled, and there is no supported way to turn it back on. For a persistent, logged-in profile this means HTTPS provides no authentication of the server — an on-path attacker can intercept sessions the browser holds.

Reported by an integrator: we drive Browser4 over `--app mcp --transport stdio` for an agent browser plugin with persistent profiles. Our engine currently **fails closed** rather than open a login-bearing browser that cannot verify HTTPS.

Observed against the published bundle `v4.14.0-rc.6`, which ships `pulsar-browser-4.11.16.jar`.

## Two independent causes

1. **Command line.** `ChromeDefaults.IGNORE_CERTIFICATE_ERRORS = true`, surfaced through `ChromeOptions` as `@ChromeParameter("ignore-certificate-errors")`, so `--ignore-certificate-errors` is on the launch line by default.
2. **DevTools.** `NetworkManager.ignoreHTTPSErrors` is a hard-coded `var … = true` (with upstream's own `// TODO: is it a launch parameter?`), so `NetworkManager.enable` sends `Security.setIgnoreCertificateErrors(true)` for the session.

## Why it cannot be configured away

- `ChromeOptions.toList()` ignores raw `browser.launch.chrome.args` entries whose key the program already set, so passing `--ignore-certificate-errors=false` (or omitting it) has no effect.
- `BrowserSettings.createChromeOptions` never clears the flag, and `AbstractBrowserFactory` passes only `proxy` as a capability.
- `ChromeDefaults.ChromeLaunchConfig.load` exposes only `window.position`, `page.load.strategy` and `throwExceptionOnScriptError`.
- An integrator's own CDP session cannot revoke it: Chromium's `SecurityHandler::SetIgnoreCertificateErrors` keeps the override per DevTools session, and the command-line flag applies below DevTools entirely.

## Impact

Any Browser4-driven profile silently accepts invalid, expired, self-signed or attacker-supplied certificates. That is defensible for scraping throwaway pages; it is not defensible for a persistent profile that holds real logins, which is exactly what agent integrations need.

## Suggested remediation

- Make certificate handling configurable, defaulting to **verification on**: a config key that clears the `ignore-certificate-errors` parameter *and* sets `NetworkManager.ignoreHTTPSErrors = false`.
- Ideally scope any opt-out per session/profile rather than per process, so a scraping context can relax it without affecting a logged-in one.

Happy to verify a fix against our integration — our engine already detects the condition and will simply stop refusing once a bundle ships with verification available.
