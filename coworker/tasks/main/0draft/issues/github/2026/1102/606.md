# crawl: add checkpoint/resume — an interrupted crawl cannot be resumed, and restored tasks report a phantom running state

URL: https://github.com/platonai/Browser4/issues/606
State: OPEN
Author: platonai
Labels: enhancement, CLI, reliability
Created: 09/24/2026 03:32:42
Updated: 09/24/2026 03:32:42

## Summary

A crawl that is interrupted — backend restart, crash, or a task cancelled by the server-side `--timeout` budget — **cannot be resumed**. Only the task *record* survives; the work itself is lost, and reproducing the same crawl means re-submitting it and re-fetching every page.

This issue asks for real checkpoint/resume (断点续传): resume an interrupted crawl and continue from where it stopped, without re-fetching pages that already succeeded.

## Current behavior

1. `CrawlService.restoreFromDisk()` (`browser4-rest/src/main/kotlin/ai/platon/pulsar/rest/api/service/crawl/CrawlService.kt`) restores `CrawlResponse` records only:

   ```kotlin
   @EventListener(ApplicationReadyEvent::class)
   fun restoreFromDisk() {
       ...
       persistence.restore { entry ->
           ...
           taskStore.put(entry.taskId, entry)
       }
   }
   ```

   `jobStore` is not repopulated and no coroutine is launched. A task that was in a running state (`Created` / `Processing`) when the process died is restored **still reporting that running state, with no worker behind it** — so `crawl status <taskId>` keeps reporting a phantom running task forever.

2. What survives is aggregate *result* data (`pages`, `failedPages`, `pagesExpected`, `seedStatuses`, `linksDiscovered` in `CrawlResponse`). What does not survive is the per-URL *work* state. `CrawlLedger` already tracks exactly that in memory — `submittedUrls` (URL → depth), `succeededKeys`, `failedKeys`, `outstanding()` — but it is per-round, in-memory, and never persisted.

3. The resume state would be evicted anyway: `taskStore` is `maximumSize(100)` with Window TinyLFU eviction, and terminal tasks are purged after `taskTtlMinutes = 1440`. `purgeExpiredTasks()` and `clear` then call `rewritePersistence()`, which **drops** those entries from the append-only JSONL — so anything the bounded store no longer holds is gone for resume purposes too.

4. For comparison, `SwarmService` already takes the honest option on restart: non-terminal tasks are marked failed with a `restart` message (see `restoreFromDisk marks non-terminal tasks as failed` in `SwarmServicePersistenceTest`). crawl does not even do that today.

Related but different: `--expires <dur>` is a *time-window dedup* on the page store, not a checkpoint. It cannot reconstruct the frontier of a `--depth >= 1` crawl, and it refetches anything older than the window.

## Expected behavior

### 1. Status must tell the truth

- A restored task that was interrupted is reported as **interrupted** (e.g. a new `Interrupted` status), not as `Created`/`Processing`. `crawl status <taskId>` on such a task should say what it is and what it would take to finish it.
- `crawl list --status interrupted` lists them.
- Careful: the CLI poller currently treats only `OK` as a successful terminal state, so a new status must be classified as terminal-or-not deliberately — a status that is neither terminal nor pollable would make every `crawl status` wait hang.

### 2. Persist a resumable checkpoint, not just the result

Persist, per task:

- **The input contract** — seed URLs / the `--seed-file` contents (or its path + hash), `depth`, `--out-link-selector`, `--out-link-pattern`, `--top-links`, `--ignore-url-query`, `--no-norm`, `--sql` (or its hash), `--parallel`, `--expires`, `--priority`, `--readonly` — enough to reproduce the run without the user re-typing it.
- **The work state** — submitted URLs with their depth, succeeded URLs, terminally failed URLs with their reason, and the outstanding (submitted but unsettled) URLs. This is what `CrawlLedger` already knows.
- **The frontier** — links discovered at `depth < maxDepth` that were never submitted. `CrawlLedger.outstanding()` covers only *submitted* URLs, so a `depth >= 1` crawl cannot be continued correctly without this.

Checkpoint writes must be crash-safe and periodic (for example every N settled URLs or T seconds, plus on every status transition) — not only on status change as `onStatusChanged` does today — and flushed so a hard kill does not lose the last window.

### 3. Resume entry points

- CLI: `browser4-cli crawl resume <taskId>`; REST: `POST /crawl/{taskId}/resume`.
- Opt-in auto-resume on backend start (config flag / `crawl.autoResume`, **default off**), so restarting the backend never silently starts re-hitting third-party sites.
- Naming should be consistent with the existing `webminer all … --resume` precedent.

### 4. Resume semantics (the important part)

- **Already-succeeded URLs are not re-fetched.** They are counted and reported as `skippedAlreadyFetched`. A target-site request log after a resume should show no repeat request for a URL that had already succeeded.
- **Terminally failed URLs stay failed** and are not retried unless `--retry-failed` is passed, mirroring the existing `DEFAULT_MAX_DELIVERY_ATTEMPTS` reasoning (a third load of a twice-failed URL buys nothing but time).
- **Outstanding URLs are re-submitted** and get a fresh delivery-attempt budget.
- **The frontier is restored**, so a `--depth >= 1` crawl continues discovering links from where it stopped instead of restarting from the seeds.
- **The task id is kept** (the same task continues, with a resume counter), and the result is a merge of pre- and post-resume rows with provenance (per-row `fetchedAt` / attempt), so a consumer can tell which rows came from which run. `pagesExpected == pagesFound + failedPages.size` must still hold across the merge.
- **Concurrency is enforced**: resuming a task that already has an active job is rejected; resuming a terminal `OK` task is a no-op unless `--force`.
- **Resumable state is exempt from eviction**: an interrupted task's checkpoint must not be discarded by the 100-entry LRU or the 1-day TTL while it is still resumable (either persist it outside `taskStore`, or exempt interrupted tasks from `purgeExpiredTasks`). `crawl clear --all` stays the explicit way to throw it away.

### 5. Reporting

- `crawl status` / `crawl result` expose `resumedFrom`, `skippedAlreadyFetched`, `remaining`, and the number of resume attempts.
- With `--verbose`, per-URL rows are marked as fetched-in-this-run vs restored-from-checkpoint.

## Acceptance criteria

- SIGKILL the backend mid-crawl during a `--depth >= 1` crawl with `--parallel > 1`; restart; `crawl status <taskId>` reports the task as interrupted, not running.
- `crawl resume <taskId>` finishes the crawl; the target site's request log shows **no repeat request for any URL that had already succeeded**, and the previously discovered frontier is followed.
- `crawl result <taskId>` returns the union of pre- and post-resume rows with provenance, and the `pagesExpected == pagesFound + failedPages.size` invariant still holds.
- A task cut off by the server-side `--timeout` budget can be resumed and completes.
- Resume after a partially written checkpoint (truncated last line) neither crashes nor re-fetches succeeded URLs — consistent with the corrupt-line handling already covered for persistence.
- Docs state plainly whether automatic resume is on or off by default.

## Notes / non-goals

- No distributed / cross-node resume required; single-backend checkpoint + resume is enough for a first cut.
- Not about the page store's cache semantics (`--expires`), and not about WebMiner's own `--resume` (separate tool, already has it).
- Step 1 (status truthfulness) is worth landing on its own even if resume comes later: a restored task that reports `Processing` forever is a bug by itself.
