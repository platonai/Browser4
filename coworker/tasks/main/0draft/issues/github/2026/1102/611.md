# attach --cdp chrome fails on Chrome 153: the new "Allow remote debugging" mode exposes no page targets to /json

URL: https://github.com/platonai/Browser4/issues/611
State: OPEN
Author: wzwei1990
Created: 09/28/2026 05:27:05
Updated: 10/01/2026 15:32:21

## Summary

On Chrome 153 the CDP attach flow documented in `references/attach.md` — *"go to `chrome://inspect/#remote-debugging` and enable **Allow remote debugging for this browser instance**"* — does not yield an attachable endpoint: the endpoint that Browser4 resolves answers `GET /json/version`, but `GET /json` lists **no page targets**, so `attach` refuses. The extension route works fine, so this is specifically about the CDP path.

## Environment

- Windows 11, Chrome 153.0.8010.48 (single default profile)
- browser4-cli 4.13.23, installed runtime bundle v4.13.23

## Reproduction

1. `chrome://inspect/#remote-debugging` → enable "Allow remote debugging for this browser instance" (the page reports `Server running at: 127.0.0.1:9222`).
2. `browser4-cli attach --cdp chrome`
   ```
   ERROR: attach_browser failed: CDP endpoint http://localhost:51343 is reachable but has no page targets
   (browser=Chrome/153.0.8010.48 pages=0). Open a tab in the target browser, then retry attach.
   ```
   (`localhost:51343` is the port Browser4 resolved; several tabs are open in that browser.)
3. `browser4-cli attach --cdp http://localhost:9222`
   ```
   ERROR: attach_browser failed: CDP endpoint http://localhost:9222 is not reachable:
   GET /json/version → HTTP 404. Start the target browser with --remote-debugging-port and retry attach.
   ```

## Raw endpoint observations

- `127.0.0.1:9222` (the port Chrome itself reports): `/`, `/json`, `/json/list`, `/json/version`, `/mcp`, `/devtools/browser` → **all HTTP 404**.
- A second local CDP listener on a random port (`51343`) behaves like a normal CDP endpoint for `/json/version`:
  ```json
  {"Browser":"Chrome/153.0.8010.48","Protocol-Version":"1.3",
   "webSocketDebuggerUrl":"ws://localhost:51343/devtools/browser/<uuid>"}
  ```
  but `GET /json` returns `[]`, and `Target.getTargets` sent over that browser-level WebSocket also returns **0 targets**.
- `…\User Data\DevToolsActivePort` contains `9222` and `/devtools/browser/<uuid>` — i.e. the new mode is active, it simply does not expose page targets the way `attach` expects.

So on this Chrome version no reachable endpoint satisfies attach's requirement (`attach.md`: *"`GET /json` must list at least one `page` target"*), even with tabs open.

## Workaround that does work

`browser4-cli attach --extension` (unpacked extension built from `chrome-extension/`, loaded via *Load unpacked*) connects immediately:

```
Extension connected and healthy! (1s)
Connected browser: Google Chrome 153.0.0.0
```

and can drive tabs (`goto`, `page-info`, `htmlsnapshot`, `snapshot`, `screenshot` all succeed). Worth mentioning in the docs as the supported path on recent Chrome.

## Suggestions

- Resolve page targets through the **browser-level WebSocket** (`Target.setDiscoverTargets` + `Target.getTargets`) as a fallback when HTTP `/json` yields no `page` entries — or accept a browser-level `ws://` URL and derive page targets from it.
- When the endpoint is reachable but target discovery is empty, keep the current explicit error, and mention the Chrome-version behaviour + the extension fallback in the message and in `references/attach.md`.
- Consider documenting which Chrome versions keep legacy `/json` discovery.

## Related friction in the same workflow (low priority)

`attach --extension` hardcodes the Chrome-Web-Store extension id, so a locally built extension loaded with *Load unpacked* (different, path-derived id) requires the environment variable `BROWSER4_EXTENSION_ID=<id>`. `browser4-cli config set extension_id <id>` is rejected:

```
Error: Unknown config key 'extension_id'. Valid keys are: 'server', 'timeout', 'proxy', 'session'
```

Auto-detecting the installed extension id, or accepting `extension_id` as a config key, would remove that manual step.

### 中文摘要

Chrome 153 的"允许远程调试本浏览器实例"开关（`chrome://inspect/#remote-debugging`，页面显示服务在 `127.0.0.1:9222`）与 Browser4 的 CDP attach 不兼容：9222 上 `/json/version` 等路径全部 404；Browser4 实际解析到的另一个 CDP 端口虽然 `/json/version` 正常，但 `/json` 返回 `[]`、浏览器级 WS 的 `Target.getTargets` 也是 0 个目标，于是 attach 因"没有 page target"被拒（即使浏览器里开着多个标签页）。可行替代是扩展方式 `attach --extension`（本机约 1 秒连上并可正常导航/读取/截图）。建议：在 HTTP `/json` 拿不到页面目标时回退到浏览器级 WS 的 `Target.getTargets` 解析，或在文档中说明该版本行为并推荐扩展方式。附带一个小摩擦：`attach --extension` 硬编码商店扩展 ID，本地"加载已解压"必须用环境变量 `BROWSER4_EXTENSION_ID` 覆盖（`config set` 不接受该键），建议支持自动探测。
