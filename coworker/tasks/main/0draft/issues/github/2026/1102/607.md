## Summary

The long-standing "`DOM_*_IMG` ignores PowerCSS `:expr(...)`" limitation **no longer reproduces**. The engine half was fixed upstream — `platonai/Browser4base#5` ("DOM_FIRST_IMG with PowerCSS :expr() selector silently matches nothing") was **closed 2026-09-07** — and this repo now depends on `browser4-base 4.11.18` (bump `e5dbfb64a5`, 2026-09-22).

Verified on browser4-cli **4.13.21** / runtime `4.13.21-SNAPSHOT` (2026-09-24): `DOM_FIRST_IMG` / `DOM_NTH_IMG` / `DOM_ALL_IMGS` **do evaluate** `:expr()` filters.

But four in-repo artifacts still assert the opposite and now actively mislead:

1. the **CLI advisory** printed after every `DOM_*_IMG ... :expr(...)` query,
2. the **backend warning log** in `HTMLSnapshotToolExecutor`,
3. the **reference docs** (`x-sql.md`, `x-sql-dom-select-functions.md`, `power-dom.md`, `quick-patterns.md`, `SKILL.md`),
4. the **unit tests** on both sides that pin the stale assumption.

Reported by a user as "`:expr()` is not supported in UDFs — this is a bug". It is not; the bug is that we still tell users it is.

## Verification

Environment: browser4-cli 4.13.21, headless Chrome, 1920×1080; Amazon product page / eBay item page / Wikipedia.

Decisive test — an unsatisfiable predicate must return empty, a satisfiable one must return a match. **If `:expr` were ignored, both would return the first image in DOM order:**

```sql
SELECT
  DOM_FIRST_IMG(DOM, 'img:expr(width > 10000)') AS impossible,
  DOM_FIRST_IMG(DOM, 'img:expr(width > 400)')   AS wide,
  DOM_FIRST_IMG(DOM, 'img')                     AS plain,
  DOM_FIRST_IMG(DOM, 'img:expr(width >= 0)')    AS tautology
FROM DOM_LOAD_AND_SELECT(@url, ':root')
```

Amazon `dp/B0CXJ1NT4B?th=1`:

| column | result |
|---|---|
| `impossible` | **(empty)** |
| `wide` | `715XQGUVU9L._AC_SX679_.jpg` (507×507, the real main image) |
| `plain` | `nav-sprite-global-1x-reorg-privacy…png` (first `img` in DOM order) |
| `tautology` | `nav-sprite-global-1x-reorg-privacy…png` |

Wikipedia `Web_scraping` (page has no image ≥ 400 px wide):

| selector | result |
|---|---|
| `img:expr(width > 400)` | **(empty)** |
| `img:expr(width > 200)` | **(empty)** |
| `img:expr(width > 20)` | `enwiki-25.svg` |
| `img` | `enwiki-25.svg` |

Also verified:

- `DOM_ALL_IMGS(DOM, 'img:expr(width > 400)')` → 1 matching URL; `DOM_NTH_IMG(DOM, 'img:expr(width > 400)', 1)` → the same URL.
- Composite selectors `img.a-dynamic-image:expr(width > 400)` and `img[src*=media-amazon]:expr(width > 400)` → the same URL as the `DOM_FIRST_ATTR(DOM, 'img:expr(width > 400)', 'src')` control.
- eBay item page: `img:expr(width > 400)` → `…/s-l500.webp` (876×630) vs `img` → `…/s-l200.jpg`.

A filter whose outcome changes with the predicate is being evaluated, not ignored. The CLI nevertheless printed after **each** of these statements:

```
⚠️  DOM_FIRST_IMG does not evaluate PowerCSS :expr(...) filters — a filtered selector silently matches nothing (no error).
```

## Expected

- Drop the advisory, or gate it on an **observed empty result for a filtered selector** — selector syntax alone cannot know whether the engine honored it. (Also: the advisory is written to **stdout**, not stderr, so it corrupts `--format csv` output — see the in-repo draft below.)
- Docs must describe current behavior: `:expr(...)` works in `DOM_*_IMG` selector arguments. The `DOM_FIRST_ATTR(DOM, sel, 'src')` pattern can stay as a composability note, not as "the only way to filter images".
- Regression tests must pin **both** directions: a satisfiable `:expr` matches, an unsatisfiable one returns empty.
- `hasDomFirstImgExpr` in the backend and `sql_uses_dom_first_img_expr` in the CLI now have no true-positive case left; either delete them with the advisory, or repurpose them to the observed-empty gate.
