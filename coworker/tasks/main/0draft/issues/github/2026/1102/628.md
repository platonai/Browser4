## Background

In the Agent permission/capability model (phase A5), the workspace boundary still carries two historical exemptions that were carried over verbatim for behavioral equivalence:

- **B3** — launcher reference exemption (`isLauncherReference`): absolute paths outside the workspace whose basename is a known launcher (`mvnw`, `python3`, ...) or whose extension is a launcher extension (`.exe`/`.ps1`/...) are treated as in-scope, even though they live outside the workspace root. Expressed today as `Scope.launcherBasenames` / `Scope.executableExtensions` consumed by `CanonicalScope.isLauncher`.
- **B4** — toolchain roots exemption (`toolchainRoots`): `java.home`, `~/.m2`, `~/.gradle`, `~/.cache`, the system temp dir, and the system root are granted read+write through the boundary `Authorizer`, so a build can write to its toolchain directories.

These exemptions are currently encoded as capability scope entries in `CodingComponents.boundaryAuthorizer` (the `cap-shell-boundary` lexical-scope grant). They were preserved in A4/A5 specifically so M0 (behavioral equivalence) would hold, with the understanding that they would be removed once a verified, explicit root list existed.

## Goal

Replace B3 and B4 with **explicit, enumerated roots** from the P0 scope manifest (`ScopeManifest`), and remove the launcher-exemption logic and the blanket toolchain-roots grant. After this change:

- A path/command is allowed **only** if it is covered by an explicit scope entry in the manifest — no implicit launcher basename/extension match, no whole-toolchain-tree grant.
- The manifest is the single source of truth for what is reachable; removing an entry removes the reach.
- The boundary `Authorizer` scope no longer needs `launcherBasenames` / `executableExtensions` fields (they can be deleted from `Scope` and `CanonicalScope`), and `toolchainRoots` stops feeding the boundary scope.

## Blocker (G0 gate)

This issue is **blocked on P0-1** (scope-manifest observation):

- At least **one week of production-style observation** with the current boundary (B3/B4 still in place) must complete, collecting which roots are actually exercised by real workloads.
- The observed roots must be written into `ScopeManifest` as explicit `WORKSPACE` / `MIRROR` / `TOOLCHAIN` entries and verified against the golden-decision baseline (`PermissionDecisionBaselineTest`).
- Until the manifest covers every root B3/B4 currently reach, deleting the exemptions would regress legitimate workloads.

Do not start implementation until P0-1 is signed off.

## Acceptance criteria

- [ ] `Scope.launcherBasenames` and `Scope.executableExtensions` removed; `CanonicalScope.isLauncher` and its callers removed.
- [ ] `CodingComponents.boundaryAuthorizer` no longer injects `toolchainRoots` into the shell scope; the `cap-shell-boundary` grant covers only workspace + mirror roots plus any explicit `TOOLCHAIN` entries from `ScopeManifest`.
- [ ] Every root B3/B4 previously reached is now represented by an explicit `ScopeManifest` entry; no legitimate workload path/command is newly denied.
- [ ] `PermissionDecisionBaselineTest` (A7 golden baseline) still passes after the exemptions are removed — proving behavioral equivalence is preserved through the manifest, not through ad-hoc exemptions.
- [ ] Tests that asserted the launcher/toolchain exemption behavior are rewritten to assert the equivalent explicit-root behavior.
- [ ] `Authorizer` remains the single decision point; no path/command judgment leaks back into `CodingAgentShell` or `CodingAgentFileSystem`.

## Notes

- The OS sandbox (`browser4.agent.sandbox`) remains the enforced layer underneath; the string/boundary check is advisory fast-fail, so any gap is still caught by the sandbox — but the boundary must still be correct so the model gets accurate refusals.
- Windows sandbox ACL roots (P1-3) are derived from the same workspace/writable/readonly/deny lists; ensure the manifest-driven roots stay consistent with the sandbox provisioning after B3/B4 removal.
- See `docs-dev/copilot/agent-permission-capability-model-dev-plan-v2.md` §P4-2 and the A4/A5 implementation records for the current exemption encoding.
