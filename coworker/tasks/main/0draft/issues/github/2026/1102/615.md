# attach --cdp <channel> cannot find a browser started with --remote-debugging-port=0 on Linux/macOS (listening-port tier is Windows-only)

State: OPEN

Created: 10/02/2026 02:00:50

## Summary

`attach --cdp <channel>` resolves a browser's debug endpoint through four candidate stages, and one of them — *the ports the browser process is listening on* — exists only on Windows. On Linux/macOS the same command therefore fails for a browser launched with `--remote-debugging-port=0` (Chrome picks a random port; this is what Browser4-managed browsers do) whenever the first stage cannot locate its `DevToolsActivePort`, even though the port is trivially discoverable from the OS.

## Current behaviour

- `cli/browser4-cli/src/daemon.rs:4075` — `process_listener_candidates()` implements the tier with `Get-NetTCPConnection -State Listen | Where-Object { $_.OwningProcess -eq <pid> }`, keyed to the PID from `resolve_executable_pid()` (`daemon.rs:4334`).
- `cli/browser4-cli/src/daemon.rs:4100` — the non-Windows build gets a stub returning `Vec::new()`, and `resolve_executable_pid()` (`daemon.rs:4355`) returns `None`.
- Candidate order in `resolve_channel_to_endpoint()`: (1) `<user-data-dir>/DevToolsActivePort` plus `--remote-debugging-port=N`; (2) the process's other listening ports *(Windows only)*; (3) the channel's default port; (4) a 9222–9333 scan.
- The gap is documented, and the CLI admits it at runtime: `skills/browser4-cli/references/attach.md:66`, `references/browser-modes.md:295`, and `platform_discovery_note()` (`daemon.rs:4317`), which prints "…enumerating a browser's listening ports (that tier is Windows-only)…" off Windows.

## Why it still matters after the `DevToolsActivePort` work (#611)

Stage 1 reads `--user-data-dir` from the running process command line, so Browser4-managed browsers, portable builds and custom profiles are resolved on every platform. What is left uncovered:

1. a browser started with `--remote-debugging-port=0` whose `DevToolsActivePort` is not where the CLI looks — the default profile in an unusual install root (snap/flatpak/chromium builds, custom `XDG_CONFIG_HOME`, …);
2. an endpoint whose `DevToolsActivePort` was removed or is unreadable while the socket is alive;
3. third-party CDP shells that neither expose a parseable flag nor publish `DevToolsActivePort`.

In all three, Windows finds the port while Linux/macOS fail with "Could not find a running chrome browser with remote debugging enabled." — a platform-dependent capability, which is the only reason the caveat exists in the docs.

## Proposal

Implement the tier for Linux and macOS, keeping the existing contract (`Vec<CdpCandidate>`; every candidate is still probed for page targets, so extra ports are harmless):

- **Linux** — locate the browser PID (`ps -e -o pid=,args=`, excluding `--type=` children), collect its socket inodes from `/proc/<pid>/fd/*` (`socket:[N]`), then map those to LISTEN entries in `/proc/net/tcp{,6}` (`st == 0A`). Fallback when `/proc` is unreadable/namespaced: parse `ss -ltnp`; its `-p` needs privileges for other users' processes, so an empty parse must mean "no candidates", not an error.
- **macOS** — `lsof -nP -a -p <pid> -iTCP -sTCP:LISTEN`, parsing the `NAME` column (`*:9222`, `127.0.0.1:9222`, `[::1]:9222`); `lsof` missing or not permitted degrades to today's behaviour.
- **`resolve_executable_pid()` needs a POSIX counterpart** — it is Windows-only today (`daemon.rs:4334` / `:4355`).

Implementation notes that matter here (learned on the Windows tier):

- keep the **parsers pure** — `parse_proc_net_tcp_listen`, `parse_socket_inodes`, `parse_ss_listen_ports`, `parse_lsof_listen_ports` — with unit tests, so a tier can be tested without a browser; today's Windows tier is I/O-only;
- never trust a single sample: every candidate must still be **probed** before selection (page count over `/json`, else the browser-level WebSocket);
- do not widen the candidate set to unrelated processes: filter by the browser executable *and* exclude renderer/GPU/utility children (`--type=`), which is also what keeps `msedgewebview2.exe` out on Windows.

## Acceptance criteria

- [ ] On Linux and macOS, `attach --cdp chrome` resolves a browser launched with `--remote-debugging-port=0 --user-data-dir=<custom>` **after** its `DevToolsActivePort` is removed/renamed — i.e. through the port sweep, not stage 1.
- [ ] Unit tests per parser, including malformed/empty input and IPv6 forms.
- [ ] An e2e scenario covering the Linux and macOS legs, tagged so it runs only where a browser is available.
- [ ] `attach.md:66`, `browser-modes.md:295` and `platform_discovery_note()` lose the "Windows-only" caveat (or keep a short note about snap/flatpak roots).
- [ ] No behaviour change on Windows.

## Notes

- Not a blocker for #611: the browser-level WebSocket path and `DevToolsActivePort` resolution already work on every platform. This is a parity gap, not a regression.
- Background and the Windows pitfalls are written up in `docs-dev/copilot/cdp-attach-websocket-4.13.x.md` (§3 candidate stages, §9 open items).
- Rough effort: 150–250 lines of Rust plus tests; the riskiest parts are `/proc` namespaces (containers) and `lsof` permissions, both of which degrade to "no candidates".
