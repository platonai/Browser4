# [4.13.x] uninstall never detects the npm install on Windows — fix exists on main/4.14, needs backport

URL: https://github.com/platonai/Browser4/issues/595
State: OPEN
Author: platonai
Labels: bug, CLI, medium
Created: 09/16/2026 16:13:46
Updated: 09/16/2026 16:13:46

## Summary

On Windows, `browser4-cli uninstall` can never see the npm-installed package. The uninstall path spawns the bare command `npm`, which `CreateProcess` cannot resolve (npm ships as `npm.cmd`, and PATHEXT is not consulted). The spawn fails, the error is swallowed as "not installed", and the global npm package plus its shims are left on disk while `uninstall` reports success.

A fix already exists on `main` / `release/4.14.0-rc.3` — it just never reached `4.13.x`, so the released **4.13.19** (what npm `latest` hands out today) still has the bug.

## Environment

- `browser4-cli` **4.13.19**, installed with `npm install -g browser4-cli`
- Windows, PowerShell; Node v24.19.0, npm 11.17.0
- npm global prefix: `%APPDATA%\npm`

## Steps to reproduce

```powershell
npm install -g browser4-cli      # 4.13.19
browser4-cli uninstall --dry-run
```

Output:

```
🧹 Uninstalling browser4-cli ...

🔍 DRY RUN — no changes will be made.

ℹ  npm not found or browser4-cli not installed via npm.
ℹ  cargo not found or browser4-cli not installed via cargo.
🔍 Would remove runtime data directory: %APPDATA%\browser4
🔍 Would remove runtime cache directory: %LOCALAPPDATA%\browser4

ℹ  browser4-cli was not found in npm or cargo global installs.
   Running binary: %USERPROFILE%\.local\bin\browser4-cli.exe
   🔍 Would attempt to remove the binary.
```

`npm` is on PATH (`npm -v` → `11.17.0`) and the package is definitely installed:

```
> npm ls -g --depth=0
+-- browser4-cli@4.13.19
```

`browser4-cli uninstall -y` behaves the same in non-dry-run mode: the runtime dir and cache are removed, npm is skipped.

## Root cause

`cli/browser4-cli/src/main.rs`, `async fn handle_uninstall` (branch `4.13.x`, ~L17094):

```rust
} else {
    let mut cmd = Command::new("npm");            // ~L17183 — bare "npm"
    cmd.args(["uninstall", "-g", "browser4-cli"])
        ...
    match run_with_timeout(cmd, 60) {
        Ok(output) => { ... }
        Err(_) => {
            // npm not on PATH or spawn failed — treat as not installed
            (false, None)                          // ~L17202-17204
        }
    }
}
```

On Windows `Command::new("npm")` always fails because npm is `npm.cmd`. The correct helper already exists in the same file:

```rust
/// On Windows npm ships as `npm.cmd` (a batch shim) — plain `npm` is not
/// resolvable because CreateProcess does not consult PATHEXT.
fn npm_command_names() -> &'static [&'static str] { /* &["npm.cmd", "npm"] */ }  // ~L17441
fn resolve_npm() -> Option<&'static str> { ... }                                 // ~L17453
```

…but it was only wired into install/upgrade (`a6e7cb9b51820c8208f213dc0c40d977c8fbf4dc`), never into uninstall.

## Fix already exists — needs a backport to `4.13.x`

- `78587ce96537e70cb8109d0ed36ac2179236d637` — *fix(cli): uninstall resolves npm via npm.cmd on Windows* (2026-08-27, +42/−25 in `main.rs`). Its own comment describes this exact failure mode:

  > On Windows npm ships as `npm.cmd` (a batch shim) — a bare `npm` is not resolvable by CreateProcess (it does not consult PATHEXT), so resolve the real command name first. Otherwise npm is reported as "not installed" and a globally installed package is silently left behind while the CLI claims uninstall succeeded.

- Present on: `main`, `release/4.14.0-rc.3`, `feat/frame-switch`
- **Absent from: `4.13.x` and tag `v4.13.19`** (verified with `git merge-base --is-ancestor` against a clone whose `4.13.x` HEAD equals `origin/4.13.x`)

Could this be cherry-picked onto `4.13.x` so the next 4.13.x patch actually uninstalls?

## Impact

A user following the documented uninstall flow ends up with a half-removed installation:

- `%APPDATA%\npm\node_modules\browser4-cli` and the `browser4-cli` / `b4` shims stay in place
- the CLI therefore still resolves on PATH, so it looks like nothing happened
- two uninstall runs produce the same "success"

Workaround for anyone on 4.13.x: run `npm uninstall -g browser4-cli` manually after `browser4-cli uninstall`.

## Scope

The `next` line (e.g. `4.14.0-rc.5`) already contains the fix — this only affects the 4.13.x stable line.
