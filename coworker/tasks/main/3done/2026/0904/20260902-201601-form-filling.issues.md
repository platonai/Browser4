## Issues Found (5 issues)

### Issue 1: select --verify reports successful label-based selections as failures (and never affects the exit code)

**Severity:** Medium
**Category:** Product

#### Reproduction

On a page with <select> options whose value differs from the visible label (e.g. the form-filling fixture: value 'sg', label 'Singapore'):
1. browser4-cli select e1918 "Singapore" --verify
   → prints "✓ Selected 'Singapore' in e1918" then "Verification: expected 'Singapore' to be selected, but current value is 'sg'." (exit code 0).
2. browser4-cli select e1918 "sg" --verify
   → prints "Verification: option 'sg' is selected." (same selection, both exit 0).

#### Expected Behavior

When the option was successfully selected by its visible label, --verify should confirm success (resolve label → option value, case-insensitively) instead of printing a failure message. A genuine verification failure should produce a non-zero exit code so scripts can rely on it.

#### Actual Behavior

select accepts both the option label and the option value as <val> and selects correctly in both cases, but --verify compares the raw argument string (exact, case-sensitive) against element.value, so any label-based or case-differing selection prints a misleading 'expected … but current value is …' failure line. All verification branches return Ok, so exit code is 0 whether verification passed or failed.

#### Root Cause Analysis

verify_select_result in cli/browser4-cli/src/main.rs:8828 reads element.value via browser_evaluate and compares it with expected_value using exact equality (main.rs:8852). The select tool itself matches option text OR value server-side, so the verify step's value-only, case-sensitive comparison disagrees with the select semantics. Verification outcome is printed via Ok(...) in every branch (main.rs:8852-8864), never Err, so exit code cannot signal failure.

#### Code Pointer

`cli/browser4-cli/src/main.rs:verify_select_result (line 8828)`

#### AI Suggested Improvement

- Make --verify resolve the expected label to its option value before comparing (e.g. evaluate the option list and match label case-insensitively, or compare against both option.text and option.value).
- Normalize case on comparison so 'Advanced' vs 'advanced' does not fail.
- Return Err (non-zero exit) when verification genuinely fails; treat label/value/case matches as success.
- Keep the success/failure wording consistent with the select argument actually accepted ('option "Singapore" (value sg) is selected').

### Issue 3: Non-browser commands missing from the no-snapshot allowlist trigger a full page snapshot (config list prints '### Page' and writes a YAML snapshot file)

**Severity:** Low
**Category:** Product

#### Reproduction

With an active browser session: browser4-cli config list → prints the four config values, then also '### Page / Page URL / Page Title / ### Snapshot / [Snapshot](...\.browser4-cli\snapshot\snapshot-....yml)' and a tip line, and writes a new snapshot file to disk. Verified twice (two snapshot files created purely by config list invocations).

#### Expected Behavior

config list is a local read-only CLI command; it should print configuration only and should not capture a browser accessibility snapshot, add ~1-3s latency, or write files.

#### Actual Behavior

Any command not in the no_snapshot_commands() allowlist triggers post_command_snapshot() whenever a session is active (main.rs:18438). 'config' is absent from the allowlist, so config list behaves like an interaction command. Output clutter plus snapshot-disk accumulation on every invocation (100+ YAML files now present in .browser4-cli/snapshot, mostly from interactions in previous sessions).

#### Root Cause Analysis

main.rs:18433-18443 implements an opt-out allowlist (no_snapshot_commands(), main.rs:362) that enumerates commands that skip the auto-snapshot. Non-browser/management commands such as 'config' were never added to the list; the allowlist design means any new command silently inherits browser-snapshot behavior. The comment at main.rs:18431 ('commands that modify browser state') does not match the implementation.

#### Code Pointer

`cli/browser4-cli/src/main.rs:no_snapshot_commands() (line 362) and post-command snapshot call site (line 18438); post_command_snapshot at line 1041`

#### AI Suggested Improvement

- Add 'config' (and audit 'plugin', 'skills', 'experience', 'webminer', 'swarm', 'crawl' subcommand families) to no_snapshot_commands().
- Invert the design: only run the post-command snapshot for a small explicit set of interaction commands (fill/click/type/press/select/check/…) rather than for everything except an allowlist.
- Add a regression unit test asserting config-style commands do not trigger post-command snapshots.

### Issue 5: snapshot -v 0 captures a mid-page chunk after interactions that auto-scroll; no actionable hint that the page top is above the current viewport

**Severity:** Low
**Category:** Documentation

#### Reproduction

After filling the form and clicking the submit button (which sits at y≈1573, below the 1080px viewport, so the driver scrolls it into view), run: browser4-cli snapshot -v 0 --stdout. The output header shows '# hiddenTopHeight: 1057px' but the tree starts mid-page: the top-of-page confirmation text ('Submission Result / Your form data was captured successfully.', at y≈434-747) is excluded from the capture because it lies above the visible band.

#### Expected Behavior

The captured 'result page' chunk should be recognizable as not starting at the page top, and the help/docs should tell the user how to reach the top chunk (-v -1, or scroll up first) when they intend to document the page from the top.

#### Actual Behavior

The doc table says '-v 0 = current visible screen' and the header comment lists hiddenTopHeight, so the behavior technically matches the docs — but a first-time user reading '-v 0' as 'top of the result page' silently produces an artifact missing the confirmation heading. SKILL.md only clarifies the scroll-relative semantics for fresh navigations ('After a fresh navigation -v 0 is the top of the page'); this page did not navigate on submit.

#### Root Cause Analysis

Click interactions that target below-the-fold elements scroll the page; viewport indices are scroll-relative, so -v 0 no longer equals the page top after such a click. The snapshot footer comment (viewports/scroll hints) does not warn when hiddenTopHeight is large.

#### Code Pointer

`cli/browser4-cli/src/main.rs (snapshot output footer generation / viewport hint); skills/browser4-cli/SKILL.md §5 snapshot-modes table`

#### AI Suggested Improvement

- When hiddenTopHeight > 0, print an actionable hint with the snapshot (e.g. '# Note: page is scrolled 1057px down; use snapshot -v -1 or scroll up to capture the page top').
- Extend the SKILL.md snapshot-modes row: '-v 0 = current visible screen; after clicks that auto-scroll elements into view this may be mid-page — use -v -1/-v 0 after scrolling to top for the page start'.
- Consider a 'snapshot --top' convenience flag that scrolls to top (or maps to viewport 0 of a fresh scroll) before capturing.
