### Issue 1: htmlsnapshot capture fails in reused/pre-existing sessions with cryptic error and no recovery path

**Severity:** High
**Category:** Reliability

#### Reproduction

1. Have a browser4 session created by an earlier process (e.g. a prior run's DEFAULT session, visible via `list`). 2. `./b4w.ps1 goto http://localhost:18080/generated/form-filling.html` (reconnects). 3. `./b4w.ps1 htmlsnapshot` -> ERROR: html_snapshot_capture failed: ReferenceError: __pulsar_utils__ is not defined at <anonymous>:1:1 ... help: Capture the current page as an HTML snapshot with metadata, interactive elements, and link groups. 4. `./b4w.ps1 reload` then `htmlsnapshot` again -> same failure. 5. `./b4w.ps1 -s fresh open --headless <url>` + `./b4w.ps1 -s fresh htmlsnapshot` -> works.

#### Expected Behavior

htmlsnapshot capture should succeed in any session, or fail with an actionable message telling the user how to recover (e.g. re-inject the helper script or open a fresh session).

#### Actual Behavior

Capture fails deterministically in the reused session (twice, including after reload). Error text is a raw JS exception concatenated with the tool's static description ('... help: Capture the current page as an HTML snapshot ...') and its function signature — no recovery guidance. Only a brand-new session avoids the failure.

#### Root Cause Analysis

The capture tool evaluates page JS that depends on a `__pulsar_utils__` helper injected at browser-context creation (browser4-core/browser4-protocol/.../InteractiveBrowserEmulator.kt:666, 'For some type of pages, the script can not be injected'). Reused sessions whose browser context was created under different conditions never got the injection, and reload does not re-inject it. The error formatting appends the tool's static description as 'help' text (browser4-rest/.../mcp/controller/MCPToolController.kt:1210), which reads like a debug dump.

#### Code Pointer

`browser4-core/browser4-protocol/src/main/kotlin/ai/platon/pulsar/protocol/browser/emulator/impl/InteractiveBrowserEmulator.kt:666 (injection check) and browser4-rest/src/main/kotlin/ai/platon/pulsar/rest/mcp/controller/MCPToolController.kt:1210 (error formatting)`

#### AI Suggested Improvement

- Detect the missing `__pulsar_utils__` at capture time and re-inject the helper script into the current page instead of failing
- When re-injection is impossible, return an actionable error: 'The helper script is not present in this browser session. Run `close` and re-open the session (or `open --fresh`) and retry.'
- Stop appending the tool's static description/signature to runtime errors; reserve `help` text for usage errors

### Issue 2: `get` command selector support is inconsistent across modes and contradicts its own help and SKILL.md

**Severity:** High
**Category:** Product

#### Reproduction

Fresh session on the form page. `./b4w.ps1 get text ".primary-button"` -> 'Submit form' (works). `./b4w.ps1 get text ".result-data"` -> 'No elements matched'. `./b4w.ps1 get text "#result-data"` -> works. `./b4w.ps1 get attr "#result-data" class` -> 'No elements matched "#result-data"'. `./b4w.ps1 get attr "#email" class` -> 'No elements matched'. `./b4w.ps1 get property "#email" value` -> 'No elements matched'. `./b4w.ps1 get text e1972` (ref) -> works.

#### Expected Behavior

A documented, predictable selector contract: either CSS selectors work for all modes (as the help examples imply), or the AXTree limitation is stated up front and enforced consistently.

#### Actual Behavior

Support varies by mode and by element type: refs work for text; `.primary-button` works for text but `.result-data` does not; `#id` works for text but not for attr/property; attr/property failed for every tested selector form. `get --help` describes `<selector>` as 'CSS selector or element reference (e.g. e5, .price, #main)' with CSS examples, then appends a warning that the command operates on the AXTree, not CSS. SKILL.md line ~578 shows `get text "#contactForm > button.primary"` as a CSS example.

#### Root Cause Analysis

CLI (cli/browser4-cli/src/commands.rs:1254 CommandDef) maps each mode to a different backend tool: text -> select_first_text_or_null, attr -> select_first_attribute_or_null, property -> select_first_property_value_or_null, html/styles -> browser_evaluate, box -> bounding_box. Resolution lives in the compiled pulsar-browser dependency: refs resolve via CDP DOM.resolveNode (stable), CSS via DOM.querySelector, but ref-based JS/attr reads convert the ref to a generated CSS selector from the a11y-derived DOM snapshot; for generic divs without id/class the generated selector degrades to bare `div`, so querySelector hits the first div on the page and the attr read returns null -> CLI prints 'No elements matched'. Different modes thus have different selector support and error behavior; the exact `.result-data` vs `.primary-button` divergence (both valid live-DOM class selectors) needs follow-up inside the dependency jar.

#### Code Pointer

`cli/browser4-cli/src/commands.rs:1254 (mode->tool mapping); browser4-agentic/src/main/kotlin/ai/platon/pulsar/agentic/tools/builtin/BrowserTabToolExecutor.kt:1282/1294/1374 (dispatch); resolution itself in pulsar-browser-4.11.2.jar (DOMHandler.doResolveLocator / findCssSelectorFromLocator)`

#### AI Suggested Improvement

- Make selector semantics uniform: if the AXTree is the data model, reject or translate CSS selectors consistently across modes and say so in help
- Prefer resolving refs via backend node ID for ALL modes (text, attr, property, box), avoiding the lossy ref->CSS conversion for generic elements
- Align the help text, SKILL.md examples, and the runtime error hint so all three describe one behavior

### Issue 3: "No elements matched" message conflates selector-miss with null attribute value

**Category:** UX

#### Reproduction

Fresh session: `./b4w.ps1 get attr "#email" class` -> 'null / No elements matched "#email".' The element #email exists and was matched; only the attribute read came back null.

#### Expected Behavior

When the element matched but the attribute/property is absent or null, the output should say so (e.g. 'attribute not found' or 'value is null'), not claim the element was not found.

#### Actual Behavior

The CLI treats any null/empty tool result as a selector-miss (main.rs:5317 empty_result check) and prints the same 'No elements matched' message plus a hint to use htmlsnapshot instead, misleading the user into fixing the wrong thing (the selector) when the selector was fine.

cli/browser4-cli/src/main.rs:5313-5336 (handle_get): 'null' results are indistinguishable from selector-miss because the backend tool returns null both when resolution fails and when the resolved element's attribute/property value is null.

- Differentiate the two outcomes (backend should return a distinguishable result for 'element found, attribute null')

### Issue 4: select --verify reports a false-negative when the user passes the visible option text

**Category:** UX

#### Expected Behavior

Selecting by visible text should verify successfully, or the verification message should report both the selected value and its label ('de (Germany)') without sounding like a failure.

#### Actual Behavior

The confirmation says success, then the verification line says the selection does not match — two contradictory statements in one output. Users selecting by visible label (the natural way) are told their selection failed when it did not.

#### Code Pointer

`cli/browser4-cli/src/main.rs:8669 verify_select_result and :8604-8606 handle_select_command`

- Compare against the selected option's text when the requested value does not equal element.value, e.g. `element.selectedOptions[0].textContent`
- On mismatch, report both actual value and label instead of a bare failure sentence
- Suppress or format the raw backend result array (`["de"]`) that leaks before the confirmation line
