### Issue 1: eval --file and eval --stdin are broken — always produce browser_evaluate error

**Severity:** Critical
**Category:** Product

#### Reproduction

echo 'document.title' > test.js
./b4w.sh eval --file test.js
Result: Error: ERROR: browser_evaluate failed: Unexpected error in [evaluateValueDetail]

Same with --stdin: echo 'document.title' | ./b4w.sh eval --stdin

#### Expected Behavior

The JavaScript from the file or stdin should be evaluated in the browser context and return the result, same as inline eval.

#### Actual Behavior

Both --file and --stdin always fail with 'browser_evaluate failed: Unexpected error in [evaluateValueDetail]' regardless of script content, even for trivial expressions that work fine inline.

#### Root Cause Analysis

The --file and --stdin code paths likely differ from the inline eval path in how they call the backend's evaluate function. The error message references 'evaluateValueDetail' which suggests the code is wrapping the expression differently or passing an incorrect selector parameter. The SKILL.md explicitly recommends --file and --stdin for Windows users to avoid shell quoting issues — having these broken makes eval effectively unusable for complex scripts on all platforms.

#### Code Pointer

`Likely in the CLI's eval command handler (cli/browser4-cli/src/) or the backend's MCPToolController.kt — the evaluateValueDetail function appears to receive a null/malformed selector when the --file/--stdin path is used.`

#### AI Suggested Improvement

- Fix the --file and --stdin eval paths to correctly pass the JavaScript expression to the browser without requiring a selector parameter
- Add a test that verifies eval --file and --stdin work for simple expressions
- Consider unifying the code path so inline, --file, and --stdin all use the same evaluate function

### Issue 2: PowerShell wrapper (b4w.ps1) intercepts short flags like -v and -i

**Severity:** High
**Category:** Reliability

#### Reproduction

./b4w.ps1 snapshot -v 0 --stdout
Result: Unknown command: 'snapshot-0'. Did you mean: 'snapshot'?

#### Expected Behavior

The -v 0 flag should be passed through to the browser4-cli binary as a snapshot argument.

#### Actual Behavior

PowerShell's parameter binder interprets -v as -Verbose and mangles the argument list, producing 'snapshot-0' as the command name.

#### Root Cause Analysis

b4w.ps1 uses PowerShell's ValueFromRemainingArguments which still subjects dash-prefixed arguments to PowerShell parameter binding. Short flags like -v match PowerShell common parameters (-Verbose), -i matches (-InformationAction). The SKILL.md documents this but requires the user to discover and read a separate shell-quoting.md reference.

#### Code Pointer

`b4w.ps1: PowerShell parameter binding in the param() block. The RemainingArgs parameter needs explicit handling to pass through unrecognized flags.`

#### AI Suggested Improvement

- Add explicit parameter definitions for common CLI flags in b4w.ps1 to prevent them from being captured by PowerShell's common parameters
- Or use --% (stop-parsing symbol) before CLI arguments to prevent PowerShell interpretation
- Document this more prominently in the help output, not just in SKILL.md references

**Category:** Discoverability

- Exclude known navigation patterns (nav, header, footer elements)
- Sample from the middle of the page where product content typically lives
- Fix htmlsnapshot summary timeout so users have a working fallback
