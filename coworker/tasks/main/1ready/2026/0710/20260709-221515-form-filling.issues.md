**Key decisions:**
- Used `-v all --stdout` instead of `-i` because interactive mode only showed a 10-line preview
- Re-snapshot after clicking radio button (Phone) since the SKILL.md warns DOM mutations are a "gray area" for radio buttons
- Used `htmlsnapshot get text` with CSS selectors instead of `get attr` since `get` doesn't accept element refs

**Workarounds:**
- Had to discover that `htmlsnapshot` must be captured before `htmlsnapshot get` works (two-step process)
- Had to figure out that `get attr` works with CSS selectors on the live page, not with snapshot refs
- The `#first-name` CSS selector didn't match via `htmlsnapshot get attr` but the htmlsnapshot summary listed it — had to fall back to reading the state-log JSON

## How to Reproduce

### Common Setup

1. Clone the repository and `cd` to the repo root.
2. Build the CLI: `cd cli/browser4-cli && cargo build`
3. The backend server starts automatically in dev mode.
4. All commands from repo root: `cd cli/browser4-cli && cargo run -- <command>`

### Per-Issue Reproduction Steps

#### Issue 1: Interactive snapshot (`-i`) preview too short to be useful for form discovery

Run `snapshot -i` on the form-filling page.

#### Issue 2: `get attr` command silently fails with snapshot refs, misleading error message

```
browser4-cli get attr e101 value
```
After using refs for `fill`, `click`, `check` etc.

#### Issue 3: `htmlsnapshot get attr` selector mismatch — CSS selectors from `htmlsnapshot` summary don't always work

```
browser4-cli htmlsnapshot                              # shows #identitySection input#first-name
browser4-cli htmlsnapshot get attr "#first-name" value # fails: No elements matched
```

#### Issue 4: Inconsistent viewport count between snapshots

Take `snapshot -i` before filling the form (reports 3 viewports), then take `snapshot -v 0` after all form interactions (reports 4 viewports).
