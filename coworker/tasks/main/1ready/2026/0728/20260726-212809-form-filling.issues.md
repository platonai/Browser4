### Issue 1: `b4w.ps1` fails with short flags on Linux/pwsh — `snapshot -i` intercepted by PowerShell

**Severity:** High
**Category:** Reliability

#### Reproduction

```bash
./b4w.ps1 snapshot -i
```

#### Expected Behavior

Interactive snapshot captures, showing element refs for the form.

#### Actual Behavior

```
b4w.ps1: Parameter cannot be processed because the parameter name 'i' is ambiguous.
Possible matches include: -InformationAction -InformationVariable.
```

#### Root Cause Analysis

`b4w.ps1` has a `param()` block with `[Parameter(ValueFromRemainingArguments = $true)][string[]]$RemainingArgs`. PowerShell's parameter binder processes `-i` before `$RemainingArgs` captures it, matching it against common parameters `-InformationAction` / `-InformationVariable`. The script attempts to handle this with `--` passthrough (line 48), but `--` is also processed by `param()` — `$RemainingArgs` receives `['--', 'snapshot', '-i']` and the `if ($RemainingArgs[0] -eq '--')` branch on line 48 strips it. However, `--` itself was initially parsed by PowerShell as an argument to the script's own `param()` block, causing "Parameter cannot be processed because the parameter name '' is ambiguous."

#### Code Pointer

``b4w.ps1:3-7` — the `param()` block. The `--` handling on lines 48-50 only works when `--` is the first argument after the script path, but `--` itself must survive PowerShell's parameter binder to reach `$RemainingArgs`, which is the root of the problem.`

#### AI Suggested Improvement

- Add `[CmdletBinding()]` attribute and use `--%` (stop-parsing token) before CLI arguments; document that `./b4w.ps1 --% snapshot -i` is the canonical invocation for short flags
- Alternatively, add explicit `-SnapshotArgs` parameter that accepts a single quoted string: `./b4w.ps1 -SnapshotArgs "snapshot -i"`
- Update `b4w.ps1` top help (lines 92-125) to explicitly warn about short-flag interception and give the exact workaround
- Consider renaming the script's own `-Rebuild` to `--rebuild` (double-dash) to reduce namespace collision with PowerShell common parameters

### Issue 2: CSS selectors from `snapshot` (accessibility tree) don't match `htmlsnapshot` (DOM) selectors

**Severity:** Medium
**Category:** UX / Discoverability

#### Reproduction

1. Take an interactive snapshot: `./b4w.sh snapshot -i`
2. Observe the result panel contained in a `complementary "statusPanel ..."` element
3. Capture htmlsnapshot: `./b4w.sh htmlsnapshot`
4. Try: `./b4w.sh htmlsnapshot get text ".result-panel p"` → fails: `No elements matched ".result-panel p"`
5. Try: `./b4w.sh htmlsnapshot get text "#submission-result p"` → fails: `No elements matched "#submission-result p"`
6. Try: `./b4w.sh htmlsnapshot get text "#statusPanel p"` → succeeds: `Your form data was captured successfully.`

#### Expected Behavior

Selectors visible in the accessibility-tree snapshot (class names from `snapshot`) should work with `htmlsnapshot get`, or the documentation should clearly explain the selector model differences and how to bridge between them.

#### Actual Behavior

The snapshot YAML shows class-based identifiers like `statusPanel`, `result-panel`, `submission-result` as accessible names. But `htmlsnapshot` uses actual DOM CSS selectors (`#statusPanel`, not `.result-panel`). A user reading the snapshot naturally tries the class names they see, gets failures, and has to guess the correct selector. The `htmlsnapshot inspect` tool can help but requires knowing which seed selector to inspect.

#### Root Cause Analysis

The interactive snapshot renders accessibility-tree names that are NOT CSS selectors — they're ARIA/accessible names mixed with class names. The `htmlsnapshot` system uses actual DOM CSS selectors. There is no documented mapping between the two selector systems. The `generate-locator` command (listed in help) might bridge this gap, but it's not mentioned in the form-filling workflow documentation and requires an additional step.

#### Code Pointer

`The gap is architectural — `snapshot` produces accessibility-tree output (CDP `Accessibility.getFullAXTree`) while `htmlsnapshot` captures the DOM. A bridge command or documentation section is needed.`

#### AI Suggested Improvement

- Document the selector-system difference prominently in the "Critical Warnings" section of SKILL.md: *"Snapshot ref names are accessibility labels, not CSS selectors. Use `htmlsnapshot inspect` to discover valid CSS selectors for extraction."*
- After `htmlsnapshot`, print a hint listing the actual CSS IDs found on the page (e.g., `#statusPanel`, `#result-data`) to reduce blind trial-and-error
- Add a `snapshot get-selector <ref>` command that uses `generate-locator` under the hood and prints the CSS selector for a given ref, integrating the bridge into the core workflow
- In `htmlsnapshot get` error messages, suggest running `htmlsnapshot inspect` with the page's top-level container selectors

### Issue 3: No command to list `<select>`/dropdown option values

**Category:** UX / Discoverability

A command like `select e245 --list` or `get options e245` that returns the available option values and labels. Alternatively, the snapshot should include option values alongside labels.

#### Actual Behavior

The snapshot shows option labels as text (e.g., `"United States us United States"`) but does not clearly separate labels from values. - In the `snapshot` output, add a tip when comboboxes are detected: "Use `select <ref> --list` to see available options"

### Issue 7: `fill` auto-captures a new snapshot after every call, producing many snapshot files

**Severity:** Low
**Category:** UX

#### Reproduction

1. Run multiple `fill` commands in succession: `fill e224 "John"`, `fill e231 "Smith"`, etc.
2. Observe each command produces a new snapshot file

#### Expected Behavior

Option to suppress auto-snapshot during batch form filling, since the SKILL.md explicitly states "form interactions (fill, type, press, check, uncheck, select) are safe — you can fill an entire form from a single snapshot." If refs are safe, re-snapshotting is unnecessary overhead.

#### Actual Behavior

Each `fill` command creates a new `snapshot-*.yml` file (~13 KB each). For a form with 8 fields, this produces 8 snapshot files that serve no purpose since the user is intentionally reusing refs from the initial snapshot.

#### Root Cause Analysis

Every interactive command triggers an automatic snapshot capture as a side effect. This is useful for navigation commands (where refs change) but wasteful for form-filling commands (where refs survive).

#### Code Pointer

`The auto-snapshot behavior after each tool execution in the backend's `MCPToolController` or the CLI's post-command hook.`

#### AI Suggested Improvement

- Add a `--no-snapshot` flag to form interaction commands (`fill`, `check`, `uncheck`, `select`, `type`, `press`) to suppress auto-snapshot
- Or automatically suppress auto-snapshot for form interactions since refs are known to survive, and only trigger on navigation/DOM-mutating commands
- Add a global `--auto-snapshot=off` option for scripting scenarios
