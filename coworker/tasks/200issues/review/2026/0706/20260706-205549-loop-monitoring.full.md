### Issue 1: `--name` after `--` silently treated as subcommand args instead of loop-level flag

**Severity:** Medium

**Category:** UX / Discoverability

**Reproduction:**
```bash
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- loop -- status --count 2 --interval 5 --name cli-test
```

**Expected:** The loop is named "cli-test" and the nested browser4-cli receives `status --count 2 --interval 5`.

**Actual:** The loop runs as "(default)" with the task string `status --count 2 --interval 5 --name cli-test`. The `--name` after `--` is consumed as part of the subcommand arguments.

**Root Cause:** The `--` separator in CLI argument parsing conventions sends everything after it to the subcommand. The `--name` flag (a loop-level option) must appear _before_ `--` to be parsed by the loop command. Users unfamiliar with this convention may not realize `--name` is a loop flag, not a browser4-cli flag.

**Code Pointer:** `cli/browser4-cli/src/args.rs` — argument parsing logic for the loop subcommand.

**AI Suggested Improvement:**
- When `--name <value>` appears after `--` in loop subcommand mode, emit a warning: "`--name` after `--` is treated as a nested browser4-cli argument, not a loop name. Did you mean `loop --name <value> -- ...`?"
- Update the loop documentation to explicitly show `--name` before `--` in subcommand-mode examples
- Add an example: `browser4-cli loop --name my-check --count 5 -- status`

### Issue 2: `--resume` is a state-only operation — doesn't launch process execution

**Severity:** Medium

**Category:** UX / Documentation

**Reproduction:**
```bash
browser4-cli loop --pause --shell "echo test" --name demo
browser4-cli loop --resume --name demo    # changes state to "running"
browser4-cli loop --status --name demo    # shows "Running" but nothing executes
```

**Expected:** `--resume` should either start executing the loop, or the UX should make it clearer that a separate `run` step is needed.

**Actual:** `--resume` changes the persisted state from `"paused"` to `"running"` but does not spawn an execution process. The user must re-run the original task command to actually start iterations. The status shows "Running" despite nothing executing, which is misleading.

**Root Cause:** The loop command has two distinct concepts: (1) persisted state control (pause/resume/stop/status) and (2) actual iteration execution (running the task command). `--resume` only changes #1. The design expects the user to re-invoke the task command, which reads the persisted state and resumes from where it left off. This two-step model is not obvious.

**Code Pointer:** `cli/browser4-cli/src/commands.rs` or the loop handler in `main.rs`.

**AI Suggested Improvement:**
- Rename `--resume` to `--unpause` to clarify it only changes state, not launches execution
- Or: make `--resume` also spawn a background process that starts executing iterations (more intuitive)
- Add a hint in the `--resume` output: "Run the same task command to begin execution: `browser4-cli loop --shell \"echo test\" --name demo`"
- The `--status` output for a "running but not executing" loop could show "▶ Running (no active process)" to distinguish from actively executing loops
