# `scroll` command documented in SKILL.md but not implemented in CLI

The `scroll` command is prominently documented in SKILL.md as a supported command, but the actual CLI does not recognize it. Running `browser4-cli scroll down 500` prints the full help text instead of scrolling the page, indicating the command is not wired up. Users must fall back to `browser4-cli eval "window.scrollBy(0, N)"` as a workaround, which is unintuitive and poorly documented.

## Steps to reproduce

1. Open any page longer than one viewport: `browser4-cli open https://www.baidu.com`
2. Attempt to scroll: `browser4-cli scroll down 500`

## Expected behavior

The page scrolls down by 500 pixels.

## Actual behavior

The full help text is printed; the command is not recognized.

## Additional context

- The `eval "window.scrollBy(0, N)"` workaround works but is undiscoverable for new users.
- This is a critical blocker for real-world browsing, as most pages are longer than one viewport.
- Either implement the `scroll` command as documented, or remove it from SKILL.md to avoid misleading users.

# `summarize` command times out with opaque error

The `summarize` command — one of the most valuable AI-agent features — consistently times out with an unhelpful error message. The user receives no indication of whether the backend AI service is unavailable, misconfigured, or simply overloaded.

## Steps to reproduce

```
browser4-cli summarize "武汉龙虾节的历史背景"
```

## Expected behavior

An AI-powered summary of the current page content is returned.

## Actual behavior

```
Error: HTTP request timed out [tool=agent_summarize, endpoint=http://localhost:8182/mcp/call-tool, timeout=30s]
```

## Additional context

- The 30-second timeout is insufficient for AI-powered summarization on long or complex pages.
- The error message does not distinguish between "service unreachable," "service is slow," and "configuration issue" — leaving the user with no actionable next step.
- Consider increasing the default timeout for AI-powered commands and/or improving the error message with diagnostic information (e.g., whether the MCP endpoint responded at all, whether the tool was found, etc.).

# `eval` command produces no output after execution

The `eval` command executes JavaScript in the page context but produces no visible output, making it impossible to distinguish between a successful evaluation, a silent failure, or an expression that returned `undefined`.

## Steps to reproduce

```
browser4-cli eval "window.scrollBy(0, 800)"
```

## Expected behavior

Some confirmation that the eval executed, or the return value of the expression (e.g., `undefined`, a scroll position, or "OK").

## Actual behavior

No output at all (blank line).

## Additional context

- This is particularly problematic when `eval` is used as a workaround for broken commands (e.g., `scroll`), because a silent success is indistinguishable from a silent failure.
- At minimum, the CLI should confirm that the eval expression was executed. Ideally, it should print the return value of the JavaScript expression.

# `go-back` after encountering a 404 does not return to the previous page

When `goto` navigates to a URL that returns a 404 (possibly after a server-side redirect chain), running `go-back` stays on the 404 page instead of returning to the previously browsed page.

## Steps to reproduce

1. Navigate to a search engine and perform a search: `browser4-cli open https://www.baidu.com` → fill → click
2. Navigate to a URL that returns 404: `browser4-cli goto "https://baike.baidu.com/item/武汉小龙虾消费季"`
3. Attempt to go back: `browser4-cli go-back`

## Expected behavior

The browser returns to the search results page.

## Actual behavior

The browser stays on the 404 page. This likely occurs because the 404 response was preceded by a server-side redirect, meaning the failing URL is the only entry in the history stack for that origin.

## Additional context

- Document this edge case in SKILL.md.
- Consider a multi-step `go-back` that can unwind past redirect chains, or a `go-back N` variant to step back multiple history entries at once.

# Baidu search result redirect links may not resolve via `click`

Baidu search result links use an intermediate redirect URL format (`http://www.baidu.com/link?url=...`) that requires Baidu's redirect service to resolve. In at least one test, clicking a search result stayed on the search page rather than navigating to the target — possibly because the link opened in a new tab, or Baidu's anti-bot measures interfered with the redirect.

## Steps to reproduce

1. Open Baidu and search for a term: `browser4-cli open https://www.baidu.com` → `fill` → `click`
2. Identify a search result link (e.g., a Baidu Baike entry)
3. Run `browser4-cli click <ref>` on that result

## Expected behavior

The browser navigates to the target page.

## Actual behavior

In one test case, the browser stayed on the search results page. The target page did not load.

## Additional context

- Baidu links are of the form `http://www.baidu.com/link?url=...` — a redirect service that may behave differently from direct `<a href>` links.
- The documentation should clarify how `click` handles redirect chains, whether it follows them, and whether new-tab/window targets are intercepted.

# Snapshot file naming convention differs between documentation and actual output

The SKILL.md documentation shows snapshot files named with the prefix `page-*.yml`, but the actual CLI produces files named `snapshot-*.yml`. This inconsistency causes confusion when users try to locate files by following the documentation.

## Steps to reproduce

1. Run `browser4-cli open https://www.baidu.com` (which auto-generates a snapshot)
2. Run additional `browser4-cli snapshot` commands
3. Observe the generated file names

## Expected behavior

File names match the convention shown in documentation (`page-*.yml`).

## Actual behavior

Files are named `snapshot-2026-06-21T02-52-08Z.yml` (from `open`) while documentation examples show `page-2026-02-14T19-22-42-679Z.yml`.

## Additional context

- Align documentation examples with the actual output, or allow a configurable naming prefix.
- The inconsistency also suggests the naming prefix may have changed at some point without a corresponding documentation update.

# `help <command>` is unlikely to work for undocumented or missing commands

The CLI has a `help` command that lists available commands, but it is unlikely that `help <command>` works for commands that don't appear in the main help output — such as `scroll`. This means users cannot get per-command documentation for features they discover through SKILL.md or other channels.

## Steps to reproduce

1. Run `browser4-cli help scroll`

## Expected behavior

Documentation for the `scroll` command is displayed (usage, arguments, examples).

## Actual behavior

Presumed to fail or return an error, since `scroll` does not appear in the main `help` listing and may not have a registered help entry.

## Additional context

- Every command that is documented externally (SKILL.md) should have a corresponding `help <command>` entry in the CLI.
- This is a discoverability and documentation integrity issue — users should be able to trust that `help <anything-in-docs>` returns real information.

# Article content is truncated in snapshot due to lazy-loading or viewport-only capture

When navigating to a long article page (e.g., a Baidu Baijiahao article) and taking a snapshot, only the visible portion of the article is captured. Content below the initial viewport is omitted, likely because the accessibility tree only includes elements within the current viewport, or because the page uses lazy-loading for off-screen content.

## Steps to reproduce

1. Navigate to a Baidu Baijiahao article or similar long-form page
2. Run `browser4-cli snapshot`
3. Read the snapshot file

## Expected behavior

The full article body is captured in the snapshot.

## Actual behavior

The snapshot captures the article header and first few paragraphs, then cuts off — showing UI elements like a comment box ("发表神评妙论") and "作者最新文章" (author's latest articles) that normally appear at the bottom of the page, while the middle of the article body is missing.

## Additional context

- The truncation is likely caused by lazy-loading or the accessibility tree only containing viewport-visible content at the time of capture.
- Mitigations could include: auto-scrolling through the page before capturing, or providing a "full-page snapshot" option that scrolls and aggregates content.
- This significantly reduces the value of `snapshot` for research tasks that require reading full articles.
