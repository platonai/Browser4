**88 points | 22 comments | by verditelabs**

**122 points | 33 comments | by kouosi**

Second, **`@bitCast` has been formally redefined** per language proposal #19755 — moving from the old "reinterpret memory bytes" model to precise, portable semantics already proven in the self-hosted x86_64 backend. # Deliverable C: Issues Found

### Issue 1: No built-in article/body text extraction command

**Severity:** High
**Category:** Product / UX

**Reproduction Steps:**
1. Navigate to any article page.
2. Try to extract the article's readable text content.
3. No command like `get text body` or `extract-content` exists that directly returns the page's main text.

**Expected Behavior:** A command or straightforward workflow to retrieve the main textual content of a page (e.g. `browser4-cli get text body`, or `browser4-cli extract --mode=article`).

**Actual Behavior:** The user must write raw JavaScript via `eval` (e.g., `document.body.innerText.substring(0, 4000)`) to get page text. This requires JavaScript knowledge and manual truncation to avoid enormous output. The `extract` command exists but appears to call an AI backend and its output is not surfaced in the CLI (see Issue #3).

**Suggested Improvement:** Add a `get text` target that works on the full page body or auto-detects the main content area. Alternatively, enhance `extract` to reliably return LLM-extracted summaries as CLI output. Document this as the primary workflow for article summarization.

### Issue 2: `extract` command output is opaque / content not returned to CLI

**Severity:** High
**Category:** Product / Reliability

**Reproduction Steps:**
1. Navigate to any page.
2. Run `browser4-cli extract "Summarize this page"`.
3. Observe the output.

**Expected Behavior:** The CLI returns the extracted/summarized content clearly.

**Actual Behavior:**
- Without `--json`: Output shows `success: true message: OK data: {"title":"Hacker News","content":"This is the f...` — the content is truncated with `...`.
- With `--json`: Output contains only page metadata (`page_title`, `page_url`, `snapshot_path`). The actual extraction result is not present.
- The extracted content appears to be lost between the backend and the CLI output layer.

**Suggested Improvement:** Ensure `extract` results are fully surfaced in CLI output. The `--json` output should include an `extracted_content` field. Non-JSON output should print the full extracted text.

### Issue 3: Snapshot YAML uses absolute Windows paths with backslashes

**Severity:** Low
**Category:** UX / Platform

**Reproduction Steps:**
1. Use browser4-cli on Windows.
2. Run any command that produces a snapshot.
3. Observe the snapshot path in the output.

**Expected Behavior:** The path shown matches the documentation style: `.browser4-cli/snapshot/page-<timestamp>.yml` (relative, forward slashes).

**Actual Behavior:** The output prints an absolute path with Windows backslashes: `D:\workspace\Browser4\Browser4-4.11\cli\browser4-cli\.browser4-cli\snapshot\snapshot-2026-06-25T17-48-34Z.yml`. This is noisy and inconsistent with the documentation examples.

**Suggested Improvement:** Either always display snapshot paths relative to the working directory (using forward slashes), or normalize paths for display. The absolute path makes the CLI output harder to scan.

### Issue 5: Ref validity after navigation is undocumented

**Severity:** Medium
**Category:** Documentation / Reliability

**Reproduction Steps:**
1. Take a snapshot on a page, noting element refs.
2. Navigate away and then back to the same page.
3. Attempt to use the original refs.

**Expected Behavior:** Documentation clearly states whether refs persist across navigations (go-back, goto).

**Actual Behavior:** In practice, refs from the initial HN snapshot still worked after `go-back`. However, this behavior is not documented, leaving users uncertain whether they need to re-snapshot after every navigation.

**Suggested Improvement:** Document the ref lifecycle: when refs become stale, when they persist, and best practices (e.g., "re-snapshot after any navigation that may change DOM").

**Severity:** Medium
**Category:** Discoverability / UX

**Reproduction Steps:**
1. Take a large snapshot (e.g., HN with 30 stories, 990 lines).

# Deliverable D: Overall Assessment

### Task Completion Status: ✅ Completed

The task was successfully completed. All three top HN stories were opened and summarized using browser4-cli alone, without any other browser automation tool.

### Estimated Task Success Rate: 75%

A new user with basic web development knowledge would likely complete this task, but with more friction than necessary. The main obstacles are: (1) discovering how to extract page content without a dedicated command, (2) knowing to use `eval` with JavaScript, (3) navigating the snapshot YAML to find element refs.

### Issues Found: 9
- **High:** 2 (no body-text extraction command, `extract` output broken)
- **Medium:** 3 (ref validity undocumented, no snapshot search, eval usability)
- **Low:** 4 (Windows paths, filename mismatch, open vs goto guidance, source-build discoverability)

### Major Blockers
- No straightforward command to extract readable page text. This is the most fundamental gap — reading page content is arguably the #1 thing users want to do after navigation, yet requires hand-crafted `eval` JavaScript.
- The `extract` command's output is broken/not surfaced, making it unusable for its intended purpose.

### Most Confusing Aspects
1. **Content extraction workflow**: A new user expects `get text` or similar to return page content. Discovering that `eval` with raw JS is the path requires reading the help output carefully and understanding what `eval` does.
2. **Snapshot vs domsnapshot**: Two different snapshot systems (accessibility-tree YAML with refs vs static DOM with CSS selectors) with overlapping but different use cases. Understanding which to use when takes time.
3. **Ref lifecycle**: It's unclear whether refs from a snapshot remain valid after go-back or other navigation.

### Most Valuable Improvements (Priority Order)
1. **Add a page-text extraction command** (`get text page` or a new `content` command) — this addresses the most common workflow.
2. **Fix the `extract` command** so its output is properly surfaced in the CLI.
3. **Add a snapshot search command** (`find <text>`) for locating elements by content.
4. **Document ref lifecycle** and add a "Quick Start" section to SKILL.md.
5. **Normalize snapshot path display** to use relative paths.

### Overall Usability Rating: 6/10

**Strengths:**
- The accessibility-tree snapshot model is intuitive once understood — ref-based interaction is clean and avoids fragile CSS selectors.
- `goto` auto-managing sessions is excellent UX — the user doesn't need to think about session lifecycle.
- Command naming is consistent and predictable (`click`, `type`, `fill`, `go-back`, etc.).
- Help output is comprehensive and well-structured.
- The YAML snapshot format is human-readable and diffable.

**Weaknesses:**
- Content extraction (arguably the most important workflow) is underdeveloped. The gap between "navigate" and "read the page" is filled only by raw JS `eval` or a broken `extract` command.
- The dual snapshot systems (accessibility vs DOM) create cognitive overhead.
- Platform-specific rough edges (Windows path display).
- No search/discovery command within snapshots.
- Source-build discoverability is poor for contributors.
