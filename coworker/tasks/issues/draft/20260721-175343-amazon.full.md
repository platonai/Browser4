## C. Issues Found

### Issue 1: Amazon locale auto-detection produces non-English results

**Severity:** Medium

**Category:** Reliability

**Reproduction:** Run `./b4w.ps1 goto "https://www.amazon.com/s?k=pens+to+draw+on+whiteboards"` from a non-US IP. Amazon auto-detects the geographic location and serves zh-CN interface with SGD pricing.

**Expected:** Reasonable to expect en-US content when navigating to `amazon.com` explicitly.

**Actual:** Page served in Chinese with Singapore Dollar pricing. Titles, ratings, and UI were all in Chinese. Prices in SGD rather than USD.

**Root Cause:** Amazon uses IP geolocation to determine locale. browser4-cli connects from the machine's IP address, which Amazon maps to Singapore/International. No `Accept-Language` header or locale override is documented for browser4-cli.

**Code Pointer:** Unknown — this is primarily an Amazon behavior issue, but browser4-cli could potentially expose CDP's `Network.setUserAgentOverride` or `Emulation.setLocaleOverride` to set `Accept-Language: en-US`.

**AI Suggested Improvement:**
- Document that Amazon (and similar sites) will auto-detect locale based on IP, and that results/prices/UI language may differ from the expected `.com` experience
- Consider adding a `--locale` or `--headers` option to `goto` that sets `Accept-Language` and other locale-related headers
- Add a note in the Amazon scenarios doc about locale variation being expected behavior, not a bug

### Issue 2: Separate `get all` calls silently produce misaligned arrays

**Severity:** High

**Category:** UX

**Reproduction:**
```bash
./b4w.ps1 htmlsnapshot get all text "a.a-link-normal.s-line-clamp-4" --limit 4
# Returns: [maxtek..., Volcanics..., 25-pack..., LED...]
./b4w.ps1 htmlsnapshot get all text "span.a-offscreen" --limit 4
# Returns: [SGD 9.02, SGD 0.75, SGD 7.72, SGD 0.65]
```
The second price (SGD 0.75) belongs to an unrelated element, not the Volcanics product.

**Expected:** Either (a) correlated results that align across calls, or (b) a clear warning when results from separate `get all` calls have different counts or cannot be safely aligned.

**Actual:** Each `get all` call scans the entire document independently. Different selectors match different element counts (titles: ~48, prices: ~70+ including non-product prices), producing arrays of different lengths that appear to align at first glance but contain misassigned values.

**Root Cause:** `htmlsnapshot get all` uses `querySelectorAll` semantics scoped to the entire document, not to a shared parent container. Each call is stateless — there's no way to correlate index N from one call with index N from another.

**Code Pointer:** The SKILL.md §4c already documents this warning. The fix could be at the CLI/UX level — when consecutive `get all` calls return different counts, emit a warning that arrays may not align.

**AI Suggested Improvement:**
- After each `get all` call, print the count of matched elements (e.g., "48 matches"). If a subsequent `get all` returns a different count, emit a prominent stderr warning: "⚠ Count mismatch (48 vs 72) — arrays may not align. Use `htmlsnapshot query` for correlated extraction."
- Add a `--count` flag that only returns match counts without extracting data, so users can validate before committing to extraction
- In the `htmlsnapshot` help output, emphasize the X-SQL path more prominently for multi-field extraction

### Issue 4: `htmlsnapshot inspect` (auto-discover without selector) finds navigation elements instead of product cards

**Severity:** Medium

**Category:** Discoverability

**Reproduction:** On an Amazon search results page, run `./b4w.ps1 htmlsnapshot inspect` without a selector argument.

**Expected:** Auto-discover finds the most prominent repeating patterns — product cards with titles, prices, and ratings.

**Actual:** Auto-discover analyzed 3775 `div` elements and suggested selectors for keyboard shortcut navigation elements (`span.shortcut-key.nav-assistant-card-font`, `div.shortcut-keys-container`) — elements that are hidden off-screen (`box=-9966`). Zero product-related selectors were suggested.

**Root Cause:** The auto-discover algorithm picks the first repeating pattern it finds in DOM order. Amazon's accessibility navigation elements appear early in the DOM (before product cards) and have consistent structure, so they're chosen as the pattern to analyze. The `div` element at `:root` level has 3775 matches — the algorithm appears to pick a very broad selector and gets lost in navigation chrome.

**Code Pointer:** The `htmlsnapshot inspect` auto-discovery logic. The algorithm should prioritize visible elements (positive bounding box coordinates) and de-prioritize elements with negative box coordinates (which indicate off-screen/hidden elements like accessibility skip-links).

**AI Suggested Improvement:**
- Filter out elements with negative bounding box coordinates from auto-discovery (accessibility skip-links are typically positioned at `-9999px`)
- Prioritize visible, in-viewport elements when choosing which repeating pattern to analyze
- When `inspect` is run without arguments on a page where a well-known pattern exists (e.g., `[data-component-type="s-search-result"]` on Amazon), suggest trying that selector in the output
- The tip at the bottom suggesting `htmlsnapshot summary` as an alternative is good — but it timed out, creating a dead end (see Issue 3)

**7/10**

The main friction points are: (a) the `get all` alignment trap that can produce silently wrong data, (b) locale-dependent selector fragility on sites like Amazon, and (c) auto-discovery sometimes surfacing irrelevant elements. These are addressable with improved warnings, smarter defaults, and expanded locale guidance.
