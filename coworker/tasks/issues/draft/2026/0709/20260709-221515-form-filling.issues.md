### Issue 1: Interactive snapshot (`-i`) preview too short to be useful for form discovery

**Severity:** Medium
**Category:** UX

#### Reproduction

Run `snapshot -i` on the form-filling page.

#### Expected Behavior

The interactive snapshot should show enough lines to display all form fields and their refs, or provide clear guidance on how to see the full content.

#### Actual Behavior

Only 10 lines of preview are shown. The user sees the header/banner but no form fields. The output directs to use `--stdout` or open the file, but a first-time user following the task instruction to use `-i` would be blocked — they can't discover form field refs from the preview.

#### Root Cause Analysis

The interactive mode's preview truncation (10 lines) is designed for quick scanning, but it doesn't account for pages where the interactive content lies below the fold. The form fields start ~30 lines into the snapshot.

#### Code Pointer

`The snapshot rendering logic that controls preview line count.`

#### AI Suggested Improvement

- Increase the interactive snapshot preview to at least 30 lines, or make it dynamically show content until the first interactive element
- When the page has interactable elements (textboxes, comboboxes, checkboxes), bias the preview toward showing those rather than the top of the page
- Add a tip: "Form elements found below — use `snapshot -v 0 --stdout` to see all fields" when interactive elements are detected beyond the preview

### Issue 2: `get attr` command silently fails with snapshot refs, misleading error message

**Severity:** Medium
**Category:** Discoverability

#### Reproduction

```
browser4-cli get attr e101 value
```
After using refs for `fill`, `click`, `check` etc.

#### Expected Behavior

Either accept refs directly (consistent with `fill`, `click`, `check`), or give a clear error explaining that `get` uses CSS selectors on the live accessibility tree, not snapshot refs.

#### Actual Behavior

Returns `null` with "No elements matched 'e101'" and a tip suggesting to use `htmlsnapshot get text "e101"` instead — confusing because `e101` is not a CSS selector.

#### Root Cause Analysis

The `get` command operates on the live accessibility tree using CSS selectors, while other interaction commands (`fill`, `click`, `check`) use CDP backend node IDs (refs). The error message conflates the two concepts and doesn't clearly explain the mental model difference.

#### Code Pointer

`The `get` command handler that resolves selectors.`

#### AI Suggested Improvement

- Detect when a user passes what looks like a ref (matches `e\d+` pattern) and give a targeted error: "`get` uses CSS selectors on the live page, not snapshot refs. To get an element's `value` attribute, capture the DOM with `htmlsnapshot` first, then use `htmlsnapshot get attr "input#first-name" value`."
- Add a `get` subsection to the quick patterns in SKILL.md showing the correct pattern for reading form field values
- Consider supporting refs in `get` for consistency with other interaction commands

### Issue 3: `htmlsnapshot get attr` selector mismatch — CSS selectors from `htmlsnapshot` summary don't always work

**Severity:** Medium
**Category:** Reliability

#### Reproduction

```
browser4-cli htmlsnapshot                              # shows #identitySection input#first-name
browser4-cli htmlsnapshot get attr "#first-name" value # fails: No elements matched
```

#### Expected Behavior

A CSS selector shown in the `htmlsnapshot` interactive elements summary should work with `htmlsnapshot get attr`.

#### Actual Behavior

`#first-name` returns "No elements matched." The summary lists `input#first-name` but using just `#first-name` doesn't find the element.

#### Root Cause Analysis

The htmlsnapshot interactive elements summary shows compound selectors like `#identitySection input#first-name` but the user naturally tries just `#first-name` which appears valid. The DOM structure stored by htmlsnapshot may not preserve id-based lookup in the same way the live DOM does. Alternatively, the element may be in a shadow DOM or have a different snapshot representation.

#### Code Pointer

`The htmlsnapshot CSS selector resolution logic.`

#### AI Suggested Improvement

- Ensure IDs are queryable in the stored htmlsnapshot — `#first-name` should always match an element with `id="first-name"` in the original HTML
- If the snapshot strips or transforms IDs, document this clearly in the htmlsnapshot output
- Add an `htmlsnapshot inspect` suggestion when `get` returns no matches: "Try `htmlsnapshot inspect` to discover valid selectors for this page"

### Issue 4: Inconsistent viewport count between snapshots

**Category:** Reliability

The viewport count should remain stable for the same page, or the change should be explained.

#### Actual Behavior

The viewport count is computed from the current page height. ### Issue 6: Cargo build output pollutes every command result in dev mode

**Severity:** Low
**Category:** UX

#### Reproduction

Any `cargo run --manifest-path ... -- <command>` in dev mode.

#### Expected Behavior

Clean command output, or a way to suppress build output while still seeing command results.

#### Actual Behavior

Every command is prefixed with:
```
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.47s
     Running `cli/browser4-cli/target/debug/browser4-cli ...`
```
This adds ~2 lines of noise to every command output.

#### Root Cause Analysis

Cargo prints build status to stderr on every invocation. While `--quiet` suppresses this, it also suppresses the command's normal output (tips, snapshot paths, etc.).

#### Code Pointer

`The development.md reference mentions `--quiet` for output redirection but notes the trade-off.`

#### AI Suggested Improvement

- Document a pattern for suppressing only cargo output while preserving command output, e.g.: `cargo run ... 2>/dev/null` or provide a wrapper script
- In development.md, add a note: "To suppress only cargo build lines while keeping command output: `cargo run --quiet ... 2>&1 | grep -v '^\s*\(Finished\|Running\)'`"
- Consider a `--cargo-quiet` flag that's distinct from the CLI's own `--quiet`

### Issue 8: Two-step htmlsnapshot workflow not obvious to new users

**Severity:** Low
**Category:** Discoverability

#### Reproduction

Try to use `htmlsnapshot get text "selector"` without first running `htmlsnapshot`.

#### Expected Behavior

Either auto-capture the htmlsnapshot on first `get` call, or give a clear error: "Run `htmlsnapshot` first to capture the page, then use `htmlsnapshot get`."

#### Actual Behavior

The command returns results from a potentially stale snapshot without warning. A new user might not realize they need to re-capture after page changes.

#### Root Cause Analysis

`htmlsnapshot get` queries the previously stored snapshot. If none was captured or it's stale, results may be empty, misleading, or from a previous page. The two-step workflow (capture → query) is implicit.

#### Code Pointer

`The htmlsnapshot command handler.`

#### AI Suggested Improvement

- Add a `--capture` flag to `htmlsnapshot get` that auto-captures before querying (combining two steps into one)
- When `htmlsnapshot get` returns zero results, add a hint: "No snapshot may be stored for this page. Run `htmlsnapshot` first to capture."
- Track the capture URL and warn if the current page URL differs from the capture URL
