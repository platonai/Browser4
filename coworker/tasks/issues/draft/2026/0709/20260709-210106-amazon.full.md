### Issue 1: htmlsnapshot operations timeout on large pages

**Severity:** High

**Category:** Reliability

**Reproduction:**
```
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- goto "https://www.amazon.com/s?k=pens+to+draw+on+whiteboards"
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- wait --load networkidle
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- htmlsnapshot
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- htmlsnapshot summary
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- htmlsnapshot get all text "a" --limit 4
```

**Expected:** `htmlsnapshot summary` should produce a compressed DOM summary, and `htmlsnapshot get all` should return matching elements, within a reasonable time.

**Actual:** Both commands fail with `HTTP request timed out [tool=..., endpoint=http://localhost:8182/mcp/call-tool, timeout=60s]`. The HTML snapshot was 1788 KB, which appears to exceed the server's processing capacity for summary/get operations.

**Root Cause:** The backend server processes the full HTML snapshot synchronously per request. For large pages (Amazon search results at 1788KB), CSS selector matching and DOM summary generation exceed the 60-second HTTP timeout. The server likely processes the entire DOM tree without streaming or chunking.

**Code Pointer:** `browser4-rest/...` — the MCP tool handler for `html_snapshot_summary` and `html_snapshot_scrape_all` likely performs synchronous in-memory DOM processing without pagination or timeout extension.

**AI Suggested Improvement:**
- Add streaming/chunked processing for large HTML snapshots — process in batches of N nodes rather than the entire tree at once
- Increase the MCP tool timeout for htmlsnapshot operations to 120s or make it configurable
- Add a warning when htmlsnapshot capture exceeds a size threshold (e.g., "Snapshot is 1788KB — extraction commands may be slow. Consider using eval for data extraction instead.")
- Implement server-side result caching so repeated queries against the same snapshot don't reprocess from scratch
- Add a `--timeout` flag to htmlsnapshot commands so users can extend the deadline for large pages

### Issue 2: Browser session becomes unresponsive after htmlsnapshot on large pages

**Severity:** High

**Category:** Reliability

**Reproduction:**
1. Execute `htmlsnapshot summary` on a large page (it times out)
2. After the timeout, run `snapshot -v 0 --stdout`
3. Run `screenshot`

**Expected:** Subsequent commands should work normally against the live browser session.

**Actual:** After `htmlsnapshot summary` timeout, the browser session enters a "ping timeout" state where all commands (`snapshot`, `screenshot`, `reload`) fail with: `ERROR: ... Ping timeout`. The only recovery is `close` followed by re-`goto`.

**Root Cause:** The timed-out htmlsnapshot request likely leaves the backend in a state where the CDP connection to the browser is blocked or the session's WebDriver is stuck waiting for a response. The ping mechanism that checks browser liveness also times out, suggesting the browser process itself may be hung processing the large DOM.

**Code Pointer:** `browser4-core/...WebDriver.kt` — the ping mechanism and CDP connection management; the htmlsnapshot tool may be holding a lock or blocking the CDP channel during long-running DOM serialization.

**AI Suggested Improvement:**
- Implement request cancellation propagation — when an MCP tool call times out, cancel the underlying browser operation and release any locks
- Add a watchdog that detects hung CDP connections and auto-recovers the session
- Isolate htmlsnapshot processing from the live browser connection — snapshot the DOM once, then process it asynchronously without blocking the CDP channel
- After a timeout, automatically re-establish the CDP connection rather than requiring manual `close` + `goto`
