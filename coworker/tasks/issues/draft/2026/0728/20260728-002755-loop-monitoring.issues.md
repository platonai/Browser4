### Task

## Issues Found (8 issues)

### Issue 1: Plain-text loop tasks fail server-side with HTTP timeout

**Severity:** High
**Category:** Reliability

#### Reproduction

./b4w.ps1 loop "navigate to https://httpbin.org/get, take a snapshot, and report the page status" --count 2 --interval 10 --name health-check

#### Expected Behavior

Each iteration executes the natural language task via the Browser4 server's command_run MCP tool and returns results.

#### Actual Behavior

Iteration 1: HTTP request timed out [tool=command_run, timeout=30s]. Iteration 2: returned HTTP 417 Expectation Failed with 'Ping timeout'. Both failures were counted as completed iterations.

#### Root Cause Analysis

The plain-text mode submits tasks to the server's LLM-powered command_run tool, which has a 30-second timeout. For tasks involving page navigation, this timeout is insufficient. The server also returned a 417 status for the second iteration, suggesting the server-side task execution is unreliable.

#### Code Pointer

`browser4-rest MCPToolController — command_run tool timeout configuration; cli/browser4-cli/src/loop.rs — iteration error handling`

#### AI Suggested Improvement

- Increase the command_run MCP tool timeout for loop contexts, or make it configurable via a loop flag
- Distinguish between 'completed with errors' and 'completed successfully' in loop output and history
- Consider providing a --retry flag for failed iterations
- Add a warning when all iterations failed, rather than printing 'Loop finished ✓'

### Issue 2: b4w.ps1 fails with PowerShell parameter ambiguity when using -- for loop subcommand mode

**Severity:** High
**Category:** UX

#### Reproduction

./b4w.ps1 loop --count 2 --name cli-test --interval 5 -- status

#### Expected Behavior

Loop executes the status subcommand twice at 5-second intervals.

#### Actual Behavior

PowerShell error: 'Parameter cannot be processed because the parameter name '' is ambiguous. Possible matches include: -Rebuild -RemainingArgs -Verbose -Debug...'

#### Root Cause Analysis

The b4w.ps1 PowerShell script has its own parameters (-Rebuild, -RemainingArgs, etc.). When `--` is passed as an argument, PowerShell's parameter binder tries to match it against the script's own parameter set. Even wrapping with `b4w.ps1 -- loop ... -- status` doesn't help — the inner `--` still hits PowerShell's binder.

#### Code Pointer

`b4w.ps1 — parameter declaration block; the script needs to consume `--` as a separator before passing remaining args through`

#### AI Suggested Improvement

- Fix b4w.ps1 to properly handle `--` as a passthrough separator (consume it and pass remaining args verbatim to the CLI)
- If PowerShell limits prevent this, document the limitation prominently in loop --help output and the loop.md reference
- Recommend b4w.sh explicitly in the loop subcommand documentation
- Add a self-diagnostic: if the CLI detects loop flags after --, emit a clearer error message suggesting b4w.sh

### Issue 5: Completed loops silently disappear from --list (auto-clean behavior is confusing)

**Severity:** Low
**Category:** UX

#### Reproduction

1. Run a loop with --count 2 2. Wait for completion 3. Run --list

#### Expected Behavior

The loop appears in the list with a 'completed' or 'finished' status, at least for a short grace period.

#### Actual Behavior

The loop is immediately removed from --list upon completion. Users who want to see what happened must know to use --history instead.

Intended design: completed loops auto-clean their state file. The --list command only queries persisted state files, not history. The --history command exists but isn't hinted at in the --list output when no loops are found.

### Issue 6: b4w wrapper outputs redundant help text before every command

**Severity:** Low
**Category:** UX

#### Reproduction

./b4w.ps1 loop --help

#### Expected Behavior

Only the loop command's help text is shown.

#### Actual Behavior

The b4w wrapper's own usage text ('b4w — browser4-cli wrapper...') is printed before every CLI command output, adding noise to the output. The wrapper also prints warnings like 'It is strongly recommended to launch pwsh...' on every invocation.

#### Root Cause Analysis

The b4w.ps1 script always outputs its own usage/warning text in addition to forwarding to the CLI. The em-dash character '—' in 'b4w — browser4-cli wrapper' also triggers 'Unknown command: —' in the CLI's parser.

#### Code Pointer

`b4w.ps1 — wrapper banner/warning output logic`

#### AI Suggested Improvement

- Suppress the wrapper banner when forwarding to CLI commands (keep it only for 'b4w' with no arguments)
- Suppress the 'strongly recommended' warning after the first invocation per session, or make it a one-time message
- Replace the em-dash '—' with a hyphen '-' to avoid CLI parser false positives
