## Issues Found (4 issues)

### Issue 1: tab-new/tab-select help states a platform-specific insertion index that does not hold; new-tab index is unpredictable

**Severity:** Medium
**Category:** Documentation

#### Reproduction

./b4w.ps1 --help tab-new (and --help tab-select) on Windows headless CDP, then run four tab creations and note the reported indices: two `tab-new <url>` calls reported index 0 and index 2; two `tab-new` (about:blank) calls reported index 0 and index 3.

#### Expected Behavior

Either new tabs consistently appear where the help says (index 0 on Windows headless CDP), or the help describes the actual, observed behaviour without a platform-specific promise.

#### Actual Behavior

The help text says 'Tab insertion position is determined by Chrome (not Browser4) ... on Windows headless CDP, new tabs appear at index 0 (before the active tab); on macOS they typically appear after the active tab.' On Windows headless CDP the new tab landed at index 0 in 2 of 4 identical cases and at the end of the list in the other 2. The position is not determined by Chrome at all: the index is the position of the tab in the backend's tab listing (see next issue), which is not the browser's tab-strip order.

#### Root Cause Analysis

The help text was written assuming Chrome/CDP insert-position semantics, but the CLI's index for a new tab comes from matching the new GUID inside the backend's `listDrivers()` order (see BrowserToolExecutor.listTabs), which is an unordered internal map. The code comment in the CLI itself states 'the list order is not guaranteed to reflect creation order (backed by ConcurrentHashMap)'. The reference doc (skills/browser4-cli/references/tabs.md) is more careful ('varies by platform, Chrome version and mode ... prefer --guid'), so the two documents contradict each other.

#### Code Pointer

`cli/browser4-cli/src/help.rs:3330 (tab-new notes) and cli/browser4-cli/src/help.rs:3469 (tab-select notes)`

#### AI Suggested Improvement

- Replace the platform-specific claim with the accurate statement: the index is the tab's position in the backend's tab listing, which may not match the browser window's tab order, can place a brand-new tab anywhere, and must be read from `tab-list` rather than predicted
- Keep the existing advice to always run `tab-list` after creating a tab and to prefer `--guid` when order matters
- After the backend stabilises tab ordering (see next issue), revise both help texts again so docs and behaviour converge

### Issue 2: Tab indices come from an unordered internal driver map, so they do not reflect the browser's tab strip and are inherently fragile

**Severity:** Medium
**Category:** Product

#### Reproduction

./b4w.ps1 tab-new (about:blank) → new tab reported at index 0; repeat with a different active tab → new tab reported at index 3. The index assigned to a new tab bears no relation to visual position or creation order. Also: after closing the active tab, the list's ▶ marker moves to an index that a user cannot predict from the browser window's tab order.

#### Expected Behavior

An 'index' shown next to tabs should be stable and meaningful (e.g. left-to-right tab-strip order or creation order), so 'switch to the first tab' unambiguously identifies a tab across commands.

#### Actual Behavior

Indices are the positions of drivers in `browser.listDrivers()` iteration order. New tabs therefore appear at arbitrary indices (observed 0, 2, 0, 3 across four creations), the ordering does not correspond to the browser's visible tab strip, and the backend's own code comments acknowledge the order is unstable ('ConcurrentHashMap iteration order is unstable'), which is why switchTab deliberately returns a GUID and the CLI re-identifies tabs by GUID internally.

#### Root Cause Analysis

BrowserToolExecutor.listTabs builds the response with `browser.listDrivers().mapIndexed { i, driver -> mapOf("index" to i.toString(), ...) }`. listDrivers() is backed by the base library's driver map (a ConcurrentHashMap), which has no ordering contract; newDriver() insertion does not place the driver at a predictable position, and index→tab resolution can bind the wrong tab if the order shifts between calls (per the comment at the switchTab branch).

#### Code Pointer

`browser4-agentic/src/main/kotlin/ai/platon/pulsar/agentic/tools/builtin/BrowserToolExecutor.kt — listTabs / newTab / switchTab (class callFunctionOn, domain browser)`

#### AI Suggested Improvement

- Sort drivers deterministically in listTabs (e.g. by driver creation sequence recorded at newDriver time, or by the CDP target list order) so `index` matches the visual tab strip and is stable across invocations
- Until the order is deterministic, keep the CLI's GUID-based resolution (already implemented) and consider making GUID the documented primary handle for all tab commands, with index described as a convenience snapshot
- Add an e2e test that creates three tabs and asserts their reported indices follow a defined order — today the code comments admit instability without a test pinning the contract

### Issue 3: tab-list table header/separator do not align with data rows (GUID column width never computed)

**Severity:** Low
**Category:** UX

#### Reproduction

./b4w.ps1 tab-list   (any session with at least one tab)
Observed with 3 tabs; analyze line lengths: header + separator rows = 83 chars, data rows = 113 chars.

#### Expected Behavior

A table whose header labels and dashed separator sit directly above their columns, as in the `list` (sessions) command, whose table is correctly aligned.

#### Actual Behavior

The header row is 83 chars while data rows are 113 chars. The 'GUID' header field is 4 chars wide but GUIDs are 32-char strings, so each data row overflows that cell and pushes 'Title'/'URL' 30 columns to the right of their headers (e.g. 'Title' header at column 15, actual titles at column 45). The active-row '▶ ' marker is additionally prepended before the padded index field, shifting the index of active rows 2 columns right of the header.

#### Root Cause Analysis

In handle_tab_list() the GUID column width is computed as `let guid_w = "GUID".len();` (always 4) while idx_w/title_w/url_w are widened to the data maxima via .max(...). Rust's `{:<4}` does not truncate, so 32-char GUIDs overflow and shift all later columns; header/separator rows are also printed without the 2-char active-marker prefix accounted for.

#### Code Pointer

`cli/browser4-cli/src/main.rs:handle_tab_list() (approx. lines 3643-3710, the human-readable table branch)`

#### AI Suggested Improvement

- Compute the GUID width from the data like the other columns: `let guid_w = "GUID".len().max(tabs.iter().map(|t| format_guid_display(t.guid.as_deref()).len()).max().unwrap_or(0));`
- Account for the 2-char active marker in the header/separator rows (e.g. print the header with a 2-space prefix before the index field) so the Index column also lines up
- Add a unit test asserting the header/separator line length equals each data row length (the sessions `list` table already behaves correctly and can serve as the reference implementation)
