### Issue 1: crawl reports success while emitting fully-empty rows for pages that matched nothing

**Severity:** High
**Category:** Reliability

#### Reproduction

./b4w.ps1 -s cy-gift crawl --seed-file .test-sessions/20260920T0355347004286Z/urls.txt --depth 0 --sql "@.test-sessions/20260920T0355347004286Z/detail.sql" --format json -o out.json

#### Expected Behavior

Pages from which no field could be extracted should be flagged (a per-row warning, a null/'not extracted' marker, or at minimum a count in the summary line), since the consumer cannot distinguish them from real data.

#### Actual Behavior

The run printed '16 pages crawled, 16 rows extracted.' and exited 0. Five rows (B0CHB79PLJ, B0C6HVDH7W, B0FVVXCRF9, B08LD61Q67, B000TPUTTS) are empty strings in every single field. Those URLs are Amazon Music pages: /dp/<ASIN> redirects to a Music player page that has no #productTitle, no price and no rating, so every X-SQL projection resolves to an empty string.

#### Root Cause Analysis

The X-SQL projection emits a row of empty strings when no source selector matches, and the crawl aggregator counts rows without checking whether any column actually produced a value. There is no per-row 'nothing extracted' signal.

#### Code Pointer

`browser4-rest CrawlRoundRunner.kt / browser4-agent-tools .../crawl/common/ScrapeAPIUtils.kt (row emission and result aggregation)`

#### AI Suggested Improvement

- Mark rows where every projected column is empty, e.g. add "noFieldsExtracted": true.
- Report the count distinctly in the completion line: '16 pages crawled, 11 rows with data, 5 rows empty'.
- Detect the /dp/<ASIN> -> Amazon Music redirect (or a missing page-title element) and surface it as a per-URL status rather than an empty row.

### Issue 2: htmlsnapshot summary emits invalid CSS selectors labelled "Copy-paste ready"

**Severity:** Medium
**Category:** Product

#### Reproduction

1) ./b4w.ps1 -s cy-gift goto "https://www.amazon.com/s?k=Calabi-Yau"
2) ./b4w.ps1 -s cy-gift htmlsnapshot summary
3) Run any command from the '### Suggested Commands' block, e.g.:
   ./b4w.ps1 -s cy-gift htmlsnapshot get all text ".s-main-slot s-result-list s-search-results sg-row a" --limit 5

#### Expected Behavior

The command prints 'Copy-paste ready — use these to extract data', so running it should return page data.

#### Actual Behavior

Returns []. Note the sibling output printed 3 identical suggested commands, and each fails the same way. The supplied selectors join CSS class names with spaces ('.s-main-slot s-result-list s-search-results sg-row') instead of dots, so they are not valid selectors for the intended element.

#### Root Cause Analysis

PageSummaryIndexService.buildSelectorHint() returns ".$className" where className is the element's entire class attribute string. For a multi-class element this yields '.a-size-base s-desktop-toolbar a-text-normal' — one class selector followed by two descendant type/tag selectors, matching nothing. The CLI then interpolates this string verbatim into a copy-paste command without validating it. Confirmed in the raw summary YAML: `selector: ".a-size-base s-desktop-toolbar a-text-normal"`.

#### Code Pointer

`browser4-core/browser4-skeleton/src/main/kotlin/ai/platon/pulsar/skeleton/workflow/parse/html/PageSummaryIndexService.kt:424 (buildSelectorHint); consumed at cli/browser4-cli/src/main.rs:8515`

#### AI Suggested Improvement

- In buildSelectorHint, split className on whitespace and prefix every token with '.': `className.trim().split(Regex("\\s+")).joinToString("") { ".$it" }`.
- Validate the generated selector before printing it in Suggested Commands; if it does not resolve, omit it rather than emitting a broken command.
- De-duplicate the suggested-command list (three identical lines were printed for three link groups sharing one container).
- Add a regression test using a multi-class element (e.g. `class="a-size-base s-desktop-toolbar"`).

### Issue 6: A 16-URL depth-0 crawl exceeds the 600 s cap; only an environment variable raises it

**Severity:** Medium
**Category:** Reliability

#### Reproduction

./b4w.ps1 -s cy-gift crawl --seed-file urls.txt --depth 0 --sql "@detail2.sql" --format json -o out.json
# 16 Amazon /dp/ URLs, default --parallel 4

#### Expected Behavior

A 16-page bulk fetch should complete, or the CLI should warn up front that the job may exceed the limit and point at --parallel / --background.

#### Actual Behavior

At 600 s the CLI printed 'Crawl timed out after 600 seconds (CLI wait)' and exited non-zero without writing out.json. `crawl status <id>` then reported the server-side task itself had died: "status": "Request Timeout", error "Crawl timed out while processing seeds (server-side limit of 600s exceeded). Partial results below." Only 8 of 16 pages were processed. Partial data was recoverable via `crawl result <id>`, which the error message did correctly suggest.

#### Root Cause Analysis

cli/browser4-cli/src/http.rs:14 sets CRAWL_REQUEST_TIMEOUT_SECS = 600, matching a server-side 600 s seed-processing cap. The CLI wait and the server cap are the same value, so they race and the CLI gives up at the same moment the server does. Amazon pages take ~15-25 s each, so 16 pages at --parallel 4 exceeds 10 minutes. `crawl --help` documents neither the limit nor the env var nor --parallel as the mitigation; the only remedy offered is BROWSER4_CLI_CRAWL_TIMEOUT_SECS, which must be set before the run.

#### Code Pointer

`cli/browser4-cli/src/http.rs:14 (CRAWL_REQUEST_TIMEOUT_SECS) and cli/browser4-cli/src/main.rs:13893 (timeout message)`

#### AI Suggested Improvement

- Document the 600 s cap, BROWSER4_CLI_CRAWL_TIMEOUT_SECS and `--parallel N` in `crawl --help` and in the docs' bulk-fetch recipe.
- Add a `--timeout` flag so the limit is settable per invocation instead of only via an env var.
- Print guidance during the run when elapsed time is high relative to the page count (e.g. 'consider --parallel 8 or --background').

## Overall Assessment

**Completion Status:** Successful with caveats — search, a ranked 10-item shortlist, detail-page review of all 16 results, and a justified single pick were all delivered. Notable caveat: the underlying catalogue is a poor fit for the task's premise, so most of the shortlist is graduate-level mathematics rather than age-appropriate gifts, and only 2 of the 10 are genuinely suitable for a 12-year-old.

**Success Rate:** 90% — every task step completed; two commands failed outright (a 600 s crawl timeout and the unusable suggested selectors), each with a working recovery, and one result file per invocation intermittently came back as unparseable JSON.

**Issues Found:** 11

**Major Blockers:** None fatal. The two significant friction points were (1) both documented discovery affordances failing on the canonical Amazon example, so selector discovery had to be done by hand with eval; and (2) a 16-URL bulk crawl exceeding the 600 s cap and dying server-side, requiring recovery via crawl result.

**Most Confusing Aspects:** Discovering which selectors actually work. The summary's 'Copy-paste ready' commands return nothing, inspect auto-discovery returns navigation chrome instead of product cards, and the documented Amazon selectors are inverted from the live DOM. A first-time user has no reliable in-tool way to find a working selector on Amazon and must fall back to writing their own JavaScript. Secondary confusion: the locale/currency silently switching between CNY and USD depending on which command fetched the page, and a crawl reporting '16 rows extracted' when 5 rows are entirely empty.

**Most Valuable Improvements:** 1) Fix buildSelectorHint so class lists become real selectors, and validate before printing any 'copy-paste ready' command. 2) Make inspect's auto-discovery exclude off-screen nodes and score repeating card containers instead of raw match counts. 3) Refresh the Amazon scenario selectors and add a self-check line to each scenario. 4) Keep stdout pure for --json — a CLI aimed at agents must never prepend build chatter to its JSON envelope. 5) Flag empty extraction rows so silent data loss becomes visible.

**Usability Rating:** 6/10

## How to Reproduce

### Common Setup

1. Clone the repository and `cd` to the repo root.
2. The CLI is invoked via `./b4w.ps1` (PowerShell) or `./b4w.sh` (Bash / Git Bash), which auto-build from source when needed.
3. The backend server starts automatically in dev mode.
4. All commands from repo root:

   - **PowerShell:** `./b4w.ps1 <command>`
   - **Bash / Git Bash:** `./b4w.sh <command>`
   - **Direct:** `browser4-cli <command>` (if installed globally)

   > **Note:** `$(./b4w.ps1)` is command substitution in bash — do NOT use it.
