### Issue 1: Amazon locale auto-detection produces non-English results

**Severity:** Medium
**Category:** Reliability

#### Reproduction

Run `./b4w.ps1 goto "https://www.amazon.com/s?k=pens+to+draw+on+whiteboards"` from a non-US IP. Amazon auto-detects the geographic location and serves zh-CN interface with SGD pricing.

#### Expected Behavior

Reasonable to expect en-US content when navigating to `amazon.com` explicitly.

#### Actual Behavior

Page served in Chinese with Singapore Dollar pricing. Titles, ratings, and UI were all in Chinese. Prices in SGD rather than USD.

#### Root Cause Analysis

Amazon uses IP geolocation to determine locale. browser4-cli connects from the machine's IP address, which Amazon maps to Singapore/International. No `Accept-Language` header or locale override is documented for browser4-cli.

#### Code Pointer

`Unknown — this is primarily an Amazon behavior issue, but browser4-cli could potentially expose CDP's `Network.setUserAgentOverride` or `Emulation.setLocaleOverride` to set `Accept-Language: en-US`.`

#### AI Suggested Improvement

- Document that Amazon (and similar sites) will auto-detect locale based on IP, and that results/prices/UI language may differ from the expected `.com` experience
- Consider adding a `--locale` or `--headers` option to `goto` that sets `Accept-Language` and other locale-related headers
- Add a note in the Amazon scenarios doc about locale variation being expected behavior, not a bug

### Issue 2: Separate `get all` calls silently produce misaligned arrays

**Severity:** High
**Category:** UX

#### Reproduction

```bash
./b4w.ps1 htmlsnapshot get all text "a.a-link-normal.s-line-clamp-4" --limit 4
# Returns: [maxtek..., Volcanics..., 25-pack..., LED...]
./b4w.ps1 htmlsnapshot get all text "span.a-offscreen" --limit 4
# Returns: [SGD 9.02, SGD 0.75, SGD 7.72, SGD 0.65]
```
The second price (SGD 0.75) belongs to an unrelated element, not the Volcanics product.

#### Expected Behavior

Either (a) correlated results that align across calls, or (b) a clear warning when results from separate `get all` calls have different counts or cannot be safely aligned.

#### Actual Behavior

Each `get all` call scans the entire document independently. Different selectors match different element counts (titles: ~48, prices: ~70+ including non-product prices), producing arrays of different lengths that appear to align at first glance but contain misassigned values.

#### Root Cause Analysis

`htmlsnapshot get all` uses `querySelectorAll` semantics scoped to the entire document, not to a shared parent container. Each call is stateless — there's no way to correlate index N from one call with index N from another.

#### Code Pointer

`The SKILL.md §4c already documents this warning. The fix could be at the CLI/UX level — when consecutive `get all` calls return different counts, emit a warning that arrays may not align.`

#### AI Suggested Improvement

- After each `get all` call, print the count of matched elements (e.g., "48 matches"). If a subsequent `get all` returns a different count, emit a prominent stderr warning: "⚠ Count mismatch (48 vs 72) — arrays may not align. Use `htmlsnapshot query` for correlated extraction."
- Add a `--count` flag that only returns match counts without extracting data, so users can validate before committing to extraction
- In the `htmlsnapshot` help output, emphasize the X-SQL path more prominently for multi-field extraction

### Issue 3: `htmlsnapshot summary` times out on large pages (1590 KB Amazon page)

**Severity:** Medium
**Category:** Reliability

#### Reproduction

Navigate to `https://www.amazon.com/s?k=pens+to+draw+on+whiteboards`, run `./b4w.ps1 htmlsnapshot`, then run `./b4w.ps1 htmlsnapshot summary`.

#### Expected Behavior

WPSI summary returns within a reasonable time, or a clear error message if the page is too large.

#### Actual Behavior

`Error: HTTP request timed out [tool=page_title, endpoint=http://localhost:8182/mcp/call-tool, timeout=30s]`. The error message references `tool=page_title` which is misleading — the user asked for `summary`, not `page_title`.

#### Root Cause Analysis

The 30-second HTTP timeout was insufficient to process the 1590 KB page. Additionally, the error message references the wrong tool name (`page_title` instead of `htmlsnapshot summary`), suggesting a backend dispatch issue.

#### Code Pointer

``browser4-rest` — `MCPToolController.kt` or the page-summary generation code. The 30s timeout appears to be a client-side HTTP timeout. The tool name in the error message may come from an internal dispatch chain that maps `htmlsnapshot summary` to an underlying `page_title` tool.`

#### AI Suggested Improvement

- Increase the HTTP timeout for `htmlsnapshot summary` (large pages are the main use case for summaries)
- Fix the error message to reference the correct user-facing tool name (`htmlsnapshot summary`, not `page_title`)
- Consider streaming or progressive summary generation for very large pages, or fall back to a partial summary with a note that the page exceeded size limits
- Add a `--timeout` flag to allow users to extend timeouts for known-large pages

### Issue 4: `htmlsnapshot inspect` (auto-discover without selector) finds navigation elements instead of product cards

**Severity:** Medium
**Category:** Discoverability

#### Reproduction

On an Amazon search results page, run `./b4w.ps1 htmlsnapshot inspect` without a selector argument.

#### Expected Behavior

Auto-discover finds the most prominent repeating patterns — product cards with titles, prices, and ratings.

#### Actual Behavior

Auto-discover analyzed 3775 `div` elements and suggested selectors for keyboard shortcut navigation elements (`span.shortcut-key.nav-assistant-card-font`, `div.shortcut-keys-container`) — elements that are hidden off-screen (`box=-9966`). Zero product-related selectors were suggested.

#### Root Cause Analysis

The auto-discover algorithm picks the first repeating pattern it finds in DOM order. Amazon's accessibility navigation elements appear early in the DOM (before product cards) and have consistent structure, so they're chosen as the pattern to analyze. The `div` element at `:root` level has 3775 matches — the algorithm appears to pick a very broad selector and gets lost in navigation chrome.

#### Code Pointer

`The `htmlsnapshot inspect` auto-discovery logic. The algorithm should prioritize visible elements (positive bounding box coordinates) and de-prioritize elements with negative box coordinates (which indicate off-screen/hidden elements like accessibility skip-links).`

#### AI Suggested Improvement

- Filter out elements with negative bounding box coordinates from auto-discovery (accessibility skip-links are typically positioned at `-9999px`)
- Prioritize visible, in-viewport elements when choosing which repeating pattern to analyze
- When `inspect` is run without arguments on a page where a well-known pattern exists (e.g., `[data-component-type="s-search-result"]` on Amazon), suggest trying that selector in the output
- The tip at the bottom suggesting `htmlsnapshot summary` as an alternative is good — but it timed out, creating a dead end (see Issue 3)

`h2 a.a-link-normal` returned empty. The working selector was `a.a-link-normal.s-line-clamp-4` (discovered from the interactive elements output of `htmlsnapshot`). Amazon's zh-CN locale uses different heading structures for product titles. The `h2` wrapping may not exist, or the `a-link-normal` class may have additional modifiers. The docs acknowledge this but the discover→validate→extract workflow is spread across scenarios — a new user reading Scenario 15c sees `get all text "h2 a.a-link-normal"` as the first command and tries it directly.

- In Scenario 15c, show the `inspect` output FIRST and then derive selectors from it, rather than presenting hardcoded selectors that the user is expected to try directly

**Category:** UX

#### Expected Behavior

Consistent output behavior across commands — either all file-based or all stdout.

`snapshot` saves to a YAML file by default (with `--stdout` to override). `htmlsnapshot get all` prints JSON to stdout by default. This is actually fine and documented — just noting the asymmetry.

#### Root Cause Analysis

Different output models — `snapshot` produces large YAML files (up to 256KB+), so file output is the safe default. `htmlsnapshot get` returns small JSON arrays suitable for stdout.

### Issue 7: X-SQL `reviews` field returned rating text instead of review count

**Severity:** Low
**Category:** Documentation

#### Reproduction

The query.sql file included `DOM_FIRST_TEXT(DOM, '.a-size-base.s-underline-text, .a-row.a-size-small span:expr(char>10)') AS reviews`, but on this locale the selector didn't match. The `reviews` field fell back to the same value as `rating`.

#### Expected Behavior

Review count (e.g., "13,131") should be extracted separately from rating text.

#### Actual Behavior

The `reviews` field contains rating text ("4.4 颗星，最多 5 颗星"), duplicating the rating field.

#### Root Cause Analysis

The CSS selector for review counts in the query.sql file was written for the en-US locale. On zh-CN locale, the review count element has different classes/structure. The `DOM_FIRST_TEXT` function with fallback selectors didn't find a match and may have fallen back to a parent element's text.

#### Code Pointer

``query.sql` — the CSS selector for review counts needs locale-aware variants. This is a documentation/example issue — the query serves as a template users adapt.`

#### AI Suggested Improvement

- Add a note in the Amazon scenarios that the `reviews` selector is locale-dependent and may need adjustment
- Show how to use `htmlsnapshot inspect` to discover the correct review-count selector for the current locale
