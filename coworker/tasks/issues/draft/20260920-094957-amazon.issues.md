### Issue 1: X-SQL (htmlsnapshot query) times out on every query — the documented extraction path is completely non-functional

**Severity:** Critical
**Category:** Product

#### Reproduction

./b4w.ps1 -s probe open --headless "https://example.com"
./b4w.ps1 -s probe htmlsnapshot query --sql "SELECT DOM_FIRST_TEXT(DOM, 'h1') AS h FROM DOM_LOAD_AND_SELECT(@url, ':root')"
Also reproduced against the Amazon search results page, with selector 'body', and with a literal URL instead of @url.

#### Expected Behavior

The query returns the page's h1 text ('Example Domain') in a fraction of a second — this is the exact example printed by `browser4-cli` help.

#### Actual Behavior

Every query hangs and returns: {"statusCode":408,"pageStatusCode":408,"pageContentBytes":0,"isDone":false,"resultSet":null,"message":"X-SQL query timed out after 120s. The page may be too large or the session may be unresponsive."} — reproduced on a ~1.3 KB static page and on a 1.4 MB Amazon page, with ':root', 'body', and a literal URL. The whole documented extraction workflow (SKILL.md section 4b decision tree, x-sql.md, and the Amazon scenario's 'Step 15d') is unusable in this build.

#### Root Cause Analysis

The failure is independent of page size, selector, and URL source, so the 120s server-side timeout is not caused by page complexity — the message is misleading. pageContentBytes:0 indicates the target document is never serialized into the query engine before the timeout fires, i.e. DOM_LOAD_AND_SELECT never yields rows. Most likely culprits are the page-load/serialize step of the X-SQL execution path or a lock/deadlock on the session's page context. Needs investigation in the backend X-SQL executor and the htmlsnapshot query handler.

#### Code Pointer

`Backend X-SQL execution path used by `htmlsnapshot query` (browser4-rest htmlsnapshot/query handler + the X-SQL DOM_LOAD_AND_SELECT implementation); CLI entry point in cli/browser4-cli/src/ (htmlsnapshot query).`

#### AI Suggested Improvement

- Reproduce with the one-line example.com query above and instrument the backend query executor to find where those 120s are spent (page acquisition vs. serialization vs. SQL evaluation).
- Check whether the session/page lock is held or re-entered while the query engine tries to acquire the page, which would deadlock until the timeout.
- Fix the error text to report the real cause instead of blaming page size, once identified.
- Add a regression test that runs a trivial `DOM_LOAD_AND_SELECT(@url, ':root')` query against a tiny fixture page and asserts it completes in well under 5s.
- Until fixed, correct the docs that present X-SQL as the primary structured-extraction path so users do not lose time on it.

### Issue 2: Failed queries exit 0 and `--format table` prints a bare `null` — failures are silent

**Severity:** High
**Category:** Reliability

#### Reproduction

./b4w.ps1 -s probe htmlsnapshot query --sql "SELECT DOM_FIRST_TEXT(DOM, 'h1') AS h FROM DOM_LOAD_AND_SELECT(@url, ':root')" --format table

#### Expected Behavior

A visible error describing the failure, and a nonzero exit code. The CLI's own docs promise: 'Exit code is nonzero on a server error envelope (417, 5xx) but 0 on a 200 with an empty resultSet.'

#### Actual Behavior

Prints exactly `null` with exit code 0. The 408 timeout envelope and its explanatory message are discarded entirely; the empty result is indistinguishable from a legitimately empty query. The same query without --format table does show the envelope, so the table renderer is the layer swallowing it.

#### Root Cause Analysis

The --format table renderer has no branch for resultSet == null / a non-success statusCode, and the exit-code mapping keys off the HTTP status rather than the envelope's `statusCode` field (which is 408 inside an otherwise-successful HTTP response). Any non-2xx envelope statusCode should be treated as an error.

#### Code Pointer

`cli/browser4-cli/src/ — the `htmlsnapshot query` output renderer (table format) and the shared exit-code mapping for command envelopes.`

#### AI Suggested Improvement

- Make --format table print an error line to stderr and exit nonzero whenever envelope.statusCode is not 2xx or resultSet is null.
- Drive exit codes from the envelope's statusCode, not just the HTTP status, so a 408/417/5xx body is never reported as success.
- Distinguish 'empty result set' (print an empty table / 'no rows') from 'query failed' (print the message) — currently both collapse to `null`.
- Add CLI tests covering each envelope statusCode to lock in the exit-code contract.
