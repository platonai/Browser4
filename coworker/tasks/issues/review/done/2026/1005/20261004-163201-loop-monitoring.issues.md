## Scenario Background

### Task

All 12 steps were executed end-to-end with `./b4w.ps1`. The `loop` command itself works well in its core execution modes: a plain-text LLM task ran twice (navigated to `https://httpbin.org/get`, produced a page summary and status), shell mode printed the time twice, and subcommand mode ran `status` twice — all with correct interval pacing and persisted progress (`--list`, `--status`, follow-up iterations). Pause/resume/start-paused worked as documented.

However, three of the twelve steps did not achieve their stated intent without manual intervention:

- **Step 9/11 failed**: `--stop` and `--stop-all` report success and delete the state file, but the running loop process is never signalled. It keeps iterating and **re-creates** the state file, so the loop "resurrects"; a paused loop's spawned process becomes a **permanent orphan**. I had to kill two orphaned `browser4-cli.exe` processes manually with PowerShell `Stop-Process` to clean up.

- **Step 6 partially**: only 1 of the expected 3 loops appeared in `--list`, because completed loops auto-delete their state immediately (documented, but easy to misread as "loop never existed").

Server health remained UP throughout, and `--stop-all` after the manual kills left zero persisted loops and zero loop processes.

### Issue 1: --stop/--stop-all report success but do not stop running loops (state resurrects)

**Severity:** Critical
**Category:** Reliability

#### Reproduction

1) ./b4w.ps1 loop --name timeout-test -t 600 --interval 5 --count 100 --shell "echo tick" (or any long-running loop)
2) ./b4w.ps1 loop --stop --name timeout-test   # prints 'stopped. 62 iteration(s) completed. State cleared.'
3) wait ~60s, then ./b4w.ps1 loop --list      # loop shows as running again with MORE iterations and the state file is back
4) ./b4w.ps1 loop --stop-all                  # same result: file recreated (observed 71 -> 75 -> 82 iterations)

#### Expected Behavior

The running loop process receives a stop signal, exits at the next iteration boundary, and the state file stays gone.

#### Actual Behavior

Only the state file is deleted; the running process never sees a signal, keeps executing iterations (observed 62 -> 71 -> 75 -> 82 iterations over ~2 minutes) and re-persists status 'running' after each iteration, resurrecting the loop. The success message ('stopped... State cleared') is false, and --stop-all had to be re-run after manually killing the process.

#### Root Cause Analysis

handle_loop's --stop branch (main.rs ~15998-16046) calls state::clear_loop_state and --stop-all (~16048-16068) calls state::clear_all_loop_states; both only unlink the JSON file. The worker's only stop channel is a persisted state with status == 'stopped' (checked at main.rs ~16464 top-of-iteration and ~16696 during sleep), but no code path ever writes status 'stopped' - the writes are dead code. Deleting the file is interpreted as 'no signal', and the per-iteration persist() then rewrites the file.

#### Code Pointer

`cli/browser4-cli/src/main.rs: handle_loop --stop branch (~15998-16046), --stop-all branch (~16048-16068), worker signal checks (~16462-16520); cli/browser4-cli/src/state.rs: clear_loop_state/clear_all_loop_states`

#### AI Suggested Improvement

- Make --stop persist status 'stopped' (state::set_loop_status / write_loop_state) instead of deleting the file; the worker already detects that status and exits, and it clears state on exit.
- Keep --stop clearing the file immediately only when no worker process is alive (add pid/liveness info to LoopState), or garbage-collect stale 'stopped' entries on the next --list/--status.
- Avoid double history entries: the control op writes a 'stopped' history entry now while the worker would also write one on exit.
- Add an integration test that starts a real loop subprocess, runs --stop, and asserts the process exits and the state file does not reappear (current tests only exercise parse_loop_args).
- Report a nonzero exit or warning if a running process could not actually be signaled.

### Issue 2: loop --timeout (long form) is silently swallowed by the global HTTP timeout; resumed loops lose their timeout

**Severity:** High
**Category:** Product

#### Reproduction

1) ./b4w.ps1 loop --pause --name t-long --shell --count 100 --interval 5 --timeout 30 "echo t"  -> header says 'up to 100 iterations or 604800s'; ~/.browser4/loops/t-long.json has "timeoutSecs": 604800
2) ./b4w.ps1 loop --pause --name t-short --shell --count 100 --interval 5 -t 30 "echo t"          -> header says 'or 30s'; state has "timeoutSecs": 30
3) ./b4w.ps1 loop --name timeout-test --timeout 30 --interval 5 --count 100 --shell "echo tick"    -> runs past 300s (82 iterations, ~7 min) instead of stopping at ~30s
4) Create paused loop with '-t 12', then ./b4w.ps1 loop --resume --name <n>; after one iteration the state file's timeoutSecs becomes 604800

#### Expected Behavior

loop --timeout 30 (documented as '-t, --timeout') bounds the loop to 30 seconds, exactly like -t 30.

#### Actual Behavior

--timeout is consumed by the global flag parser as the per-call HTTP timeout and never reaches the loop parser; the loop keeps the 1-week default and runs to --count. The CLI's own --resume spawn path re-emits '--timeout', so every resumed loop also reverts to 604800 even when originally created with -t.

#### Root Cause Analysis

In cli/browser4-cli/src/args.rs, parse_global_flags consumes '--timeout <v>' and '--timeout=<v>' unconditionally (~lines 114-126) with no '!seen_command' guard (unlike --json, -q, --session, --proxy); the tokens are stripped before dispatch, so parse_loop_args (main.rs ~15574-15577) never sees them. '-t' is not a global flag, so it survives. The resume spawner emits the long form at main.rs ~16213-16216, making the same mistake internally.

#### Code Pointer

`cli/browser4-cli/src/args.rs: parse_global_flags (~114-126); cli/browser4-cli/src/main.rs:16213-16216 (resume spawn args); cli/browser4-cli/src/main.rs:15574-15577 (loop parser, currently unreachable for the long form)`

#### AI Suggested Improvement

- Add the same '!seen_command' guard to --timeout/--timeout= that --json/-q/--proxy have, so after a command name it is forwarded to the subcommand; document that global flags go before the command.
- Audit commands that legitimately accept --timeout after the command (e.g. plugin tools) to parse it themselves, so the guard does not regress them.
- As defense in depth, emit '-t' from the resume spawner instead of '--timeout'.
- Add a regression test through the real path (parse_global_flags + parse_loop_args); the existing test at main.rs:26470 calls parse_loop_args directly with '--timeout' and passes while the shipped path is broken.
- Consider warning when loop finds a numeric --timeout-looking value in argv that was consumed elsewhere.

### Issue 3: --stop on a paused loop orphans its background process forever

**Severity:** High
**Category:** Reliability

#### Reproduction

1) ./b4w.ps1 loop --pause --name paused-test --shell --count 5 --interval 10 "echo paused-check"
2) ./b4w.ps1 loop --resume --name paused-test        # spawns detached PID
3) ./b4w.ps1 loop --pause --name paused-test         # loop now paused, process alive
4) ./b4w.ps1 loop --stop --name paused-test          # prints 'stopped... State cleared'
5) powershell Get-CimInstance Win32_Process ...      # the loop PID is still alive minutes later

#### Expected Behavior

The paused loop's process exits when --stop clears it.

#### Actual Behavior

Observed PID 51556 still alive ~7 minutes after --stop (it had to be killed with Stop-Process). A paused worker never exits and keeps consuming a process slot indefinitely.

#### Root Cause Analysis

The pause-wait inner loop (main.rs ~16486-16515) only exits when read_loop_state returns a state with status 'stopped' or 'running'. --stop deletes the file, so read_loop_state returns None and neither branch fires; the process polls every 2 s forever. Compounded by the stop bug above (nothing writes 'stopped').

#### Code Pointer

`cli/browser4-cli/src/main.rs:16486-16515 (pause-wait poll loop); 15998-16046 (--stop deletes state)`

#### AI Suggested Improvement

- Treat a missing state file while paused as a stop signal (print a message and exit), or keep the file and write status 'stopped' (fixed naturally by the --stop fix).
- Record the worker PID (and/or heartbeat timestamp) in LoopState so control ops can detect and terminate orphaned workers.
- Have --stop attempt process termination (or at least warn) when a live worker is detected.

## Overall Assessment

**Completion Status:** Partially Successful - all 12 steps were executed end-to-end and the loop feature's execution modes (plain/shell/subcommand), listing, status, start-paused and pause/resume all worked; but steps 9-11 did not achieve their intent: --stop/--stop-all left loop processes running (manual taskkill required) and step 10's --timeout was silently ignored until re-run with -t.

**Success Rate:** 70% - 8.5 of 12 steps achieved their stated intent; steps 9, 10 (as specified) and 11 failed without manual process kills, step 6 showed 1 of the expected 3 loops due to documented auto-cleanup.

**Issues Found:** 8

**Major Blockers:** loop --stop and --stop-all do not signal running processes: loops keep iterating and resurrect their state file, and paused loops orphan a process forever; cleanup required manual PowerShell Stop-Process. Separately, loop --timeout 30 is silently consumed by the global HTTP timeout option, turning a 30-second bounded loop into an 82-iteration ~7-minute runaway.

**Most Confusing Aspects:** The same long flag --timeout means two different things and is silently stolen by the global parser while -t works; control commands (--stop/--stop-all) print confident success while the loop keeps running; completed loops disappear from --list within seconds of finishing, with --history never mentioned in that output; resumed loops run with their output discarded and their timeout reset to one week.

**Most Valuable Improvements:** 1) Make --stop/--stop-all actually signal workers (persist status 'stopped' and treat a missing state file as a stop in the pause-wait loop), so processes exit and state cannot resurrect. 2) Stop the global parser from consuming --timeout after a command and emit -t from the resume spawner. 3) Give resumed loops a visible log (redirect Stdio::null to a per-loop log and print its path). 4) Surface --history in --list output and print concise per-iteration results for plain-text mode.

**Usability Rating:** 5/10
