### Issue 2: `fill` fails on search textbox with "Element is not focusable" while `type` succeeds

**Severity:** Medium
**Category:** Reliability

#### Reproduction

```
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- goto "https://www.gov.cn/"
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- snapshot -v 0
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- fill e342 "人工智能"
```
The snapshot shows two textbox elements near the search form: `e340` ("text headSearchword") and `e342` ("text headSearchword 请输入关键字……"). `fill e342` fails; `type e340` succeeds.

#### Expected Behavior

`fill` on the visible search textbox (e342) should work, or the snapshot should clearly distinguish which element is the actually-focusable input vs. a decorative duplicate.

#### Actual Behavior

`ERROR: browser_type failed: Element is not focusable`. The user must try another ref (`e340`) and switch from `fill` to `type`.

#### Root Cause Analysis

The gov.cn page has two representations of the search box — a desktop version (`.pchide`) and a mobile version (`.mhide`), each with its own textbox. The accessibility tree reports both as `textbox` elements. The ref `e342` points to the mobile/hidden version which is not focusable in a desktop viewport. `fill` uses a different internal method than `type` and has stricter focusability requirements.

#### Code Pointer

``cli/browser4-cli/src/` — the `fill` command implementation should either fall back to `type`-style text insertion when `fill`'s native method fails, or provide a better error message suggesting to use `type` with a different ref.`

#### AI Suggested Improvement

- When `fill` fails with "not focusable", the error message should suggest trying `type` as an alternative
- Snapshot output should annotate hidden/non-focusable elements differently from visible/focusable ones (e.g., mark elements with `display:none` or zero dimensions)
- The accessibility tree could indicate which of two duplicate textboxes is the "active" one (e.g., by checking `offsetHeight > 0` as the page's own JS does)
- Consider making `fill` auto-fallback to `type` when the element is not focusable via the `fill`-specific method

### Issue 3: `press Enter` on search textbox triggers form GET instead of JS search handler

**Severity:** Medium
**Category:** Reliability

#### Reproduction

```
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- goto "https://www.gov.cn/"
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- type "人工智能" e340
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- press Enter
```

#### Expected Behavior

Pressing Enter on the search textbox should execute the same search as clicking the search button — opening the search results at `sousuo.www.gov.cn`.

#### Actual Behavior

The page reloads to `https://www.gov.cn/?t=govall&headSearchword=...` (the form's GET action). The JavaScript `goSearch()` function (which opens `window.open(..., '_blank')` to the actual search) is not triggered.

#### Root Cause Analysis

The gov.cn page uses both a `<form>` with a GET action and a JavaScript `onkeyup` handler (`listenerKeyUpEventFn`). `press Enter` triggers the browser's native form submission (GET to current page + query params) rather than the JS `keyup` event handler that calls `goSearch()`. The `press` command likely dispatches a `keydown`/`keyup` event that doesn't fully replicate native browser Enter behavior in the context of this specific page's JS event handling.

#### Code Pointer

``cli/browser4-cli/src/` — the `press` command's Enter key simulation. May need to ensure it triggers both `keypress` events and the form's submit event in a way that allows JS `preventDefault()` to intercept, or to check whether the page has an `onkeyup`/`onkeydown` handler and trigger that path.`

#### AI Suggested Improvement

- After `press Enter` on a textbox inside a form, detect whether the page navigated to the form's action URL vs. a different URL — if the form action was used but there's a search button present, suggest clicking the button instead
- Document in the help/skill that `press Enter` on forms with complex JS behavior may not work; recommend finding and clicking the submit button
- Add a `--submit` flag to `type`/`fill` that clicks the nearest submit button after entering text instead of relying on Enter key behavior

After every `Bash` tool call, `Shell cwd was reset to C:\Users\pereg`. While `--manifest-path` works as a workaround, it adds ~50 characters of verbosity per command and is not discoverable from help output.

#### Expected Behavior

There should be a straightforward way to discover the selectors used for content extraction. The help text for `htmlsnapshot` suggests `inspect` but the workflow isn't obvious.

The user must either:

### Issue 7: No built-in summarization without LLM API key configuration

**Severity:** Medium
**Category:** Product

#### Reproduction

The task requires summarizing an article into 5 key points. The `summarize` command exists but requires an LLM API key. Without one configured, `summarize` would fail.

#### Expected Behavior

Either: (a) a non-LLM summarization fallback (e.g., extract first N sentences, or key paragraphs), or (b) clearer documentation that summarization requires API key setup before use.

#### Actual Behavior

The `summarize` command is listed in the help and SKILL.md but cannot be used without pre-configuring LLM credentials. The user must manually read and summarize the content.

#### Root Cause Analysis

`summarize` is an LLM-dependent feature. The documentation mentions the LLM key requirement (§ LLM配置) but a first-time user might not notice this until they try to use the command.

#### Code Pointer
