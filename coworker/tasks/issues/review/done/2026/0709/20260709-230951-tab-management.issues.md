### Issue 1: tab-new reports misleading tab index

**Severity:** Medium
**Category:** UX / Product

#### Reproduction

```
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- goto "https://en.wikipedia.org/wiki/Web_scraping"
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- tab-new "https://news.ycombinator.com"
# Reports: "Switched to tab 1"
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- tab-new "https://en.wikipedia.org/wiki/Data_mining"
# Reports: "Switched to tab 2"
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- tab-list
# Shows: index 0=Data mining, 1=HN, 2=Web scraping
```

#### Expected Behavior

The `tab-new` reported index should match the actual index in `tab-list`. If a new tab is inserted after the current tab (Chromium default), the reported index should reflect the actual insertion position, not the pre-insertion total count.

#### Actual Behavior

`tab-new` reports "Switched to tab N" where N equals the number of tabs before insertion, but the tab is actually inserted at a different position (after the active tab). After creating two tabs, the list shows them at different indices than what was reported. The first tab (Web scraping) shifted from index 0 to index 2.

#### Root Cause Analysis

Tabs are inserted after the active tab (standard Chromium behavior), but the CLI message uses the pre-insertion tab count as the index. These are inconsistent. Additionally, when the active tab is not the last tab, existing tabs beyond the insertion point shift their indices.

#### Code Pointer

``cli/browser4-cli/src/main.rs` — the `tab-new` handler and the index reporting logic.`

#### AI Suggested Improvement

- Query the actual tab list after creation and report the verified index
- Document the insertion behavior clearly in help text and SKILL.md
- Consider adding a `--position` flag: `--position end` (append), `--position after-current` (default), `--position <N>` (specific index)
- Add a tip after `tab-new` suggesting users run `tab-list` to see actual indices

### Issue 2: Snapshot and Page info after tab-new show previous page content

**Severity:** Medium
**Category:** Reliability / UX

#### Reproduction

```
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- goto "https://en.wikipedia.org/wiki/Web_scraping"
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- tab-new "https://news.ycombinator.com"
# Output:
# Switched to tab 1 (https://news.ycombinator.com)
# ### Page
# - Page URL: https://en.wikipedia.org/wiki/Web_scraping    <-- WRONG
# - Page Title: Web scraping - Wikipedia                   <-- WRONG
```

#### Expected Behavior

After creating a new tab and navigating to a URL, the automatic snapshot and Page output should reflect the new page's content.

#### Actual Behavior

The `### Page` section shows the *previous* page (the tab we were on before `tab-new`). The snapshot is also captured before the new page loads. This occurred consistently for both `tab-new` operations.

#### Root Cause Analysis

`tab-new` switches to the new tab immediately but does not wait for the page to load before capturing the automatic snapshot and printing page info. The snapshot captures the previous tab's content or a transitional state.

#### Code Pointer

``cli/browser4-cli/src/main.rs` — The `tab-new` dispatch path should wait for page load before snapshotting, or the automatic snapshot should be deferred.`

#### AI Suggested Improvement

- Wait for the new tab's page to reach at least `DOMContentLoaded` before capturing the automatic snapshot
- Or, skip the automatic snapshot on `tab-new` entirely — let the user capture one explicitly
- Report the *actual* page URL from the snapshot, not the previous page's, to make the disconnect visible
- Add a `--no-wait` flag for users who want the current (fast but potentially stale) behavior

### Issue 3: Raw JSON leaks into human-readable output mode

**Severity:** Medium
**Category:** UX

#### Reproduction

```
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- tab-select 0
# Output includes: {"type":"ai.platon.browser4.chrome.PulsarWebDriver","description":"Driver#41"}
# Followed by normal human-readable Page/Snapshot output

cargo run --manifest-path cli/browser4-cli/Cargo.toml -- tab-new "https://news.ycombinator.com"
# Output includes: {"guid":"F539FDB4CADB1D3336A840FB4AB8725A","url":"https://news.ycombinator.com/"}
```

#### Expected Behavior

In default (human-readable) mode, output should be consistently formatted for human consumption. JSON objects should only appear with the `--json` flag.

#### Actual Behavior

`tab-select` emits a raw JSON driver descriptor and `tab-new` emits a raw JSON object with guid/url before the formatted output blocks. This is jarring and inconsistent — most other commands don't do this. A first-time user would think something is broken.

#### Root Cause Analysis

MCP tool responses (`browser.switchTab`, tab creation) include data that gets printed to stdout directly instead of being routed through the output formatter. The JSON appears before any formatting logic is applied.

#### Code Pointer

``cli/browser4-cli/src/main.rs` — The tab command dispatch handlers print raw MCP response data before the formatted page/snapshot output. Also check the MCP response formatter/printing logic.`

#### AI Suggested Improvement

- Route all MCP response data through the output formatter (JSON in `--json` mode, text in default mode)
- For driver info, convert to a human-readable line: "Driver: #41" instead of raw JSON
- For tab-new, show "Tab created: <guid> → <url>" as formatted text
- Add an automated test that greps all command outputs for raw JSON in non-`--json` mode

### Issue 5: tab-list triggers unnecessary full page snapshot

**Severity:** Low
**Category:** UX / Performance

#### Reproduction

```
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- tab-list
# Output includes:
# ### Snapshot
# [Snapshot](/home/vincent/.../snapshot-....yml)
# 💡 Tip: Run `snapshot -v 0` to see interactive element refs
```

#### Expected Behavior

`tab-list` is a read-only metadata query. It should return tab information (indices, titles, URLs) without capturing a full accessibility-tree snapshot. Users run `tab-list` to check state, not to capture page structure.

#### Actual Behavior

Every `tab-list` invocation captures and saves a full accessibility tree snapshot to disk. This is:
- Unnecessary I/O and disk usage
- Slower than a lightweight tab query could be
- Surprising — the user didn't ask for a snapshot
- Clutters the snapshot directory with files the user didn't request

#### Root Cause Analysis

`tab-list` shares the post-command code path that automatically captures snapshots after state-mutating operations. It should be in the `no_snapshot_commands()` list.

#### Code Pointer

``cli/browser4-cli/src/main.rs` — The `no_snapshot_commands()` function and the tab-list dispatch handler.`

#### AI Suggested Improvement

- Add `tab-list` to `no_snapshot_commands()` so it doesn't trigger an automatic snapshot
- If snapshot info is useful for tab-list (e.g., showing page load state), use lightweight CDP queries instead of full AX tree capture
- Document which commands trigger automatic snapshots and which don't

### Issue 9: Cargo build output noise obscures CLI output

**Severity:** Low
**Category:** UX

#### Reproduction

Every command run via `cargo run` shows:
```
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.48s
     Running `cli/browser4-cli/target/debug/browser4-cli <command>`
```
before the actual CLI output.

#### Expected Behavior

When running from source during development, the build output should be separable from the CLI output. The `development.md` docs mention `--quiet` but this requires discovery.

#### Actual Behavior

Every command is prefixed with two lines of build output. While harmless, it adds noise and makes it harder to scan the actual CLI output. The `--quiet` flag is documented in `development.md` but not in the main `--help` output (it's shown as `-q, --quiet` in global options but described as "suppress normal output, only show errors").

#### Root Cause Analysis

Cargo always prints build status to stderr, and `cargo run` prints the "Running" line. The `--quiet` global flag suppresses CLI output, not cargo output.

#### Code Pointer

`This is a workflow/docs issue rather than a code bug. The `--quiet` description could clarify its effect on cargo output when running from source.`

#### AI Suggested Improvement

- Add a dedicated tip in `--help` output when the binary is run via `cargo run`: "Tip: Use `-q` to suppress build output"
- Or, document the `cargo run --quiet` pattern more prominently in SKILL.md and development.md
- Consider adding a `cargo` alias/wrapper script that handles this automatically for development
