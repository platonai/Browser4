### Issue 1: Plain-text loop tasks fail without a configured LLM

**Severity:** High
**Category:** Reliability

#### Reproduction

```
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- loop --count 2 --interval 10 --name health-check "Navigate to https://httpbin.org/get, take a snapshot, and report the page status"
```

#### Expected Behavior

The plain-text task should be executed by the server, navigating to the URL. Or, if an LLM is required, the CLI should detect this early and give a clear error message.

#### Actual Behavior

The loop runs each iteration as if it works, but every iteration fails with:
```
[ERROR] Iteration 1: HTTP request timed out [tool=command_run, endpoint=http://localhost:8182/mcp/call-tool, timeout=30s]
```
The CLI reports "✓ Loop finished — 2 iteration(s) completed" misleadingly, despite both iterations failing.

#### Root Cause Analysis

The `submit_plain_command` function in `handle_loop` sends the text to `http://localhost:8182/mcp/call-tool`, which requires an LLM backend to interpret natural language instructions. Without a configured LLM, the request times out silently. The CLI does not validate whether the plain-text mode is usable before starting the loop.

#### Code Pointer

``cli/browser4-cli/src/main.rs:submit_plain_command()` and the pre-flight check before the loop execution.`

#### AI Suggested Improvement

- Add a pre-flight validation before starting a plain-text loop: send a lightweight probe to the server to verify the agent command endpoint is responsive, and fail fast with a clear error if not.
- In the loop summary, report failure vs success counts instead of always printing "✓ Loop finished". If all iterations failed, surface that prominently.
- Add a `--dry-run` or validation step that checks whether the task mode is supported before beginning the loop.
- Document in `--help` that plain-text mode requires a configured LLM provider.

### Issue 2: `--` separator incorrectly consumed by `parse_raw_args` before `build_command_args` rejects multi-token loop tasks

**Severity:** High
**Category:** Product

#### Reproduction

```
cargo run --manifest-path cli/browser4-cli/Cargo.toml -- loop --count 2 --interval 10 --name test -- batch "goto https://httpbin.org/get" snapshot status
```

#### Expected Behavior

The `--` should signal the end of loop options; everything after it (including multi-word subcommands) should be collected as the task for `handle_loop` to parse with its own `parse_loop_args`.

#### Actual Behavior

```
Error: error: too many arguments: expected 1, received 3
```
The main dispatch path calls `build_command_args` (main.rs:11311) which validates positional args against the command definition. Since the `loop` command defines only 1 optional arg (`task`), having 3+ tokens after `--` triggers validation failure. The loop's own `parse_loop_args` (which correctly handles variadic subcommand tokens) never gets a chance to run.

#### Root Cause Analysis

Two interacting problems:
1. `parse_raw_args` (args.rs:164) treats bare `--` as an unknown `--key` with empty string key, consuming exactly one following token as its value. It does not recognize `--` as the POSIX "end of options" marker.
2. The main dispatch (main.rs:11307-11311) calls `build_command_args` for all commands including `loop`, but `loop` uses its own `parse_loop_args` that should handle variadic tokens. The `build_command_args` check rejects the command before `handle_loop` can run `parse_loop_args`.

The combination means: `--` followed by N tokens consumes 1 as a phantom option value, leaving N-1 as positionals, which `build_command_args` rejects if N-1 > 1 (the loop's declared arg count).

#### Code Pointer

``cli/browser4-cli/src/args.rs:parse_raw_args()` (needs `--` end-of-options handling) and `cli/browser4-cli/src/main.rs:11311` (should skip `build_command_args` validation for `loop` command, or `loop` should declare a variadic argument).`

#### AI Suggested Improvement

- In `parse_raw_args`, add special handling for bare `--` to stop option parsing and treat all remaining tokens as positional arguments (POSIX convention).
- Alternatively, skip the `build_command_args` positional-count check for the `loop` command (similar to how `batch` and `act` bypass the standard dispatch at lines 11198 and 11291).
- Document the `--` separator behavior with examples showing multi-word subcommands.

### Issue 3: Completed loops are auto-cleaned with no indication in `--list` output

**Severity:** Medium
**Category:** UX

#### Reproduction

1. Run `loop --count 2 --interval 5 --name my-test --shell "echo hello"`
2. Wait for completion (2 iterations finish)
3. Run `loop --list`

#### Expected Behavior

Either the completed loop appears in `--list` with a "completed" status, or the `--list` output clearly directs the user to `--history` to find completed loops.

#### Actual Behavior

```
No persisted loops. Start one with `browser4-cli loop <task>`.
```
The loop ran, completed, and vanished. A user who returns to check on their loop finds nothing and may think it never ran.

#### Root Cause Analysis

`handle_loop` auto-clears the loop state file on normal completion (count reached, timeout, etc.) and writes a history entry instead. This is by design (the `keep-state` option exists to preserve it), but `--list` gives no hint that completed loops can be found via `--history`.

#### Code Pointer

``cli/browser4-cli/src/main.rs:handle_loop()` — the auto-clean at completion and the `--list` handler at ~line 8094.`

#### AI Suggested Improvement

- When `--list` finds no persisted loops, add a hint: "Use `browser4-cli loop --history` to see recently completed loops."
- Consider adding a `--status` column to `--history` that shows all loops (active + recent completions) in one view.
- Add a short-lived retention period (e.g., 60 seconds) before auto-cleaning completed loop state, so quick `--list` checks catch the completion.

#### Actual Behavior


The loop reports success with a checkmark even though every iteration errored. Only the `[ERROR]` lines buried in the output indicate failure.

The loop's completion summary at the end of `handle_loop` always uses "✓" and "completed" regardless of iteration outcomes. It doesn't aggregate success/failure counts.

- Use "✓" only when all iterations succeeded; use "⚠" for partial failure; use "✗" for total failure.

### Issue 5: `--shell` mode requires full path to browser4-cli binary for browser commands

**Severity:** Low
**Category:** UX / Documentation

#### Reproduction

A user wants to run browser4-cli commands in a loop. The `--` subcommand mode is the natural choice but fails for multi-command tasks (Issue 2). The `--shell` workaround requires knowing the compiled binary path:
```
loop --shell '/home/vincent/workspace/Browser4/cli/browser4-cli/target/debug/browser4-cli goto ... && .../browser4-cli snapshot && .../browser4-cli status'
```

#### Expected Behavior

There should be a straightforward way to run multiple browser4-cli commands in a loop iteration without shell path gymnastics.

#### Actual Behavior

The user must construct a fragile shell command with absolute paths to the compiled binary.

#### Root Cause Analysis

The `--` subcommand mode invokes `run_browser4_cli` which calls `std::env::current_exe()` — this would work correctly if the `build_command_args` validation didn't reject multi-token tasks first. The underlying mechanism is sound; the validation gate is the only obstacle.

#### AI Suggested Improvement

- Fixing Issue 2 would largely resolve this, since `-- batch "goto..." snapshot status` would then work directly.
- As a secondary improvement, the `--` mode could support multiple browser4-cli invocations by splitting on `&&` or `;` within a single positional.

### Issue 6: `--help` for `loop` shows option names but lacks examples

**Severity:** Low
**Category:** Documentation / Discoverability

#### Reproduction

Run `cargo run --manifest-path cli/browser4-cli/Cargo.toml -- loop --help` (or the equivalent).

#### Expected Behavior

The help output should include concrete examples for the three task modes (plain text, `--shell`, `--`) and common lifecycle operations (pause/resume/stop).

#### Actual Behavior

The main `--help` output has a dense one-line description for `loop`. The detailed help, when run, lists all options but does not show usage examples for the different modes.

#### Root Cause Analysis

The help system prioritizes option enumeration over task-mode examples. The `loop` command is conceptually complex (three modes, lifecycle management, persistence) and examples would significantly reduce the learning curve.

#### AI Suggested Improvement

- Add an "Examples" section to `loop --help` showing:
  - Plain-text: `browser4-cli loop "check if the login page loads" --interval 300`
  - Shell: `browser4-cli loop --shell "curl -s https://api.example.com/health" --interval 60`
  - CLI subcommand: `browser4-cli loop --count 5 --interval 10 -- status`
  - Lifecycle: `browser4-cli loop --pause --name my-loop` / `--resume --name my-loop` / `--stop --name my-loop`
- Add a quick-start workflow to the main help: "Quick start: loop --shell 'date' --interval 5 --count 2 --name my-test"
