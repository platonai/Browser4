### Issue 2: Backend times out after `htmlsnapshot summary` on large pages, requiring session restart

**Severity:** High
**Category:** Reliability

#### Reproduction

```bash
goto "https://baike.baidu.com/item/华为技术有限公司/6455903"
htmlsnapshot                          # Works (returns metadata)
htmlsnapshot summary                  # Times out after 60s
```
After the summary timeout, ALL subsequent commands (eval, htmlsnapshot get, goto) fail with "Ping timeout" or "HTTP request timed out".

#### Expected Behavior

A single command that times out should not corrupt subsequent operations. The backend should recover gracefully.

#### Actual Behavior

`htmlsnapshot summary` on a 3.3MB page caused a persistent backend hang. Only closing and reopening the session (`close` → `goto`) restored functionality. The `status` command reported "Server health: UP" even while operations were failing.

#### Root Cause Analysis

The summary generator may be holding a lock or blocking a thread that subsequent operations also depend on. The timeout is detected by the CLI HTTP layer, but the backend operation continues running and blocks the browser session.

#### Code Pointer

`Backend `html_snapshot_summary` MCP tool implementation; session-level resource locking.`

#### AI Suggested Improvement

- Add a hard timeout on backend summary generation that kills the operation and releases resources
- Isolate summary computation from the browser interaction thread
- Return partial results if summary exceeds a time budget
- Have `status` report whether the browser session is actually responsive, not just the HTTP listener

### Issue 3: `eval` and `htmlsnapshot get` fail with generic "Ping timeout" — no diagnostic info

**Severity:** Medium
**Category:** Reliability / UX

#### Reproduction

```bash
eval "document.title" --json
# → ERROR: browser_evaluate failed: Ping timeout
htmlsnapshot get all text ".basicInfo-item.name" --all
# → HTTP request timed out [timeout=30s]
```

#### Expected Behavior

Error messages should indicate whether the timeout is due to (a) backend overload, (b) page JavaScript not loaded, (c) selector evaluation taking too long, or (d) session hung.

#### Actual Behavior

Both produce "timeout" messages with no diagnostic information. The user can't tell if the problem is the command, the selector, the page, or the session state.

#### Root Cause Analysis

Timeout errors from the backend are passed through without classification. The CLI layer doesn't distinguish between different timeout causes (page load, JS execution, selector matching, backend hung).

#### Code Pointer

`CLI error formatting layer; backend MCP tool timeout handling.`

#### AI Suggested Improvement

- Classify timeout errors by phase: "page not ready", "JS execution timeout", "backend unresponsive", "session hung"
- After a timeout, automatically run a lightweight health check and report whether the session is still usable
- Add a `--timeout` flag to allow users to extend timeouts for large pages

### Issue 4: `htmlsnapshot get` on React-based sites returns empty matches — no guidance to fall back

**Severity:** Medium
**Category:** UX / Discoverability

#### Reproduction

```bash
htmlsnapshot get all text ".basicInfo-item" --all
# → [] No elements matched ".basicInfo-item".
# → Try `htmlsnapshot inspect ".basicInfo-item"` to discover valid selectors
```

#### Expected Behavior

The error message suggests `htmlsnapshot inspect`, which is reasonable. But `htmlsnapshot inspect` also timed out on this page. The user needs to know about the `eval` fallback option.

#### Actual Behavior

The "try inspect" suggestion leads to another timeout. No mention of using `eval` as an alternative extraction method. The decision tree in SKILL.md §4a correctly puts "Dynamic/complex JS logic" → `eval`, but this guidance doesn't appear in CLI error messages.

#### Root Cause Analysis

CLI error messages for `htmlsnapshot get` only suggest `htmlsnapshot inspect`. They don't mention `eval` as a fallback when selectors don't match or when the page uses dynamic rendering.

#### Code Pointer

`CLI `htmlsnapshot get` error handling.`

#### AI Suggested Improvement

- Add to the "No elements matched" error: "For dynamic/JS-rendered pages, try `eval` with JavaScript to query the live DOM"
- Make `htmlsnapshot inspect` more resilient to large pages (add timeout, return partial results)
- Add a `htmlsnapshot get --live` flag that queries the live DOM via JS instead of the stored static snapshot

### Issue 5: `htmlsnapshot summary` is not resilient to large pages (3.3MB HTML)

**Severity:** Medium
**Category:** Reliability

#### Reproduction

```bash
goto "https://baike.baidu.com/item/华为技术有限公司/6455903"
htmlsnapshot               # Reports 3348 KB
htmlsnapshot summary        # Times out after 60s
```

#### Expected Behavior

The summary command, which is designed to compress pages to <1% of original size, should handle a 3.3MB page within a reasonable time budget. Or it should report that the page is too large and suggest alternatives.

#### Actual Behavior

The command hangs for 60 seconds then times out, and the timeout corrupts the session state (see Issue 2).

#### Root Cause Analysis

The summary algorithm may have exponential complexity on certain page structures, or it may be trying to process every DOM node in a deeply nested tree.

#### Code Pointer

`Backend `html_snapshot_summary` MCP tool; WPSI generation algorithm.`

#### AI Suggested Improvement

- Add a node budget (e.g., cap at 50K DOM nodes) with graceful degradation
- Implement progressive summary generation with a time budget
- Return an error immediately for pages exceeding a configurable size threshold
- Document the expected page size limits for each command

### Issue 6: `eval` on Windows requires `--file` workaround for any non-trivial JS

**Severity:** Low
**Category:** UX

#### Reproduction

```bash
eval "JSON.stringify({title: document.title})" --json
# → ERROR: browser_evaluate failed: Ping timeout
# (Actually caused by shell quoting issues that break the JS before sending)
```

#### Expected Behavior

Either the quoting works, or the error message clearly indicates the expression was malformed due to shell escaping.

#### Actual Behavior

Shell quoting silently corrupts the JS expression, and the resulting error ("Ping timeout") is misleading. The documented workaround (`--file`) works but adds friction — requires writing to a temp file for every query.

#### Root Cause Analysis

Windows Git Bash and the Rust argument parser interact poorly with nested quotes. This is documented in SKILL.md §5 but the error produced is not recognizable as a quoting issue.

#### Code Pointer

`CLI `eval` command argument parsing; error detection for malformed JS.`

#### AI Suggested Improvement

- Detect common quoting errors (unbalanced quotes, escaped characters) and warn before sending to backend
- Support `eval --stdin` as default when no positional expression is provided
- Add `eval --interactive` for REPL-style input that avoids shell entirely

### Issue 7: `cargo run` compilation output adds noise to every invocation

**Severity:** Low
**Category:** UX

#### Reproduction

Every `cargo run --manifest-path ... -- <cmd>` prints:
```
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.58s
     Running `cli\browser4-cli\target\debug\browser4-cli.exe ...`
```

#### Expected Behavior

Clean output with only the CLI response visible, or a clear documented fast-path.

#### Actual Behavior

Even though the compilation check is fast (0.5–0.8s), the two extra lines per command add up to ~50 lines of noise across 25 commands. The `--quiet` flag documented in development.md only partially helps.

#### Root Cause Analysis

`cargo run` always prints build status. `--quiet` suppresses stderr but not the "Finished" line.

#### Code Pointer

``skills/browser4-cli/references/development.md`.`

#### AI Suggested Improvement

- Document the two-step build pattern prominently: `cargo build` once, then invoke the binary directly for all subsequent commands
- Consider a wrapper script (`dev-cli.sh`/`.ps1`) that builds once and proxies subsequent calls
- Add a project-level `justfile` or script for dev ergonomics

### Issue 8: Session close loses all page state — no `snapshot save` / `snapshot restore`

**Severity:** Low
**Category:** UX

#### Reproduction

When the session hung (Issue 2), the only recovery was `close` → `goto`. This required re-searching for the Huawei page, re-navigating to the Baike entry, and re-extracting all data. The first extraction's data was only available because it had been captured to a temp file manually.

#### Expected Behavior

A way to save extracted data or the session state so that recovery doesn't lose all work. Or: the backend auto-recovers without requiring session close.

#### Actual Behavior

`close` terminates the browser and all page state. No built-in mechanism to checkpoint extraction progress.

#### Root Cause Analysis

Session persistence saves cookies/localStorage but not page content or extraction state.

#### Code Pointer

`Session management; state persistence layer.`

#### AI Suggested Improvement

- Add `session-save <name>` and `session-restore <name>` for full session checkpointing
- Auto-save the last snapshot before close
- At minimum, document that `close` is destructive and suggest saving data first
