## Issues Found (7 issues)

### Issue 1: No built-in product card extraction for e-commerce pages

**Severity:** High
**Category:** Product

#### Reproduction

Try to extract correlated product data (title + price + rating + URL) from an Amazon/Best Buy/Walmart search results page.

#### Expected Behavior

A single command or documented workflow that produces a table of product data: `./b4w.ps1 htmlsnapshot extract-products` or `./b4w.ps1 htmlsnapshot query --preset amazon-search`.

#### Actual Behavior

User must: manually discover selectors for each field (often requiring Amazon-specific CSS knowledge), run 4+ separate `get all` commands, and manually correlate the arrays — which is error-prone and time-consuming. The SKILL.md explicitly warns: 'Multiple get all calls produce unaligned arrays.'

#### Root Cause Analysis

The extraction system is powerful but low-level. There is no abstraction for the common 'extract product listings from a search results page' use case. X-SQL can do correlated extraction but requires writing a full SQL query with domain-specific functions (DOM_FIRST_TEXT, DOM_FIRST_ATTR), which is a steep learning curve for a first-time user.

#### AI Suggested Improvement

- Add an `htmlsnapshot extract-products` command with built-in heuristics for common e-commerce patterns (product cards with title/price/rating/image)
- Provide preset X-SQL templates for Amazon, eBay, Walmart, etc. in the documentation
- Add a `--correlate` flag to `get all` that groups results by parent container when given multiple selectors
- Document the X-SQL approach more prominently in the core loop section of SKILL.md

### Issue 2: Snapshot output impractical for content-rich pages

**Severity:** Medium
**Category:** UX

#### Reproduction

./b4w.ps1 snapshot -v 0 --stdout on amazon.com search results

#### Expected Behavior

Manageable output that lets a user find product elements without being overwhelmed. Pagination, summary, or automatic viewport scoping should keep output under a few KB.

#### Actual Behavior

Output was 63.1KB and was truncated by the tool harness. The snapshot contains thousands of lines of accessibility tree — far too much for a human or agent to scan for individual product elements.

#### Root Cause Analysis

The accessibility tree includes every DOM node (including deeply nested generics, hidden navigation elements, etc.). Viewport pagination (-v 0) limits depth but e-commerce pages with dense product grids still produce massive trees. The SKILL.md warns about this but the default experience for a new user following the core loop is poor.

#### Code Pointer

`cli/browser4-cli/src/snapshot.rs — snapshot rendering logic`

#### AI Suggested Improvement

- Add a `--compact` or `--summary` mode that shows only interactive elements (links, buttons, inputs) with their text and refs, skipping structural generics
- Auto-detect when snapshot exceeds a threshold and suggest `htmlsnapshot capture` instead
- Consider making `--stdout` default to a more concise format, with `--full` for the complete tree

### Issue 3: htmlsnapshot inspect defaults to analyzing wrong DOM pattern

**Severity:** Medium
**Category:** Discoverability

#### Reproduction

./b4w.ps1 htmlsnapshot inspect (with no selector argument) on an Amazon search results page

#### Expected Behavior

Auto-discovery identifies the most prominent repeating pattern — product cards with title, price, rating — and suggests selectors for them.

#### Actual Behavior

Analyzed <div> elements and picked up navigation keyboard shortcut elements from a hidden shortcuts menu as the repeating pattern. Suggested selectors like `span.shortcut-key.nav-assistant-card-font` which are useless for product extraction.

#### Root Cause Analysis

The inspect command defaults to analyzing `div` elements. The hidden navigation menu (`#shortcut-menu`) contains repeating div structures that score high as a pattern. Product cards on Amazon use complex nested divs and the inspect heuristics don't prioritize visible, high-value content areas over hidden navigation.

#### Code Pointer

`browser4-rest/ — htmlsnapshot inspect logic (likely in an HTML snapshot analysis service)`

#### AI Suggested Improvement

- Prioritize visible content areas over hidden/offscreen elements (the navigation was at box=-9988, clearly offscreen)
- Weight elements by viewport visibility and text content richness
- When inspect is called without arguments, try multiple common container selectors (div[data-*], li, article) and report the best
- Allow `htmlsnapshot inspect "div[data-component-type]"` to be documented as the recommended pattern for Amazon-style product grids

### Issue 6: Extracted prices lack currency context

**Severity:** Low
**Category:** Product

#### Reproduction

./b4w.ps1 htmlsnapshot get all text "span.a-price-whole" --limit 10 on Amazon with non-USD delivery address

#### Expected Behavior

Prices include currency symbol (¥1,031) or the currency is indicated in the output metadata.

#### Actual Behavior

Prices extracted as bare numbers: "1,031", "1,146". No currency symbol or code. User must infer currency from page context (the 'Deliver to Japan' header).

#### Root Cause Analysis

Amazon's price rendering splits the currency symbol (¥) and the numeric amount into separate DOM elements. `span.a-price-whole` only contains the numeric part. The currency symbol is in a separate `span.a-price-symbol` element.

#### AI Suggested Improvement

- Document in SKILL.md that for Amazon prices, extract both `span.a-price-symbol` and `span.a-price-whole`
- Consider adding a `--price` convenience selector that combines symbol + whole + fraction
